One server, several CXL memory pools: what public sources say
=============================================================
Written 2026-10-21 by a research agent from public sources; URLs cited inline.

Method and limits. Sources are vendor pages, the Linux kernel CXL docs, the
QEMU CXL docs, CXL Consortium white papers/blog posts and two peer-reviewed
papers. Intel's and Arm's own spec pages, Micron CZ120, MemVerge and the Hot
Chips program were JavaScript-only or blocked, so their wording comes from
third parties and is marked as such. Unverified items are labelled.

  https://neoverse-reference-design.docs.arm.com/en/latest/features/cxl.html
- Arm CMN S3 blog (search snippet; page is JS-only): CMN S3 "supports
  CXL.mem(Type3) and CXL.cache(Type1) functionality and is complaint with CXL
  specification revision 2.0 and CXL 3 revision 3.0 version."
  https://developer.arm.com/community/arm-community-blogs/b/servers-and-cloud-computing-blog/posts/arm-cmn-s3-driving-cxl-storage-innovation
- AmpereOne brief: "128 lanes PCIe 5.0 with 32 controllers (1P)", "up to
  eight x16 devices"; no CXL mention. NVIDIA Grace CXL support: unverified.
  https://amperecomputing.com/briefs/ampereone-family-product-brief

Does each root port form an independent hierarchy? Yes.
- Linux: "A Host Bridge is a special type of CXL switch port" (ACPI0016) with
  "one or more downstream port connections"; worked example is "a
  single-socket system with 4 host bridges"; "Only root decoders are capable
  of Inter-Host-Bridge Interleave".
  https://docs.kernel.org/driver-api/cxl/linux/cxl-driver.html
- QEMU: each host bridge "has 2 CXL Root Ports and programmable HDM decoders
  to route memory accesses either to a single port or interleave them across
  multiple ports." https://www.qemu.org/docs/master/system/devices/cxl.html
- Octopus sec. 5.4: pods normally interleave pooling devices at 256 B, but
  "Octopus disables this interleaving in firmware and exposes each CXL port as
  a distinct NUMA node". Sec. 2: passive copper is limited to "<= 1.5 m"
  without retimers or optics.

3. Multi-pool per host: evidence
--------------------------------
Linux driver model (one root, many hierarchies)
- cxl_acpi creates the root "if the ACPI0017 ... Root Object Device Class is
  found"; host bridges from CEDT CHBS, root decoders from CFMWS; "The CXL root
  is a special type of switch port, in that it only has downstream port
  connections." https://docs.kernel.org/driver-api/cxl/linux/cxl-driver.html
- CFMWS "describes a memory region associated with one or more CXL host
  bridges"; "INTRA-host-bridge interleave ... is NOT reported in this
  structure". https://docs.kernel.org/driver-api/cxl/platform/acpi/cedt.html
- "Linux will create a NUMA node for each CEDT CFMWS entry"; BIOS may publish
  one window across all bridges, one per bridge and one per device.
  https://docs.kernel.org/driver-api/cxl/platform/bios-and-efi.html
- "Flexible presentation": two host bridges, seven CFMWS (cross-bridge, per
  bridge, per device) over the same hardware, "to provide the user flexibility
  to configure the memory devices in various interleave or NUMA node
  configurations".
  https://docs.kernel.org/driver-api/cxl/platform/example-configurations/flexible.html
- "The CXL Port topology is enumerated by the arrival of a CXL.mem device."
  https://docs.kernel.org/driver-api/cxl/theory-of-operation.html
- The FM is "an external, privileged host with privileges to change
  configurations for other hosts"; "As of v6.14, Linux does not provide a
  formalized interface to manage non-DCD MHSLD or MHMLD devices"; DCD is
  "active work on LKML".
  https://docs.kernel.org/driver-api/cxl/devices/device-types.html
- Maturity map: "[0] Dynamic Capacity Device (DCD) Support", "[0] Sharing",
  "[0] Fabrics / G-FAM (chapter 7)", "[0] Switch CCI", "[1] Hotplug of LDs
  (via PCI hotplug)". https://docs.kernel.org/driver-api/cxl/maturity-map.html
- QEMU "will also completely ignore the fabric management aspects of CXL by
  considering only a single host and a static configuration"; "Hosts often
  have no awareness of complex rerouting and device pooling, they simply see
  devices being hot added or hot removed."
Spec concepts
- CXL 3.0 white paper: pooling "with or without a CXL 2.0 switch"; sharing =
  coherent multi-host access; fabrics "can support up to 4096 nodes" via Port
  Based Routing; "A GFAM device is like a traditional CXL Type-3 device,
  except it can be accessed by multiple nodes (up to 4095)".
  https://computeexpresslink.org/wp-content/uploads/2023/12/CXL_3.0_white-paper_FINAL.pdf
- CXL 3.1 white paper: "fabric manager API definition for PBR switch", GIM for
  inter-host communication; "Hosts rely on the switches to do the appropriate
  mapping."
  https://computeexpresslink.org/wp-content/uploads/2023/12/CXL_3.1-White-Paper_FINAL.pdf
- CXL 4.0 Q&A: "MLDs require a switch, which handles mapping the traffic from
  individual LDs to the physical CXL link connected to the host"; bundled
  ports not extended to MH-SLD/MH-MLD.
  https://computeexpresslink.org/blog/introducing-the-cxl-4-0-specification-webinar-qa-recap-4386/
Can one host see two FM domains? Nothing found binds a host to one FM. The FM
manages a switch or device, not the host; each product ships its own (H3
management center, Samsung SCMC, Liqid Matrix, UnifabriX FM, Montage FM on a
BMC). A host with ports into two appliances has two independent hierarchies
under two FMs. Direct evidence:
- Octopus (arXiv 2501.09020v3): "Octopus assumes X=8 CXL ports per server and
  N=4 ports per MPD", each port to a different pooling device, each "a
  distinct NUMA node"; prototype of three EPYC 9825 servers, each wired by
  two x8 ports to two different 2-port devices ("X=N=2"); 267 ns read
  latency, 24.7 GiB/s per x8 link.
- Montage's 2026 DCD demo adopts that topology (hosts spanning controllers).
- Samsung's white paper: one host via three USPs into one CMM-B sees three
  HDM ranges (multi-port into one pool).
- Not found: a public demo of one server on two switch-based appliances from
  different vendors.


4. Attaching one server to several pools: pros and cons
-------------------------------------------------------
Advantages
- Capacity past one box: 5.5 TB (H3 C5022), 24 TiB (CMM-B), ~100 TB per switch
  pool (XConn/Liqid); extra ports are the only way beyond a box unless the
  vendor has a backend fabric (UnifabriX).
- Bandwidth: Linux sums per host bridge and "The sum across ACPI0017 entries
  becomes the region's bandwidth coordinate"; one x8 Gen5 link is ~25 GiB/s
  (Octopus), Samsung measured +32% from three ports.
  https://docs.kernel.org/driver-api/cxl/linux/access-coordinates.html
- Latency tiers: direct multi-headed pools avoid the switch hop ("A CXL switch
  has 2.4x higher latency", "at least 220 ns" of re-serialization, Octopus);
  a host can hold a small fast pool and a large shared pool at once.
- Blast radius: each pool is its own hierarchy and NUMA node; hot-remove of
  one device cleans only "the port data that was established to support that
  Memory Expander"; sparse direct pools cut switch cost ("switches remain an
  order of magnitude more expensive than MPDs").
- Sharing domains: rack-local capacity pool plus a wider shared pool (GIM/GFAM
  or optical inter-rack links) map onto separate host bridges naturally.
Disadvantages and constraints
- Port budget: 64 CXL lanes per socket = 4 x16 or 8 x8; GPUs and NICs compete
  for the same lanes; copper <= 1.5 m without retimers.
- Static CFMWS: "Hot-adding a memory device requires this pre-defined, static
  CFMWS to have sufficient HPA space"; "some platforms omit the CFMWS in the
  CEDT. When this occurs, hot-add is not possible"; "Hotplugged devices cannot
  add host-bridge interleave capabilities at hotplug time."
  https://docs.kernel.org/driver-api/cxl/platform/device-hotplug.html
- Decoders: "A port may contain one or more decoders" (fixed by hardware);
  "expect to use one decoder per contiguous chunk of host physical memory";
  "Unbalanced interleave sets are not supported"; asymmetric topologies abort
  the bandwidth calculation. Interleaving across pools run by two FMs would
  need identical extents and symmetric paths; not forbidden by the docs, not
  documented by any product (inference).
- NUMA: each window is another node; software "must be NUMA optimized, which
  takes time and effort" (CXL 4.0 Q&A).
- Management: two FMs and APIs (Redfish/REST, CXL 3.2 FM API); the kernel has
  no DCD/sharing support yet, so allocation is vendor-tool driven.
- Cost and cabling: more CDFP/OSFP cables, HBAs or retimers; Octopus puts
  pooling at 5% of server CapEx for sparse direct pools vs 12% for switches.


5. Conclusion
-------------
A server attached to two CXL pools at once is realistic with 2025/2026
hardware: Xeon 6 and EPYC 9005 expose 64 CXL 2.0 lanes as four x16 or eight
x8 root ports, each an independent ACPI0016 hierarchy with its own CFMWS and
NUMA node, and appliances from H3, Samsung, Liqid and UnifabriX as well as
the Montage/Astera multi-headed controllers all attach with one x8/x16 cable
per host. Microsoft's Octopus work and Montage's 2026 demo already run hosts
with ports into several pooling devices; what is not yet public is one host
on two switch-based appliances from different vendors, and the kernel still
lacks DCD/sharing plumbing, so capacity moves through each pool's own FM. For
the emulated setup (each VM: two pxb-cxl host bridges, each with a 4-port
switch) the closest real shape is "rack-local pool on host bridge 0, global
shared pool on host bridge 1": pool A on host bridge 0 of servers 1-2 (small,
low-latency, Octopus/H3 style) and pool C on host bridge 1 of all servers
(the sharing domain, CMM-B/switch style). Give each pool its own cxl-fmw
(QEMU's two-bridge example does exactly this), do not interleave across the
two bridges, and treat each pool as a separate NUMA node and a separate
fabric-manager domain.
