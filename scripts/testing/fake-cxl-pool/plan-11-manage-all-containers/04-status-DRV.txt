Lock order and why it is deadlock-free
--------------------------------------
  nodeLocks claim lock -> localAllocator.mu | poolDriver.mu -> lendMu ->
  p.mu -> {nodeFence.mu, baseState mutex (GetClaimInfo), pool serialsMu}
  - Fence takes nodeFence.mu alone and releases it before the pass.
  - The pass (fenceContainers): p.mu briefly (readiness), lendMu, p.mu
    (collect), p.mu released, UpdateContainers, p.mu (record). p.mu is
    never held across UpdateContainers; nodeFence.mu, baseState and
    serialsMu are leaves held only while reading.
  - changeLend (unchanged order): lendMu -> p.mu, released before
    UpdateContainers. pool Prepare already did poolDriver.mu -> lendMu
    (lender.lend); Fence adds the same edge, and the local allocator adds
    localAllocator.mu -> lendMu. Nothing that holds lendMu or p.mu waits for
    localAllocator.mu, poolDriver.mu or a claim lock.
  - NRI handlers take only p.mu, baseState (claimedMemory, claimNodes),
    serialsMu and nodeFence.mu; none of them is held across
    UpdateContainers, so containerd's event/update lock cannot close a
    cycle. CreateContainer reads claims before p.mu.
  - Passes started by Synchronize and LendsRestored run in goroutines
    (startFencing, called with p.mu held, only spawns); passes from Fence
    run in the Prepare's goroutine, never in an NRI handler.
  - The broker calls LendsRestored from its reconcile goroutine without
    b.mu held.
  Race-freedom of CreateContainer vs. a pass: Fence adds the node to F
  before the pass takes p.mu, and CreateContainer reads F inside its p.mu
  section, so a new container either sees the node in F (adjusted) or is
  tracked before the pass collects (updated by it).

Deviations from 02-design, with reasons
---------------------------------------
  1. The local allocator gets the fence by field assignment in
     newDriverState right after newLocalHelper, not as a parameter of
     newLocalHelper: TestNewLocalHelper calls newLocalHelper with its
     current signature and must stay unchanged; Reconcile (inside
     newLocalHelper) never onlines memory, so nothing is missed. Same for
     the pool driver: loadPoolDriver(..., fence) sets pool.fence after
     newPoolDriver, whose signature the pool tests use.
  2. changeLend in allowed-mems mode: base = own(c) - F - {node} (also
     minus the node being lent or revoked, as none mode does), so a revoke
     drops the node even if it were not fenced.
  3. A steered container in allowed-mems mode: a revoke never updates it
     (D4: steered containers never updated). In none mode the old code
     runs (it may shrink cpuset.mems through cgroupMemsContain, as today).
  4. want that is empty (own nodes all fenced, no claims, no lends) is
     treated as unknown: the container is left as it is with a warning
     (cpuset.mems "" through NRI means "unchanged").
  5. Synchronize refreshes tc.mems from the runtime's spec for every
     container, also known ones (reconnect), so a lost update is redone.
  6. "Warning once at Fence": logged at each Fence that adds a node while
     NRI did not start, i.e. once per node. Fence calls before NRI starts
     (window between kubeletplugin.Start and startNRIPlugin) only record:
     the readiness pass covers them.
  7. fenceWG (a WaitGroup of background passes) exists so that the unit
     tests can wait for them; Stop does not wait on it.
  8. Late fences have their own V(3) log texts (not given by D8, listed
     above).

Fixes after review (05-review.txt V1, V2)
-----------------------------------------
V1 D/fence.go: nodeFence.fenceMu (new) serializes Fence: held across the
   check, the add and the pass. A concurrent Fence of a node that is
   being fenced (local and pool Prepare under one host bridge) returns
   only after the pass of the first one. f.mu stays the short lock of
   the set that NRI handlers take through Nodes(). Lock order now:
   claim lock -> localAllocator.mu | poolDriver.mu -> fence.fenceMu ->
   lendMu -> p.mu -> {fence.mu, baseState, serialsMu}. Nothing that holds
   lendMu, p.mu or fence.mu takes fenceMu (only Fence does), so no cycle.
   Header comments of fence.go and lend.go state the order.
V2 D/nri.go StartContainer, D/lend.go fenceMissed (new): with p.mu held,
   after trackStarted, when fencing is ready, the fenced set is not
   empty, the container is fenced and not steered, and wantMems differs
   from its recorded mems, StartContainer calls startFencing: the pass
   runs in a goroutine (it waits for lendMu and p.mu), never inside the
   handler. No new log text (the pass logs as before).
