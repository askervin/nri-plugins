Must fix
--------
V1 (major) fence.go Fence: a concurrent Fence of the same node returns
   before the containers are fenced.
   Fence adds the node under f.mu and runs the pass after releasing it.
   A second Fence of the node sees it in the set and returns at once.
   Local Prepares (localAllocator.mu) and pool Prepares (poolDriver.mu)
   run concurrently, and a local memdev and a pool device under one CXL
   host bridge share a node: the second Prepare onlines memory on N while
   the first one's pass is still updating containers. Fix: serialize
   Fence callers with a lock of their own (held across the check, the
   add and the pass; not f.mu, which NRI handlers take through Nodes),
   so that Fence(N) returns only after the pass that fenced N. Lock
   order: that lock -> lendMu -> p.mu. Unit test: two concurrent Fence of
   one node, the second returns after the first's UpdateContainers.

V2 (major) nri.go StartContainer: an update that raced with the
   container's creation is never retried before the container runs.
   containerd adds a container to its store after the NRI CreateContainer
   round returns (internal/cri/server/container_create.go). A pass that
   runs in that window (Fence from a Prepare: the handler saw the old
   fenced set, e.g. empty, and recorded mems "") sends an update that
   fails with "not found"; the next pass comes only with the next Fence
   or Synchronize, so the container starts inheriting the node that is
   onlined right after. Fix: in StartContainer, when the container is
   fenced, not steered, the fenced set is not empty, fencing is ready and
   wantMems differs from its recorded mems, start a pass in the
   background (startFencing, after p.mu is released by the handler; never
   synchronously). Unit test: a failed update of a created container is
   applied at its StartContainer.
