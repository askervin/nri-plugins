Flag and fields
---------------
  -config-key string   key of the controller's settings in pool.opaque of
                       MemoryConfig entries (default "fake-cxl-pool")
  pool.opaque.<key>:   slot (string, exact CXL slot bus of the host),
                       numaNode (integer >= 0, slot preference); strict
                       (unknown fields, wrong types refused).
  -> api.AttachRequest{Slot, NumaNode} (server chooseSlotLocked: Slot is
     exact, refused if unknown (InvalidArgument -> AttachError) or occupied
     (Conflict); NumaNode adds to the score of free slots).

Decisions
---------
C1. CheckEntries before Resolve: an invalid entry of the driver for
    another request of the claim also gives InvalidConfig (the node
    driver refuses the whole claim for it in Prepare, so attaching would
    only leave a device attached until deallocation).
C2. Resolve validates the container section: an invalid steering value
    is an invalid MemoryConfig for the controller too (InvalidConfig).
    The device section is not read (Resolve does not check it).
C3. numaNode < 0 is refused by the controller (the server would treat it
    as no preference silently).
C4. Existing attachments are never moved: the settings go into the attach
    request only when no attachment of the device to the host exists. The
    exclusive-flag update of an existing attachment is sent without them
    (the server would answer Conflict for another slot). A mismatching
    slot is logged once; the Attached message names the real slot.
C5. Several claims on one attachment (shared device, same node): the
    first claim in namespace/name order owns and places it (desired[k][0],
    as for the owner already); the others share it whatever their
    settings (C4 log for a different slot).
C6. An invalid result whose status entry is Attached already (possible
    only if another controller version or key attached it: the
    allocation's config is immutable) keeps its attachment and status; the
    error is logged with " (attached already, kept)". Never detaches a
    device in use.
C7. Not half attached: an invalid want is not desired, so an attachment
    of its own (no Attached condition) is detached in the same reconcile
    (TestConfigInvalidNotHalfAttached); a shared attachment of a valid
    claim on the node stays (TestConfigInvalidSharedWithValid).
C8. Stable: the error comes from the immutable allocation, the condition
    write is skipped when reason and message are unchanged, the log is
    deduplicated; tests check no attach, no detach, no status write, no
    event and one log line over further reconciles.
