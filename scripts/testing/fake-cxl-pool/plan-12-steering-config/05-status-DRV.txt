Deviations from 04-contract, with reasons
-----------------------------------------
V1. Every result of the driver is resolved before any device is touched
    (both drivers; also before the lend check of a companion claim): a
    value error never touches a device or marks a lease Lending. The
    device rules stay per result in result order (they need the device),
    so a device-rule error of a later result rolls back the earlier
    results, as before.
V2. "steering policy %s: no numa memory to steer" is logged only for
    containers that use results; with a node default other than none it
    would be printed for every container without claims. The management
    line shows the policy for all.
V3. A container learned at Synchronize whose settings no longer combine
    (state changed under it) is taken as steered: not fenced, not lent
    to (warning logged), as hasSteeredClaims did for errors.
V4. changeLend never changes cpuset.mems of a steered container, also on
    revoke with fencing none (before: plan-11 none mode could rewrite it
    from its base); steered cpuset.mems is cgmpolmgr's.
V5. Fenced is decided from the effective fencing only; the fenced node
    set exists only for node default allowed-mems. Equivalent today
    (entries cannot set fencing); with admin-only fencing later the
    fence set must exist whenever any container can be fenced.
V6. The stored settings are config.ResultSettings embedded in
    PreparedDeviceInfo and preparedPoolDevice: JSON "container" and
    "origins" on each device entry (contract 9 + R2).
V7. CreateContainer errors are also logged (klog Error), so a refused
    container shows in the driver log (P13).
V8. The lease device result has a marker like every result (contract 4,
    DOC O3).

Lock order and rules
--------------------
Unchanged from plan-11: f.fenceMu -> lendMu -> p.mu -> (f.mu, the node
state lock, the pool snapshot lock serialsMu). NRI handlers
(CreateContainer, StartContainer, StopContainer, RemoveContainer,
Synchronize) take p.mu, the node state lock (preparedResult) and
serialsMu (ClaimResults) only, never lendMu, poolDriver.mu or
localAllocator.mu; CreateContainer reads the results before p.mu.
Synchronize reads them under p.mu (as hasSteeredClaims did): the node
state lock and serialsMu are leaves, nothing holding them takes p.mu.
p.mu is never held across UpdateContainers; passes from Synchronize and
LendsRestored run in goroutines. poolDriver.mu -> serialsMu (updateSerials)
as before.
