3. The run
----------
online/replay: coproc MBTGEN { exec "$MBT_BIN" online FLAGS; }, stderr
>> $O/mbt-cxl.log, MBT_OUT=$O exported. FLAGS: --seed --duration
--steps --depth --profile --unsettled --settle-timeout=Ns
--local-blocks --node-hb0=2 --node-hb1=3 --out=$O [--avoid]
[--replay=FILE] and the words of MBT_ARGS (new: e.g.
"--plan-ahead=false" for P2). Checked against MODEL's main.go flag set
(no --poll: polling is bash's; Go's flag package would refuse it).
The loop runs in the test's shell (functions only, no ( ... )):
step N VERB ARGS -> mbt-run -> "done N STATUS JSON" -> ok|fail;
step N settle -> observe, "observe N JSON", wait -> sleep MBT_POLL, ok
or fail; end -> stop the coprocess -> teardown. Details that matter:
- bash unsets MBTGEN[0] when it reaps the coprocess, which loses its
  last lines (measured): MBT_RFD is a dup of its stdout taken at
  start, read with read -t $MBT_READ_TIMEOUT (900 s).
- A write to a dead coprocess kills bash with SIGPIPE without the EXIT
  trap (measured, exit 141): mbt-send ignores SIGPIPE around printf.
- fail N: mbt-fail prints the message, the head of mbt-fail.txt,
  copies the last observation to mbt-obs/fail-N.json, calls error; the
  EXIT trap stops the generator (stdin closed, 5 s, TERM, KILL).
- Files of the generator from an earlier run (mbt-fail.txt,
  mbt-steps.txt) and driver logs are removed at setup: O is reused.
offline: MBT_SCRIPT is sourced in the test's shell. mbt-step runs the
action (records it in mbt-steps.txt); mbt-expect N runs "$MBT_BIN check
--step=N --expect=FILE --observed=FILE [--since=T0
--settle-timeout=Ns]"; FILE has the on-line line ("done N STATUS
JSON" after an action, "observe N JSON" for a settle; MODEL's check
accepts both), a settle polls every MBT_POLL s while check says wait
(exit 3) and also stops itself after MBT_SETTLE_TIMEOUT.
Output: two lines per action, settle lines only when the wait message
changes; faults print their few commands. run.sh.output of run 1:
2257 lines, ~1680 of them the framework and setup. Observations:
$O/mbt-obs/obs-STEP-POLL.json, the last MBT_OBS_KEEP=30, plus
fail-N.json; times in mbt-times.tsv, mbt-obs-times.tsv; every command
and its output in mbt-exec.log (24 KB for 65 steps).

8. Deviations, ambiguities, proposed amendments
-----------------------------------------------
A1 inspect of lease pods: once per (uid, restarts) would give the
   cxl-request list of a lease pod from before any lease-get. The
   executor forgets the slot after lease-get and lease-put, so the
   next settle inspects it again. Amend 6.1: "... and lease pods after
   each lease-get or lease-put".
A2 Extra fields (MODEL decodes leniently): pods[].lastExit (exit code
   of the last terminated main container), claim.deleting; companions
   ready, deleting; drivers phase, deleting, count (pods of the node);
   containers uid (pod), attempt; memdevs enabled; dax node;
   attachments serial; lease-get result "response" (the JSON line of
   cxl-request); "errors" in the top level and in each VM object.
A3 attachments include the local memdevs that setup attached (owner
   e2e:dra-local-device, device "<node name>.memdev1"); the oracle
   should ignore owners that are not k8s:. dax lists leave out the
   size-0 seed device. cdi keys are full paths (/etc/cdi/x.yaml).
   localDevices serial is "0x..." (the file has a number).
A4 Ambiguity: the off-line observed file. Implemented as the on-line
   line (done/observe); MODEL's check takes both. Amend 5 to say so.
A5 Settle timing facts for the model: a crash or driver-kill shows in
   the pod status only ~1 s later; kubelet back-off 10/20/40 s ... 300
   s (resets after 10 min running) for crash and driver-kill alike
   (MODEL has --max-restarts 2); a restarted driver fences containers
   created while NRI was down ~2 s after its start (lends restored);
   a lease that cannot be Ready returns exit 3 after --wait 60s and the
   broker releases it (no companion left); a restarted controller
   detaches what was released while it was down ~5 s after start.
A6 --poll is not a flag of mbt-cxl (MBT_POLL is bash's); MBT_ARGS
   passes other flags (contract 8 could list it).

9. Suspected SUT problems (evidence; not fixed)
-----------------------------------------------
S1 Re-attaching an exclusive pool device whose region was destroyed
   below a newer region of the same host bridge fails for ever: every
   Prepare "cxl create-region -t ram -d decoder0.0 -m mem1: exit
   status 1: cxl region: create_region: region2: failed to set target0
   to mem1", kernel "cxl_port endpoint5: failed to attach decoder5.0 to
   region2: -16" (EBUSY), the pod stays ContainerCreating.
   Sequence on vm0 (run 2, R/steps2.txt): ldax region0 (hb0 decoder
   2.0), xdax-b region2 (b-pooled0, 512Mi, decoder 2.1 at
   0x660000000), sdax-b/sro-b region3 (b-shared0, decoder 2.2 at
   0x680000000); delete xdax-b: "memctl: destroyed region2" 08:10:22;
   the device detached (controller), attached again for a new
   xdax-b pod at 08:10:46: every create-region fails (08:10:51,
   08:11:55, 08:13:11). Meanwhile host-bridge decoder2.1 and switch
   decoder3.1 still had size 0x20000000 at 0x660000000 and no region
   (R/evidence-b/vm0-sysfs.txt, taken at 08:12:40): it looks like the
   kernel's in-order decoder reset (a lower decoder cannot be reset
   while a higher one is committed), so the freed range cannot be
   decoded again. Possibly not the driver's fault, but the driver (or
   the controller's slot choice) is where it would be handled; a
   model that frees pool devices in any order will hit it. Logs:
   R/run2-out/trace/vm0*.driver.log, nri-dra-driver-cxl.vm0.*.log,
   mbt-obs/fail-57.json, run2.log step 57.
S2 Port decoders stay programmed after the devices are gone: after
   every run (and before run 1: test19's dumps of 2026-10-23 too) the
   host-bridge decoders keep size/start with no region and no memdev
   (now vm0 decoder2.0-2.2, 1.0; vm1 2.0-2.2, 1.0-1.1; vm2 2.0-2.1,
   1.0). pool-vm-reset only looks at memdevs and regions, so the next
   test inherits them. Probably the same cause as S1; with 4 decoders
   per host bridge a VM may run out (vm0 hb0 has one left). Proposal
   (orchestrator): pool-vm-reset also restarts a VM that has port
   decoders with a size and no region; evidence: "cxl list -D" in the
   VMs, R/run1-out/cxl-sysfs.no-devices.vm0.txt vs
   R/run2-out/cxl-sysfs.no-devices.vm0.txt.
E1 (D E1 predicted, confirmed) containerd restart: "NRI connection to
   the runtime lost" (vm0 driver, 08:10:28) and no reconnect; a
   claim-less pod created afterwards on vm0 had cpuset.mems "" ->
   effective 0-2 while node 2 was fenced (run 2 step 51, mbt-obs
   obs-000052-002.json), until driver-restart: "NRI fence:
   ctr=.../mbt-plain-vm0-0-g2/main cpuset.mems=0-1 (was "", fenced
   nodes 2)" 1.8 s after the new driver started.
   Run 4 (real model): driver-restart vm1, containerd-restart vm1 2 s
   after the new driver's start ("NRI connection to the runtime lost"
   08:26:48.342), then xnuma-a@vm1#0's claim onlined node 2: "NRI fence:
   fencing CXL node 2", "NRI UpdateContainers(cpuset.mems=0-1): ttrpc:
   closed", "0 containers updated, 2 failed"; sro-c@vm1#0 kept
   effective 0-2 until the settle timeout (R/run4-out/trace/

15. driver-kill-at and driver restarts (run PM2, steps 58-63)
-------------------------------------------------------------
2026-10-28 (EXEC). The bug (mine): at a hit, the watcher re-resolved the
driver via crictl when its armed process had changed, so after
driver-restart vm2 (step 59) it SIGKILLed the NEW container 10.2 s after
arming (the extra restart that failed step 63).
Fixed (T/mbt-observe.py, T/mbt.source.sh):
- The watcher is bound to the process it was armed against (a pidfd:
  os.pidfd_open, signal.pidfd_send_signal; without pidfds, pid + start
  time). Every poll checks it: once it has ended (any driver restart),
  the watcher ends with done true, fired false, reason "driver
  restarted". A kill can only reach that process; no re-resolve.
- New state field "reason": fired | expired | driver restarted |
  disarmed by VERB | no running driver container.
- Explicit disarm (my call, for the model to predict): driver-kill,
  driver-restart and containerd-restart of the VM of an armed watcher
  disarm it first (mbt-observe.py kill-at-disarm): done true, fired
  false, reason "disarmed by <verb>" (unless it fired or ended before:
  then that state); the done line of that same step carries it, and
  killAt is not reported after it. kubelet-restart does not disarm (the
  driver keeps running; it stays armed).
- killAt reporting (A30) was not broken: the done lines of steps 59-62
  carried the armed state and observation 1 of step 63 carried done/
  fired true (mbt-exec.log 00:12:56.499 "driver-kill-at vm2 done" in
  step 63's first observation); observations 2-31 have null by A30, and
  obs-000063-001.json was rotated out of mbt-obs (MBT_OBS_KEEP 30).
  With the disarm the final state now comes in the driver-restart line.
Verified: run 7 (MBT_STUB=1 MBT_STUB_STEPS=R/steps-disarm.txt, stub
checks "killat=REASON" and "restarts=VM:N" added), PASS, 23 steps:
driver-kill-at vm2 region + driver-restart vm2 -> its done line
{"done": true, "fired": false, "reason": "disarmed by driver-restart"},
pfsd-c@vm2#0 Running, driver vm2 restarts 0; driver-kill-at vm1 +
driver-kill vm1 -> "disarmed by driver-kill", restarts 1 only; a watcher

binding tested locally too: once the armed process exited, the kill
fails (ESRCH) and a new process is untouched. Cluster left clean, lock
