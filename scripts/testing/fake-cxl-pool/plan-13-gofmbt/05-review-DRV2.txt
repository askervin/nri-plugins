the tests prove it. Some paths still publish a pool device as a local

Findings

E1  bug  bug-09: the window and the retention count time between
    scans, not observed absence
  pool_slices.go:131 sets p.pools[pool] only on a list that has the
  pool. Gate refreshes r.Seen only for memdevs present at a scan
  (pool_serials.go:245, 277). Pool serials are listed only by
  scanInput, and scans run only at start, on udev events and on the
  retries (driver.go:701, pool_slices.go:177). So
  uncertainLocked (pool_serials.go:210) and the forget loops
  (pool_serials.go:279-291) compare "now" with the time of the
  node's last scan, not with how long the pool or the serial has
  actually been absent.
  R1 TestRevQuietNodeWindowLapsed: pool-c is listed at a scan, 2 h
     pass without a scan, pool-c's slice is deleted, and a serial the
     node never listed is attached. Result:
       published [memdev-c100e2e1 memdev-c1ae2001] holding false
     bug-09 6(c) says this case is covered ("the slice was
     published, allocated, attached and deleted between two scans").
     It is covered only if the node scanned in the last hour.
  R2 TestRevQuietNodeForget: 0xc1ae2001 is in pool-c's slice at a
     scan, 25 h pass without a scan, the controller stops gracefully,
     one unrelated rescan runs (the device is detached), then the
     device is attached:
       published [memdev-c100e2e1 memdev-c1ae2001] holding false
     The forget loop deleted both the serial and the pool at the
     first scan after 25 h, without ever seeing them absent.
  The e2e cluster hides this, because udev events come every few
  seconds there. A production node can easily go hours without a
  CXL udev event. A wall-clock step forward does the same to the
  times loaded from the file (they have no monotonic reading), for
  example an RTC that runs ahead at boot and is then corrected.
  Fix (either):
  (a) List the pool slices periodically, every 5-10 min, even
      without a scan: run Serials(), which refreshes p.pools and the
      Seen of listed serials. Gate's Seen refresh needs a sysfs scan,
      or at least a "present serials" pass. This also fixes E2.
  (b) Count observed absence: give each record and pool an
      AbsentSince, set at the first successful list or scan that
      misses it and cleared when it is seen again. Forget when
      now - AbsentSince > retention. A pool is missing when it was in
      the previous successful list, or when now - AbsentSince <
      window. On the first scan after a load, set every AbsentSince
      to "now", so that downtime and clock steps never count.
  Add R1 and R2 as tests.

E2  risk  bug-09: nothing notices returning slices that list a
    published local memdev
  A memdev can be published as local while it is a pool device: the
  hold-back expired (pool_serials.go:267), R4, E1. Its pool's slices
  can come back and list it later. The driver learns this only at the
  next scan. Holding() is false by then, so retryPoolList does not
  rescan (pool_slices.go:185). Until the next udev event, the memdev
  stays in Allocatable and in the slice. A local claim allocated
  meanwhile is prepared, because Prepare checks only Allocatable
  (node_state.go:1162). This was already true at HEAD, but the
  hold-back expiry makes it a designed path now.
  Fix: E1(a), or a ResourceSlice informer for drivers other than
  cxl.nri.io that triggers rescanAndPublish when a listed serial is
  on the node and not known as a pool serial. Also add a last line of
  defense before RAM is onlined: the local allocator's Acquire, or
  the memdev Prepare, refuses a serial that poolSlices remembers as a
  pool serial (records !Local) at that moment.

E3  risk  bug-09: concurrent rescans can store a stale result
  udevRescanLoop (driver.go:690) and retryPoolList call
  rescanAndPublish with no serialization. Each one does
  scanInput -> Gate -> buildDevInfos, then stores
  d.state.Allocatable (driver.go:712) and publishes. Gate re-reads the
  records under p.mu, so an interleaved Serials cannot demote a pool
  serial (verified). But the store order is not the order of the
  Gates.
  R8 TestRevInterleavedRescans: A gates at the hold-back expiry, then
  B lists pool-c with the serial and gates:
    A [memdev-c100e2e1 memdev-c1ae2001] B [memdev-c100e2e1]
    holding false
  If A stores and publishes after B, the pool device stays published
  as local, and nothing rescans (E2). The window is narrow: A has to
  be descheduled for about one API round trip. But the hold-back
  creates exactly this coincidence, a 30 s retry at the moment the
  pool returns.
  Fix: a mutex in driver around rescanAndPublish, from scanInput
  through the publish. Prepare does not take it, and scans are short.

E4  risk  bug-09: the state file is not durable, and losing it is
    silent
  writeJSONFile (local.go:1331-1344) writes the .tmp file and renames
  it, with no fsync of the file or the directory. After a power loss
  an empty or truncated poolSerials.json is possible (xfs, or ext4
  without auto_da_alloc). loadRecords then warns and starts with no
  records (pool_serials.go:105-107). That is the "no file" residual
  of bug-09, reached without an upgrade.
  R5 TestRevTruncatedFile: the serial is listed, the slice is
     deleted, the file is truncated, the driver restarts and the
     device is attached:
       truncated file, controller down: [memdev-c100e2e1
       memdev-c1ae2001]
  Fix: fsync the tmp file before the rename, and fsync the directory
  after it (this helps every state file that writeJSONFile writes).
  A file that exists but cannot be read means the knowledge is lost,
  which is not the same as "no pools". For newMemdevHoldBack after
  start, hold back every memdev that the local allocator does not
  use, and log an Error, not a Warning.

E5  risk  bug-09: first start without the file while a controller is
    stopped (documented residual)
  R4 TestRevNoFileControllerDown: [memdev-c100e2e1 memdev-c1ae2001].
  The first deployment of this fix is such a start on every node. Two
  possible mitigations:
  - Document an upgrade precondition in local.md: all pool
    controllers running, or no pool claims in flight.
  - Use an independent signal of an attach in flight: while a
    ResourceClaim that is allocated to this node with a result of a
    driver other than cxl.nri.io is not prepared here, treat new
    memdevs as uncertain. This would also cover R1 without timing
    windows.

E6  nit  bug-09: the hold-back clock runs while no list has succeeded
  Before the first successful list, scanInput turns off local memdevs
  (pool_slices.go:170), but Gate still holds and expires: after 5 min
  it records the memdev as Local:true (pool_serials.go:267-276). When
  the first list succeeds with the pool still missing, the memdev is
  published at once instead of being held. Fix: in Gate, while
  !p.known, neither expire a hold nor record Local.

E7  nit  bug-09: any DRA driver with a "serial" attribute counts as a
    pool
  deviceSerial (broker.go:622) accepts "serial" and "<driver>/serial"
  of any driver except cxl.nri.io. Pools named by node (node-local
  drivers) disappear when a node leaves the cluster. For an hour
  after that, every node holds back each new memdev for 5 min. The
  file also collects every serial of the cluster and is rewritten on
  each new one. The API cost is a cluster-wide List of all
  ResourceSlices at each scan, which was already there, but now also
  every 30 s while holding. Suggest restricting the drivers to the
  configured pool driver names (--pool-driver-name,
  device.PoolDriverName).

E8  nit  bug-09: held memdevs are logged as pool devices
  A held serial is added to poolSerials, so it is logged as
  "pool device" (node_state.go:511, V(4)) and as "pool device
  (cxl-pool.nri.io), memory device serial ..." on its regions
  (node_state.go:379). A shared-device refusal is also logged once as
  "pool device" (logSharedRefusal caches it). This is misleading
  when debugging a bug-09-like case. Suggest passing the held set
  separately with its own reason ("held back: it may be a pool
  device").

E9  nit  bug-09: test gaps
  - The fake never goes through newDriverState: no first scan with
    the local allocator, and no !known configuration combined with
    the Gate (E6).
  - No test for an established local memdev that a pool slice lists
    later. R7 TestRevLocalBecomesPool passes; add it.
  - No test for the retry ticker (Holding), and none with regions on
    a held memdev.
  - serialsEnv.plug names memdevs "mem"+len(e.devs), so the names
    collide after unplug and plug. This is harmless now (keyed by
    serial), but it is a trap later.
  The fake itself is truthful for what it covers: the real
  scanInput and scanDetected, the fake clientset, and restarts
  through the file.

E10 nit  bug-09: docs
  local.md says a serial is forgotten after 24 h "neither in a
  ResourceSlice, nor prepared, nor on the node", and that pools
  "listed with devices in the last hour" count. Both are true only
  for a node that scans (E1); fix the text together with E1. local.md
  also does not say how to give a former pool device a new role as a
  local memdev while it stays attached (it is never forgotten). Say
  that its record has to be removed from poolSerials.json before a
  restart. loadRecords also crashes on a hand-edited file with a
  null record:
  R3 TestRevNullRecord: nil pointer dereference at
     pool_serials.go:110 (r.Serial), so the driver crash-loops. Skip
     nil entries.

E11 risk  bug-10: a pfn mode that cannot be read still settles, so
    the destructive path stays reachable
  M/pmem.go:234-241: if the mode read fails, or returns anything
  other than "ram" or "pmem", Map stays "" and the namespace is
  settled.
  TestRevPfnModeUnreadable (pfn0.1 fully probed, mode file removed):
    settled true err <nil> namespaces [{Name:namespace0.0
    Mode:fsdax Map: ... BlockDevice:/dev/pmem0 ...}] fsdax <nil>
  FsdaxNamespace then returns nil. preparePersistent
  (D/pool_persistent.go:123-133) fails a read-only or fs attach. A
  writable non-fs attach runs "ndctl create-namespace -f -e
  namespace0.0" over the writer's namespace. In the kernel,
  nd_pfn_validate sets the mode before nd_device_register, so with
  the disk complete only a teardown or an I/O error can hit this,
  which is unlikely. But the outcome is the one that bug-10 calls
  the worst. Fix: a probed pfn device whose mode is neither ram nor
  pmem is not settled (return ns, false, nil), so the deadline then
  produces an error instead of a reformat. Possibly also refuse -e
  over a namespace in mode fsdax whose Map is unknown.

E12 nit  bug-10: the C half of the fix has no deterministic test
  With only the mode read moved back first (REV/pmem_modefirst.go),
  the whole package passes -count=20. The new
  TestNamespacesWaitForProbe steps pin down only A (ENOENT). After
  E11, add a step "pfn device with driver and complete disk but no
  mode: not settled". That pins the ordering without a race.

E13 nit  bug-10: a timeout loses its cause
  At HEAD, ENOENT named the missing file. Now the caller gets only
  "<region>: namespaces still probing: context deadline exceeded"
  (pmem.go:319). Suggest keeping the last reason a namespace was
  unsettled, for example the missing path, and adding it to the
  error.

Verified correct
========================================================================

bug-09
- The L6 sequence, restarts while the slice is absent, the hot-add
  variant, and a never-listed serial while the pool is missing within
  the window are all closed. The 9 new tests pass, and 6 fail without
  the fix.
- Order: newPoolSlices loads the file in its constructor
  (pool_slices.go:81), and newDriver creates it before newDriverState
  (driver.go:381-382). So the first scanInput, newLocalHelper's
  SetShared (which excludes remembered pool serials, driver.go:602)
  and the first Gate all see the records.
- Precedence in Gate (pool_serials.go:242-269): a current or
  remembered pool serial always wins over Local, over local.uses and
  over the hold-back. A Local record flips to pool when a slice lists
  it or the pool driver prepares it, and it stays pool after the
  slice is gone (R7).
- Serials, NotePrepared, Gate and Holding all take p.mu. Gate
  re-reads the records, so an interleaved Serials cannot demote a
  pool serial. -race -count=3 is clean.
- A driver restart during the hold-back restarts the 5 min (R6),
  which is conservative. A crash loop holds for as long as it lasts,
  which is acceptable.
- Times set in the process carry monotonic readings, so in-process
  windows ignore clock steps. A backward step of the file's times is
  conservative (missing longer, never forgotten). Only a forward step
  is unsafe (E1).
- saveLocked: the file is written on any change and at most hourly
  for time-only changes. A failed write keeps saved/dirty, so the
  next call writes again.
- Held memdevs: no memdev, no region and no shared device is
  published (they are in poolSerials). Hold-back ends at 5 min, plus
  at most one 30 s tick, or as soon as the pool is listed again.
- Prepare of a memdev that is no longer in Allocatable fails
  (node_state.go:1162-1165). So a rescan that happens before Prepare
  does protect it; E2 is about rescans that do not happen.
- A genuinely local device: one present at the first start, or
  hot-added while all pools have their slices, is published at once
  and then also while the pools are absent (TestPoolSerialsLocalDevice).
  A controller that is uninstalled for good delays new local memdevs
  by at most 5 min, for at most 1 h.

bug-10
- No hang: every caller has a deadline. preparePersistent uses
  p.timeout, whose default is 30 s, and 0 maps to the default
  (pool.go:253). checkBlockDevice uses min(p.timeout, 5 s), and
  CreateFsdaxNamespace uses the caller's wctx.
  TestNamespacesWaitForProbe still checks that Namespaces gives up
  with the context.
- Only ENOENT from BlockDeviceInfo (of dev or size) means "probing".
  Parse and other errors still fail.
- Reading the mode last is correct for every mode. fsdax: the mode is
  set before the pfn device is registered, and the disk exists only
  after the probe of the registered device. devdax (holder dax*),
  raw and sector never read Map, as before. Raw is safe because a
  namespace with an info block never gets its own disk (nd_pmem
  probes btt/pfn/dax first and returns -ENXIO).
- For a probed fsdax namespace with map mem, FsdaxNamespace now always
  finds it, so the writable path never reaches create-namespace -f
  for a writer's namespace, except through E11.
- Harness: fakeSys.write renames from a second t.TempDir() on the same
  filesystem, so the write is atomic. The t.Cleanup(probes.Wait) is
  registered after the TempDir cleanups, so it runs first (LIFO).
  After the test function returns, no probe goroutine writes or
  calls t.Fatal.

E1  FIXED, both (a) and (b).
  (a) The pool watch (D/pool_slices.go poolWatch, replaces retryPoolList)
      ticks every 30 s: it rescans while the list fails or a memdev is
      held, and otherwise whenever the node has not been rescanned for
      poolSlicesPoll = 2 min (udev rescans count). A rescan is the full
      rescanAndPublish: field-selected list of the pool slices, sysfs
      scan, Gate, Update of the slice controller (no API write when
      nothing changed). Periodic rescans that change nothing log at
      V(4).
  (b) Absence is observed, not inferred from the time of the last scan:
      p.absent / p.poolAbsent hold the first observation that missed a
      serial / pool. An observation continues the previous one only if
      it is at most poolObservationGap = 5 min later (observedSince);
      after a longer gap (stopped or starved driver, failing list, clock
      step, quiet node without the watch) the absence starts again at
      "now". Serial absence = not on the node, not in the current list,
      not prepared, observed in Gate only when the list of this scan
      succeeded. Forget after poolSerialRetention (24 h) of observed
      absence; a pool is "missing" for poolMissingWindow (1 h) of
      observed absence. Absence is not persisted: after a restart it
      starts again (file times are informational only), so the clock
      steps of loaded times no longer matter.
  Why both and why not an informer: the periodic list reuses the one
  scan path that already exists (no event plumbing, no second cache),
  its latency (<= 2.5 min) is backed by the Prepare check of E2, and the
  absence of a memdev can only be observed by scanning sysfs anyway
  (udev reports arrivals, not "still absent"). (b) alone would keep a
  node that never scans conservative, but never forgetting; (a) alone
  would still let a single late observation decide. Cost: with E7 the
  list is field-selected (spec.driver=<pool driver>), one small List
  per node per 2 min.
  Tests: TestPoolSerialsQuietNodeWindow (R1), TestPoolSerialsQuietNodeForget
  (R2), TestPoolSerialsPoolDeviceRemoved (one scan after 25 h forgets
  nothing; a day of scans does), TestPoolSerialsHoldBackEnds (an hour of
  observed absence holds nothing, a restart starts it again),
  TestPoolWatch (the ticks rescan while holding; periodic rescans).
