plan-13: node reboot findings
=============================
2026-10-29 (research agent). Question: how the CXL DRA driver, the
pool controllers, the pool servers and Kubernetes behave when a worker
node of the test90 cluster reboots, so that the model can get a "node
reboot" fault. Findings only: no model, executor or driver change.

Names: N = repo root, D = N/cmd/plugins/dra-driver-cxl,
F = N/scripts/testing/fake-cxl-pool, T = test90-gofmbt-reliability,
E = N/test/e2e, K = ~/github.com/kubernetes/kubernetes (v1.37.1-22,
the cluster runs v1.37.1), Q = ~/github.com/qemu/qemu (branch
5jL-fix-cxl-hot-remove, ff076b1e6c, the qemu of the VMs), L =
~/github.com/torvalds/linux (the VMs run 7.3.0-rc4). RR =
/tmp/p13-runs/reboot-research (raw logs of this research). Image of
the driver: 2ba73741f42a (c74eff381 + bug-14, the image of FP4-FP9).

0. Summary
----------
- A guest reboot of vm1 (systemctl reboot) takes ~23 s to ssh, ~44 s
  until the driver is ready (A15) and ~90-115 s until every pod with a
  claim runs again. Restarting qemu (vmdir-restart) costs about the
  same: ~19 s to ssh, ~46 s to the driver, ~95-120 s to the pods.
- Kubernetes keeps every pod (same UID, restarts +1, new sandbox) and
  every claim (allocation and reservedFor unchanged). kubelet v1.37
  calls NodePrepareResources again for every claim after the boot.
- The driver answers "already prepared" with the result of the old
  boot. Only the local allocator knows the boot id. The containers
  start with the CDI devices of the old boot: device nodes with old
  numbers, a NODE without memory, a bind mount of a node mount that
  is gone. One stale device node reached another claim's device: the
  container of an rw claim of c-pmem1 read c-pmem0 (R1, severe).
- A guest reboot leaves every CXL memdev unusable in the guest: a
  qemu bug keeps Mem_Enable of the device DVSEC across the reset and
  Linux refuses the endpoints (R4). Only a qemu restart gives working
  devices; it drops every attachment of the host, and the pool
  controllers attach the claimed devices again; the test's local
  memdev is not attached again.
- The pool server of pool-c (HMP) races with the qemu restart: the
  controller's new attachments are dropped one second later and
  adopted without owner; the controller never detaches them (R3).
- vm2 should stay out of the model (section 5).
- The cluster was cleaned and the lock released (section 8).

1. The reboot variants
----------------------
1.1 Guest reboot: "systemctl reboot" in the guest. qemu keeps running
  and keeps its hot-plugged devices: the reset is a qemu system reset,
  no qemu option stops it (no -no-reboot in the command lines of the
  three qemu processes). ct3d_reset resets the component registers,
  so every HDM decoder is uncommitted after the reset
  (Q/hw/mem/cxl_type3.c:1327-1337). The pool servers see no change:
  the attachments stay "attached" (RR/pre1/att-*.json and
  RR/post1/att-*.json are the same). This is what a real platform
  reset looks like if the fabric keeps the devices bound to the host.
1.2 qemu restart: vm-reboot (E/lib/vm.bash:862-938, VM2) or
  vmdir-restart (E/lib/k8s.bash:144-176, VM1 and VM0): shutdown -h,
  then vagrant up --no-provision. Every hot-plugged device is gone.
  The server drops the attachments of the host ("qemu restarted (pid
  A -> B)" or "qemu process not found", F/pkg/server/server.go:682,
  766-788); the pool controller still wants them (the claims are
  allocated) and attaches them again into the new qemu
  (F/pkg/controller/reconciler.go:186-213). The local memdev of the
  test (owner e2e:dra-local-device, T/code.var.sh:280-284) has no
  controller: it stays detached. This is a power cycle in which the
  fabric unbinds the devices and binds them again.
1.3 Which one: the guest reboot is the realistic one and the cheaper
  one to write (the executor needs nothing but the reboot and the
  waits). It needs R4 fixed in qemu first: today it makes every CXL
  device of the VM useless until its qemu restarts. The qemu restart
  works today but needs R3 fixed (or it leaks pool-c devices) and an
  executor that attaches the local memdev again.

5. vm2 (control plane)
----------------------
- A reboot of vm2 stops the API server, etcd, the scheduler with the
  bug-08 fix and the three pool controllers. The controllers run as
  transient units with Restart=no (N/test/e2e/memory.test-suite/
  dra-driver-cxl/dra.source.sh:463): they do not come back after a
  boot; the model would need ctrl-start of all three after it.
- Every executor command and the observer's kubectl run on vm2
  (mbt-sh vm2, dra-vm-command "$OUTPUT_DIR"): each would need retries
  for the whole outage, and the trace collectors die.
- Drivers on vm1 and vm0 lose the API for the outage: slices, the
  pool watch and lease companions fail meanwhile; a model of that is a
  fault of its own ("API outage"), not a node reboot.
- Recommendation: leave vm2 out (MBT_REBOOT takes vm0 and vm1 only).
  A control-plane reboot can come later as its own verb.

6. Bugs
-------
R1 (driver, severe) Prepared claims survive a reboot with the
   devices of the old boot.
   Steps: claims of every kind on a node; reboot the node (either
   variant); kubelet prepares each claim again.
   Evidence: 3.3-3.5, 4.4; RR/post1/driver-vm1.log:83-112,
   RR/post1/containers.txt, RR/post2/xpb-stale-read.txt.
   Cause: the pool driver has no boot id (preparedPoolClaims.json,
   D/pool.go:1370-1396) and returns the stored result for a claim it
   has (D/pool.go:472-480); its CDI spec is built from the stored
   dax and block numbers and node mounts (D/pool.go:1314-1341);
   restoreMounts drops a mount it cannot restore but keeps the claim
   (D/pool_persistent.go:810-816). cxl.nri.io keeps the claims of
   preparedClaimsInfo.json although the allocator forgot their
   slices (D/local.go:1337-1341, D/node_state.go:977-985); only dax
   device nodes are dropped (D/node_state.go:1105-1117). The lease
   store has no boot id either (D/lease_store.go:156-178).
   Effect: containers run without their memory (numa: NODE=N with no
   memory; dax: a device node of nothing; fs: never starts), and a
   stale device node may be another device's after the boot: block
   devices (blkext 259:N) and dax devices (252:N) get their numbers
   anew. Shown: an rw container of c-pmem1 read c-pmem0.
   Fix: write the boot id into preparedPoolClaims.json,
   preparedClaimsInfo.json and leases.json (or one boot-id file per
   data directory). At start, a claim prepared in another boot is
   "stale": keep its record (Unprepare must still work and release),
   write no CDI device of it, and redo its device work at the next
   Prepare, which kubelet sends before the containers start (3.4):
   regions, onlining, dax devices, namespaces, node mounts, local
   slices, steering; then write the new result and CDI spec. Leases
   of another boot: release them (their fds died with the processes;
   a numa lease's memory is gone) and mark them Released, so that
   the requester asks again. Never reuse a device record of another
   boot for a new claim (checkSamePreparation, D/pool.go:705-723,
   compares with it).
R2 (driver, medium; part of R1) An fs claim whose node mount cannot
   be restored stays prepared with a CDI bind mount of a missing
   directory: the container fails at every start, also without a
   reboot (a region gone for any reason). Evidence: 3.5 pfsd-c.
   Cause: D/pool_persistent.go:810-816 removes the directory and goes
   on. Fix: with R1, re-prepare; without it, drop the claim's CDI
   device so that the start fails with a clear Prepare error.
R3 (fake-cxl-pool server and controller, medium) After a qemu
   restart of an HMP-controlled host the controller's new
   attachments are dropped and adopted without owner, and never
   detached.
   Steps: claims of pool-c on vm1; vmdir-restart vm1.
   Evidence: 4.1, 4.5; RR/out/fake-cxl-pool-server-pool-c.log
   08:34:18.05-08:34:19.17, RR/post2/controllers.log.
   Cause: for a configured HMP host the server takes liveness from its
   monitor; the new qemu answers on the same monitor.sock path before
   the process scan has seen the new pid, so reconcile finalizes the
   old attachments and accepts new ones into the new qemu; the next
   process scan then drops every attachment of the host
   (F/pkg/server/server.go:676-683, 766-788) and adopts the devices
   it finds (server.go:996-1013, Adopted, no owner). The controller
   ignores adopted and ownerless attachments
   (F/pkg/controller/reconciler.go:178) and so attaches (200, already
   attached) forever and never detaches.
   Fix: in the server, check the identity of the qemu behind a monitor
   (pid of the socket peer, SO_PEERCRED, or qom/uuid plus start time)
   before using its tree, and treat a new identity as "qemu
   restarted" first; or keep attachments created after the new
   process started. In the controller, take over an adopted
   attachment of a device that a claim of ours wants on that host
   (set its owner), so that it is detached later.
R4 (qemu, test environment; blocks the guest-reboot variant) After
   a guest reboot no CXL memdev can be used.
   Evidence: 3.2, RR/post1/cxl-dmesg.txt.
   Cause: Linux sets Mem_Enable in the CXL device DVSEC control
   register when it enables a device; qemu stores it (write mask
   Q/hw/cxl/cxl-component-utils.c:507-508); the PCI reset clears only
   the standard header (Q/hw/pci/pci.c:569-601) and ct3d_reset resets
   the HDM registers but not the DVSEC (Q/hw/mem/cxl_type3.c:1327-
   1337; the realize value is .ctrl = 0x2, line 373). The next kernel
   finds Mem_Enable set with HDM decoding off and DVSEC ranges outside
   every CFMWS: -ENXIO (L/drivers/cxl/core/pci.c:378-447, message at
   444). Firmware on real hardware resets this.
   Fix (qemu): restore the device DVSEC (control and range bases) to
   its realize values in ct3d_reset. Workaround: hot-remove and add
   the devices again, or restart qemu.
R5 (controller, cosmetic) The device data of an Attached claim keeps
   the qemuDeviceId of before a re-attach (4.6).
Not bugs, facts: the local memdev of the test is not re-attached
   after a qemu restart (it is the test's, not a claim's); the driver
   waits 15 s for the API after a boot (the service network comes
   up late) and publishes no local memdev until a list succeeds;
   kubelet's first Prepares after a boot fail ("driver not
   registered") and its back-off adds ~45-70 s.

7. Recommendation for the model
-------------------------------
7.1 Variant and VMs: verb "node-reboot VM" for vm0 and vm1 only.
  Guest reboot (systemctl reboot) once R4 is fixed in the qemu of the
  VMs; until then the qemu restart (vmdir-restart), which also needs
  R3 fixed and the executor to attach the local memdev again
  (dra-local-device --pool LOCAL_SERVER[VM] VM) before the settle.
  Either way R1 (and R2) must be fixed first: today the model would
  have to predict containers without memory and a CrashLoopBackOff,
  and the oracle would have to accept a stale device node that is
  another claim's.
7.2 Cost: ~2 min per reboot step and its settle (3.1, 4.1): ssh ~20
  s, driver ready ~45 s, claimed pods Running at ~90-120 s. The
  settle timeout (180 s) is enough. At about 1 reboot per 10 minutes
  a 2 h run has ~12, a fifth of the time; weight it low.
7.3 Executor (node-reboot VM): disarm a driver-kill-at watcher of VM
  (as containerd-restart, A31); note the boot id; systemctl reboot
  (the ssh returns or breaks); wait for ssh with a new boot id
  (vmdir-ssh-wait, 180 s); echo offline > auto_online_blocks (as
  pool-vm-reset; it was "offline" after both boots here); qemu
  variant: dra-local-device again; restart the trace collectors of VM
  (MBT_TRACE_REFOLLOW, dra-trace); mbt-driver-ready-wait (A15). The
  observer must accept container states Unknown/waiting while the
  pods come back (kubectl shows "0/1 Unknown" for ~60 s).
7.4 Predicted state after the step, with R1 fixed (re-prepare):
  - Every pod of VM: same UID, each container restarts +1 (allow +1
    only), Running again; pod IPs change. The driver pod: restarts
    +1. Pods on other VMs: unchanged.
  - Claims: allocation and reservedFor unchanged; no new claim.
  - Volatile pool numa (xnuma): region again, memory online on its
    node, the node fenced (A36 allowed-mems).
  - Volatile pool dax (xdax, sdax, sro, sexcl): region and dax device
    again, new names and numbers in CDI and env. Content: the host
    backing file keeps it (guest reboot: the same backend; qemu
    restart: the same file); real memory might not. Predict "token or
    zeros" for a read until the next write. Shared devices on other
    VMs keep their regions and data.
  - Local slices (lnuma, ldax, lsteer): re-acquired from the local
    memdev (the allocator of the new boot starts empty); ldax zeroed
    (read gives ""); lsteer steered again (memory.high).
  - Leases (lease): released by the reboot; the requester has none,
    its companion pod and claim go; lease-get works again.
  - Persistent block/fs (pwr, pbro, xpb, pfsd, pfsc, xpf, plse): the
    content survives (host files, labels in the LSA: 3.2, 4.3); the
    namespace and erofs are found again, node mounts and lease binds
    made again; pread gives the last pwrite. Refused kinds stay
    refused (A25).
  - plain: restarts +1.
  - Decoder stacks of VM (A9): empty at the boot, then rebuilt in
    kubelet's re-prepare order, which is not known: adopt the
    observed order for VM after a reboot.
  - Attachments: guest reboot: unchanged (same qemu device ids). qemu
    restart: every attachment of VM again with new qemu device ids
    and slots; the local memdev re-attached by the executor.
7.5 Oracle additions: the boot id of each VM (observation:
  /proc/sys/kernel/random/boot_id; the driver's state files carry it
  after R1) and a reboot count; every device node in a container's
  CDI devices matches the current device of its claim on that node
  (name and major:minor of its dax or pmem device): this check finds
  R1 in one step; numa claims: CXL_<KEY>_NODE has memory and is in
  cpuset.mems; fs claims: the node mount exists; no container in
  CrashLoopBackOff; leases of VM empty after the reboot; pread tokens.
  Today's checks (regions, CDI, env, state files) catch R1 too.
7.6 Optional from run_tests.sh: MBT_REBOOT (default empty: no
