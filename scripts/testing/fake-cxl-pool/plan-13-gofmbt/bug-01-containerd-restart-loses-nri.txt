1. Summary
----------
When containerd (or CRI-O) restarts, it closes the NRI connection of
nri-dra-driver-cxl. The driver only logged "NRI connection to the
runtime lost" and ran on without NRI for good: the NRI stub never
connects again, and the DaemonSet has no liveness probe. Until the
driver was restarted by hand:
- new containers were not fenced (a claim-less container got the
  fenced CXL node in cpuset.mems), not steered, and conflicting
  container settings were not refused (no CreateContainer hook);
- every UpdateContainers failed with "ttrpc: closed": fence passes
  (running containers keep a newly fenced node), numa lends (the
  lease is Failed) and revokes (the Unprepare of a numa companion
  claim fails on every retry, the memory stays held).

Fix: the driver exits with status 1 when the runtime closes the
connection, like the other NRI plugins of the repository, and is
restarted by the DaemonSet (or by systemd's Restart= for a host
process); the restarted driver connects again and rebuilds its state
from its state files and Synchronize, as after a SIGKILL. A close
caused by the driver itself (Stop, a done context) or by a failed
Start does not exit.

3. Root cause
-------------
Line numbers of HEAD (ed0370b24).
- D/nri.go:178-180: startNRIPlugin gives the stub
  stub.WithOnClose(p.onClose); D/driver.go:440 starts the NRI plugin
  once, at driver start, and nothing starts it again.
- D/nri.go:224-226: onClose only logged:
    func (p *nriPlugin) onClose() {
        klog.Warning("NRI connection to the runtime lost")
    }
- vendor/github.com/containerd/nri/pkg/stub/stub.go:626-633
  connClosed: on a lost connection the stub closes itself (close(),
  :491-516, resets it so that a new Start could connect) and calls
  onClose. The stub itself never reconnects; only a new Start would.
- D/lend.go:648-658 updateMems: UpdateContainers on the closed stub
  returns "ttrpc: closed" to fence passes, LendNode and RevokeNode.
- deployment/helm/dra-driver-cxl/templates/daemonset.yaml: no
  liveness probe, so nothing restarts the still running driver.
Every other NRI plugin here exits in onClose so that it is restarted:
N/pkg/resmgr/nri.go:121-124 (os.Exit(1)), memory-policy, memtierd,
memory-qos (os.Exit(0)), resctrl-mon.

The stub also calls onClose when the driver closes the connection
itself: Stop() (on SIGTERM, driver.Shutdown, D/driver.go:713) closes
the ttrpc client, whose goroutine calls onClose after Stop has
returned. Seen in every orderly stop, e.g. R/run4-out/trace/
vm1.driver.log lines 49-53: "Received signal terminated", "NRI
plugin stopped", then "NRI connection to the runtime lost". So
exiting in onClose unconditionally would turn each SIGTERM into an
exit 1 in the middle of Shutdown (before the kubelet plugins stop).

4. The fix
----------
D/nri.go:
- exitOnNRILost = os.Exit: the seam for tests.
- nriPlugin gets connMu and started, stopping, closed.
- startNRIPlugin: stub.WithOnClose(func() { p.onClose(ctx) }); after
  a successful Start, connStarted(ctx) marks started.
- Stop() marks stopping before it closes the stub.
- onClose(ctx) marks closed; exitIfLostLocked exits when started and
  closed and not stopping and ctx not done: it logs "NRI connection
  to the runtime lost, exiting to be restarted and connect again"
  (error), flushes klog and calls exitOnNRILost(1). An orderly close
  logs "NRI connection to the runtime closed (stopping)" at -v=3.
- A close before Start has returned: if Start fails, nothing (the
  driver runs on without NRI as before, "Failed to start NRI plugin
  (continuing without it)"); if Start succeeds, connStarted exits.
- The decision and the exit are taken with connMu held, so a Stop
  cannot come between them (and tests see a settled state).
Exit status 1: Kubernetes restarts the container whatever the status;
systemd's Restart=on-failure restarts only on a failure. Nothing has
to be done before the exit: not stopping the kubelet plugins, the
broker and the steering managers is what a SIGKILL does, and the
driver survives that (driver-kill in place by the plan-13 executor,
the e2e driver-restart tests).

Why exit and not reconnect in-process: a reconnect is possible in
principle (stub.close resets the stub for a new Start, and
Synchronize keeps the lent sets of containers that remain), but it is
a new path that nothing tests, while the restart path (state files,
reconcile, fence reseeding, lends restored, broker) is tested. It
would need: a Start retry loop that races with Stop; Start of a reused
stub racing with UpdateContainers callers (the stub reads its runtime
client without a lock); pending steering plans and managers of
containers whose Start/Stop/Remove fell into the gap; containers
created in the gap (never seen by CreateContainer). It would also
mask a runtime that dropped the plugin for a timeout. Its only gain:
the steering managers of running steered containers keep running,
whereas a restart stops them (a documented limitation of every
restart, doc/usage.md Steering).

Docs, N/docs/memory/cxl/usage.md:
- As a host process: the systemd-run example has -p Restart=on-failure
  -p RestartSec=5s, and two sentences: the plugin exits with status 1
  when the runtime closes its NRI connection and connects again only
  when restarted (DaemonSet; a host process needs Restart=on-failure
  or always); RestartSec gives the runtime time to bring its NRI
  socket back, as a plugin that cannot reach it at start runs on
  without NRI.
- Flags: "exits with status 1 when the runtime closes the NRI
  connection, to be restarted".
- Steering: the restart after a runtime restart also stops the
  steering of running containers.

6. To verify on the cluster
---------------------------
With an image of the fix, test90 without MBT_AVOID=containerd-restart:
a. the run 2 and run 4 sequences above (containerd-restart vmN, then
   a claim-less create, and a numa claim that onlines a node).
   Expected: "kubectl logs --previous" of the driver pod on vmN ends
   with "NRI connection to the runtime lost, exiting to be restarted
   and connect again"; the same pod, restartCount +1, lastState
   terminated exitCode 1; the new container logs "Started plugin
   30-dra-driver-cxl", "NRI Synchronize: ...", "NRI fence: lends
   restored, fencing running containers"; the claim-less container
   has cpuset.mems without the fenced node; the settle passes.
b. an orderly driver-restart (pod deleted, SIGTERM): exitCode 0, no
   "exiting to be restarted" line.
c. a numa lease and its release after a containerd restart: the
   lease becomes Ready, the companion claim is unprepared.
Notes for the executor and the model: containerd-restart now implies
an in-place driver restart (like driver-kill): wait for the driver to
be Ready again and follow its new log; containers created between the
runtime restart and the new driver's Synchronize are fenced by the
first fence pass, not at creation, and steering claims created then
run unsteered (as after driver-kill).

Remaining risks, not fixed here:
- The exit can hit a Prepare in progress, as a SIGKILL would (D E2).
- A host process restarted before the runtime's NRI socket is back
  runs on without NRI for good (the start behaviour of before;
  RestartSec mitigates). In the DaemonSet the container is restarted
  through the restarted runtime, so its NRI socket is back [I].
- Repeated runtime restarts within minutes put the driver into
  CrashLoopBackOff (10 s up to 5 min between restarts).
