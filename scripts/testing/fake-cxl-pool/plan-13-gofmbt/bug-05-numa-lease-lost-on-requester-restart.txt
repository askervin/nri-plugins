BUG-05: A NUMA LEASE IS LOST WHEN ITS REQUESTER RESTARTS

Branch 5jg-cxl, 2026-10-24. Found by the model-based test (plan 13),
run P3; a second case found by the verification replay v14. Fixed in
the working tree (uncommitted), unit tested; cluster verification
pending.

D/ = cmd/plugins/dra-driver-cxl/, doc/ = docs/memory/cxl/,
C/ = containerd v2.4.0-154-g57d315c6e (~/github.com/containerd/
containerd). Line numbers of HEAD (ed0370b24) unless "new".

========================================================================
1. SUMMARY

One root cause, two cases.

containerd applies an NRI UpdateContainers to the cgroup only of a
container that it has marked started (Status.StartedAt, set after
task start, right before PostStartContainer). For a container that it
has created but not marked started it changes only the spec, which
reaches the cgroup only if the task is created after it; the task
(and the cgroup) is created before the StartContainer event. It
reports the update as applied. The driver recorded every successful
update as applied and compared later only with its own records, so it
never noticed and never sent it again.

Case 1 (P3): a container holds a Ready numa lease (node 2 lent). Its
workload crashes, the broker keeps the lease for the restart. The new
container is created with cpuset.mems 0-1 (node 2 fenced), and the
lend at its StartContainer reaches its spec only. The lease stays
Ready, the container runs without the leased node, silently, until
the lease is released. Every 60 s the reconcile says "cpuset.mems
unchanged".

Case 2 (v14): the driver restarts (after a containerd restart, bug-01)
while a claim-less container is being started. Synchronize sees it
CREATED, the first fence pass updates it to 0-1, which reaches its
spec only: the task already had cpuset.mems "" (every node). The
fenced CXL node 2 leaks to a container that has not claimed it, for
its lifetime.

4. ROOT CAUSE

containerd (C/):
- internal/cri/server/container_start.go: NewTask :146 (runc create:
  the cgroup is made from the spec as it is now), BlockPluginSync
  :168, nri.StartContainer :181, task.Start :188, Status.StartedAt
  :195, nri.PostStartContainer :206.
- internal/nri/nri.go: StartContainer :320 and updateFromPlugin :527
  take the same lock: an update that a plugin sends while the
  StartContainer event is relayed waits for its end, and then races
  task.Start and StartedAt.
- internal/cri/nri/nri_api_linux.go UpdateContainer :468 ->
  internal/cri/server/container_update_resources.go :122: "If
  container is not running, only update spec is enough, new resource
  limit will be applied when container start" (State() is RUNNING iff
  StartedAt != 0, internal/cri/store/container/status.go :111); no
  error. (internal/nri/domain.go :127 skips, without an error, an
  update of a container that is not in the store yet.)
So an update is applied to the cgroup only after StartedAt; between
NewTask and StartedAt it is lost, reported as applied.

Driver, case 1:
- broker.go containerGone :1297 keeps the lease; the restarted
  container gets a new id, nri.go CreateContainer -> lend.go
  fenceCreated :774 computes wantMems with tc.lent of the new entry:
  empty. Adjustment 0-1.
- nri.go StartContainer :483 fireStarted -> broker containerStarted
  :1328 -> relendContainer :1334 -> LendNode -> changeLend :537 ->
  fencedLend :634 -> updateMems: the update hits the window above,
  succeeds, and changeLend records tc.mems = 0-2.
- Why the periodic check did not notice: reconcile :1387 calls
  relendContainer every 60 s; fencedLend compares want (0-2) with the
  recorded tc.mems (0-2) (:644): "unchanged". The cgroup was never
  read. Fence passes compare with tc.mems too (:874).

Driver, case 2:
- lend.go Synchronize: the container is CREATED (pid 0, no cgroup):
  the containerd NewTask of it is running (BlockPluginSync comes
  after it). The first fence pass (:842) sends 0-1: spec only, and
  records tc.mems = 0-1. StartContainer's fenceMissed (:785) compares
  wantMems with tc.mems: equal, no pass. Nothing reads the cgroup.

Every update aimed at a container before StartedAt can be lost this
way: the lend at StartContainer (case 1), the pass that fenceMissed
started at StartContainer, a pass or a revoke during the start
(case 2).

5. THE FIX

Principle: an update counts only when the container's cgroup has it;
updates prompted by a start are sent after the runtime marked the
container started; a restarted requester is created with its leased
nodes, without an update.

- D/lend.go keptLends, seedLends (new :317, :335), broker.go
  LeaseNodes (new :1342, the predicate lendsNode shared with
  relendContainer): CreateContainer (new nri.go :301) and
  Synchronize (new lend.go :427, containers new to this process)
  give a container that is not steered the lends of the Ready numa
  leases of its pod UID and container name. A fenced one gets them
  in the adjustment: the restarted requester is created with
  cpuset.mems 0-2. Steered containers are not seeded (lending stays
  refused, errSteered); fencing none: no adjustment (an NRI resource
  policy may own cpuset.mems), the lend is an update after the start.
  The companion pod has another pod UID: not seeded. The query runs
  under p.mu (lock order p.mu -> broker b.mu; b.mu is never held
  across a lender call): the broker marks a lease Releasing before it
  revokes, so the revoke always finds a seeded container.
- D/nri.go PostStartContainer (new :608, the stub subscribes to it):
  fires the OnContainerStarted callbacks (moved from StartContainer)
  and, for a fenced, not steered container when fencing is ready, a
  fence pass of that container only (fenceAtStart, fenceStarted,
  fencePass new lend.go :981-1051). Updates sent from here are
  processed after StartedAt. StartContainer only tracks pid, cgroup
  and base and starts steering. fenceMissed is gone.
- D/lend.go curMems (new :347): the cpuset.mems of the cgroup of a
  started container (the spec's as recorded for a created one).
  fencedLend and the fence passes compare wantMems with it (via
  memsDiffer, new :806, Info log "the cpuset.mems of its cgroup is
  "X", not Y as updated, updating again"); the non-fenced lend path
  checks that the cgroup has the lent nodes (cgroupLacks, new :821;
  cpuset.mems.effective when cpuset.mems is empty). So the broker's
  60 s reconcile repairs a lost lend, and the pass at
  PostStartContainer repairs a lost fence update (case 2).
- changeLend, created container: a lend of a seeded holder is done
  (V4 "lent at its creation, not started yet"); a revoke drops it,
  and a fenced one's spec loses the node by an update (checked again
  at its start); other lends still fail "not started yet".
- driver.go: startNRIPlugin gets the broker (the lease table is
  loaded before NRI starts, so Synchronize can use it).

Fencing: the seeded nodes are in tc.lent, so wantMems keeps them in
every pass. Revoke on release: unchanged for started containers.
Driver restart while a requester restarts: created by the old
process with 0-2 -> seeded at Synchronize, the first pass keeps it;
created while the driver was down (spec "") -> seeded, the first
pass sends 0-2, checked again at its PostStartContainer.

Cost: one cgroup file read per fenced container per pass, per lent
container per reconcile, and one single-container pass per fenced
container start (no update, no log when it matches).

Docs: doc/leases.md (Life cycle: requester restart, reconcile),
doc/usage.md (Containers without claims: checked at the start).
