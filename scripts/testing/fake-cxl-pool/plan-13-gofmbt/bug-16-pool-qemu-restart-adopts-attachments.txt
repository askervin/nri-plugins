1. SUMMARY

A qemu restart of a VM (vmdir-restart, vm-reboot: shutdown, then
vagrant up) gives a new qemu process on the same monitor socket paths.
The server learns the new pid only at its next discovery (every 10 s).
Meanwhile any monitor call reaches the new qemu, and the server took its
answers for those of the old process:
a) the tree of the new qemu has none of the hotplugged devices: the
   attachments were finalized ("qemu device ... is gone", object_del
   into the new qemu);
b) the controller attached the claimed devices again, into the new
   qemu, with its owner;
c) the next discovery saw the new pid: "qemu restarted (pid A -> B)"
   dropped every attachment of the host, b) included, and the reconcile
   right after it found b)'s devices in qemu and adopted them: adopted,
   no owner;
d) the controller ignores adopted and ownerless attachments: it POSTed
   attach for each device every ~5 s ("already attached (attached,
   owner "", ...)") and never detached them. After the claims were
   deleted the devices stayed in the VM: the teardown failed.
Also (R5): the device data of an Attached claim kept the qemuDeviceId of
before the re-attach; the controller writes the status only when the
Attached condition is missing.

The finding said "a configured HMP host". pool-c has no hosts in its
config: its hosts are discovered, with discovery control hmp. The
window is the same for every host whose qemu process is known: from the
moment the new qemu listens until the next discovery. QMP is affected
too: the QMP monitor reconnects to the same path at the next command
(F/pkg/qemu/qmp.go:228-253). pool-a (QMP) escaped by timing: its
discovery at 08:34:16.98 ran after its qemu had exited (SHUTDOWN
08:34:14.35, refused 08:34:14.93) and before the new one listened; it
stopped the host, and a discovered host has no monitor until the next
discovery (08:34:26.99), which found the new pid. pool-c's discoveries
were at :09.15 and :19.15; the GET /hosts of its controller at
08:34:18.05 read the new qemu in between.

Severity: medium. Every qemu restart (a node "power cycle" of the
model, 12-findings 7.1) of a VM with pool devices risks it; the window
is up to one discovery interval after the new qemu starts. The effect
is leaked pool devices: never detached, an exclusive device blocked for
every other node, a failed teardown.

4. ROOT CAUSE

- F/pkg/server/server.go:462-547 queryHosts uses the answer of a
  monitor (version, tree) without checking that the qemu process behind
  it is the one that the host has (h.pid, h.startTime). The monitor is
  bound to a socket path (setMonitorLocked :724-762, the key
  proto:path, :746), not to a process. HMP connects for every command
  (F/pkg/qemu/hmp.go:111), QMP again after its connection broke
  (qmp.go:228-253).
- The restart is noticed only by discovery: updateHostLocked
  (server.go:663-683): a new pid or start time is "qemu restarted",
  hostGoneLocked (:766-788) drops every attachment of the host, also
  those made into the new qemu.
- reconcile (:931-1030) then adopts the qemu devices that use a known
  backend and have no attachment (:993-1013: Adopted, no owner).
- Attach (F/pkg/server/ops.go:672-905) reads the tree through the same
  monitor (:729) and plugs into whatever qemu answers.
- The controller skips adopted and ownerless attachments
  (F/pkg/controller/reconciler.go:178): the claim's attach request gets
  200 (the server's existing attachment, ops.go:697-709) every sync,
  and with no attachment in "actual" there is never a detach (:219-229).
  The README says so: "never adopted ones or those made with the CLI".
- R5: writeStatus returns when the Attached condition exists
  (reconciler.go:365-367), before it compares the device data.

5. THE FIX

a) Server: after every monitor call of a refresh, and after the tree
   read of an attach, check that the known qemu process still runs
   (qemuGoneLocked, F/pkg/server/server.go new :740; called in
   queryHosts new :516 and Attach, ops.go new :741). If it does not,
   the host stops at once as if discovery had not found the process
   ("host H: stopped: qemu process PID not found"): the attachments are
   dropped, the tree is not used, an attach fails with 503 "host is not
   running", and the next discovery takes the new process, whose pid is
   then the first one of the host (no "qemu restarted", nothing dropped
   later). A config host takes its liveness from its configured monitor
   again, as before. The common part of updateHostLocked is
   processGoneLocked (new :715). Checked both when the call fails (the
   exit is seen at once, 3: 08:34:15.366) and when it answers (the new
   qemu, 08:34:18.05).
   Phase 2 of an attach (object_add, device_add; F/pkg/server/ops.go
   new :835-906) checks it too, before every command and after the
   device_add (attachStoppedLocked, new :931-943: the attachment dropped
   meanwhile, or qemuGoneLocked). A qemu that restarts after the tree of
   phase 1 was read gets nothing: the attach fails with 503 "attach D to
   H failed: host H stopped during the attach: its qemu process is gone",
   and the host stops. A new qemu listens only after the old one has
   exited, so what was added before a failed check went to the old qemu
   and is gone with it: no object_del (the monitor of the stopped host is
   closed anyway). A device_add that the old qemu took right before it
   exited fails the attach too, instead of an attachment Attached in a
   dead qemu. Not covered: an exit right after a check and a new qemu
   that listens before the next command, within microseconds (review,
   section 10).
b) F/pkg/qemu/discovery.go ProcessAlive (new :429): a zombie (state Z
   or X) is not alive. Discover never listed one (empty cmdline); now
   both agree, and a qemu that exited but is not reaped yet does not
   pass the check of a).
c) Server: an attach request with an owner for an attachment without
   owner (adopted, or attached without one) takes it over: the
   attachment gets the owner (200, nothing plugged; logged "taken over
   by owner O (it had none, adopted B)", saved, published).
   updateExistingLocked (ops.go new :915, it was updateExclusiveLocked).
   Adopted stays as it is: where the attachment came from.
d) Controller: an attachment without owner on a host of its nodes of a
   device that a claim wants there is taken over (reconciler.go new
   :190, :213-218: logged "taking over attachment D@H without owner
   (STATE, adopted B, qemu device ID)"): the attach request carries the
   claim's owner and no slot or NUMA settings (an existing attachment
   stays where it is). Then it is the controller's: detached when no
   claim wants it. The filter of its own attachments is the owner
   prefix only (adopted ones with its owner are its own). Ownerless
   attachments that no claim wants, and attachments of other owners,
   are left alone as before. A safety net now: with a) the race does not
   adopt; a lost state file still does.
e) R5: writeStatus builds the condition and the device data first and
   writes when they differ from the claim's (attachedUpToDate,
   F/pkg/controller/status.go new :91, compared as DeviceData): after a
   re-attach the claim gets the new qemuDeviceId and slot. In steady
   state no write, as before (the comparison uses the informer's copy).
f) Docs: F/README.md (discovery: a restarted qemu; the controller's
   take-over; the attach API's owner), F/pkg/api/types.go
   (Attachment.Owner).

8. PROPOSED COMMIT MESSAGE

fake-cxl-pool: do not take a restarted qemu for the old one

A restarted qemu answers on the monitor socket of the old one before
the next discovery has seen its pid. The server took its answers for
the old process. It finalized the attachments, the controller attached
the claimed devices into the new qemu, and the next discovery dropped
them ("qemu restarted") and adopted the devices without owner. The
controller skipped adopted attachments, so it never detached them.

The server now checks after every monitor call, and before every
command of an attach, that the qemu process of the host still runs. If
not, the host stops at once and the next discovery takes the new
process; an attach then fails without plugging into the new qemu. A
zombie process is not alive.

An attach request with an owner takes over an attachment without one.
The controller takes over such an attachment of a device that a claim
wants on that node, so that it detaches it later. It also updates the
device data of an Attached claim when the attachment changed.
