BUG-17: QEMU KEEPS MEM_ENABLE OF THE CXL DEVICE DVSEC ACROSS A RESET

qemu of the test VMs, Q branch 5jL-fix-cxl-hot-remove (ff076b1e6c),
2026-10-29. Found by the node reboot research (12-findings-reboot.txt
R4). Fixed in Q's working tree (uncommitted), built into the VMs'
build directory; qtest and an A/B register check pass; verified on vm1
(a guest reboot with a committed region: the memdev probes and takes a
region after the boot). Only vm1 runs the fixed qemu so far (9).

Q = ~/github.com/qemu/qemu, L = ~/github.com/torvalds/linux (the VMs
run 7.3.0-rc4), E = ~/github.com/containers/nri-plugins/test/e2e,
RR = /tmp/p13-runs/reboot-research, B = /tmp/bug17. Line numbers of
ff076b1e6c unless "new".

========================================================================
1. SUMMARY

After a guest reboot ("systemctl reboot", qemu keeps running) no CXL
memdev of the VM can be used: cxl_pci refuses every endpoint with
"Range register decodes outside platform defined CXL ranges", so there
is no endpoint port, no region, no dax or pmem device, and "cxl list
-M" is empty. The memdevs stay in sysfs without a driver. Only a
hot-remove and re-add of the device, or a qemu restart, gives a working
device again.

Cause: the guest's writes to the PCIe DVSEC for CXL Devices survive a
reset of the device. Linux sets Mem_Enable when it enables CXL.mem;
after the reset the HDM decoders are disabled again (qemu resets them)
but Mem_Enable is still set, which Linux reads as "firmware set the
device up through the DVSEC range registers" and then rejects (the
ranges, base 0, are in no CFMWS).

Severity: high for the test environment (blocks the guest-reboot
variant of the model's node-reboot fault, 12-findings 1.3 and 7.1),
none for real hardware (a platform reset clears the DVSEC). Every
cxl-type3 device is affected, cold-plugged and hot-plugged (both are
reset by a system reset); the cluster's devices are all hot-plugged.

========================================================================
2. REPRODUCTION

On a VM with a CXL memdev that cxl_pci has probed (any attached pool
device or the test's local memdev): systemctl reboot in the guest; after
the boot dmesg has, for each memdev that was enabled before:
  cxl_pci 0000:0f:00.0: Range register decodes outside platform defined CXL ranges.
  cxl_mem mem0: endpoint7 failed probe
Without a guest: B/dvsec-reset-check.py QEMU [hotplug] (qtest; programs
ECAM and the root port's bus numbers, writes Mem_Enable and range 1
base of the device DVSEC, system_reset over QMP, reads them back).

4. ROOT CAUSE

- Linux enables CXL.mem by setting Mem_Enable (bit 2) of the DVSEC CXL
  Control register (L/drivers/cxl/core/pci.c:183-221,
  cxl_set_mem_enable / devm_cxl_enable_mem). It clears it only through
  the devm action at unbind (clear_mem_enable, :206); a reboot does not
  unbind, so the bit is still set when the guest resets.
- qemu makes the register writable (Q/hw/cxl/cxl-component-utils.c:
  505-523: control 0xFD/0x4F, control2, lock, range 1/2 base high and
  low) and keeps whatever the guest wrote there.
- A reset does not touch it: pci_do_device_reset() clears only the
  standard header (command, status, interrupt line, cache line size,
  PM state, BARs; Q/hw/pci/pci.c:569-601). ct3d_reset() (Q/hw/mem/
  cxl_type3.c:1327-1354) refills the link capability, resets the
  component registers (HDM decoders uncommitted, HDM decoding disabled)
  and the device registers and CCIs, but not the DVSEC; its realize
  value (.ctrl = 0x2, IO_Enable only; bases 0) is written once, by
  build_dvsecs() at realize (:337-388).
- The next kernel: cxl_dvsec_rr_decode() (L/drivers/cxl/core/pci.c:263)
  reads mem_enabled = 1 and the DVSEC ranges (base 0, size of the
  device); cxl_hdm_decode_init() (:368) finds the HDM decoder
  capability globally disabled with mem_enabled set, so it requires a
  DVSEC range inside a CFMWS (:410-446); base 0 is in none, hence
  -ENXIO and the message at :444.
- Hot-plug is not affected: a newly realized device starts from
  build_dvsecs(). That is why hot-remove plus re-add (the workaround)
  and a qemu restart work.
- The hot-remove patch of the branch (ff076b1e6c: ct3_exit releases the
  backends, cxl-downstream advertises a power controller) does not
  touch reset or the DVSEC; no interaction. With this fix the
  remove/re-add workaround is no longer needed.

Other CXL devices (checked):
- cxl-rp (cxl_rp_reset_hold, Q/hw/pci-bridge/cxl_root_port.c:192),
  cxl-downstream (cxl_dsp_reset, Q/hw/pci-bridge/cxl_downstream.c:92)
  and cxl-upstream (cxl_usp_reset, Q/hw/pci-bridge/cxl_upstream.c:97)
  reset their component registers but not their DVSECs either. Writable
  there (Q/hw/cxl/cxl-component-utils.c:527-583): Extensions DVSEC Port
  Control and the alternate bus/memory ranges (all three), GPF Port
  DVSEC phase 1/2 control (rp, dsp), Flex Bus Port control (rp, dsp).
- Linux 7.3 writes only two of them: the GPF port timeouts of each
  dport at port probe (update_gpf_port_dvsec, L/drivers/cxl/core/
  pci.c:819; it writes the same maximum every time and skips the write
  when the register has it already), and Unmask SBR of Port Control
  around a CXL bus reset (cxl_reset_bus_function, L/drivers/pci/
  pci.c:5015), which it restores afterwards. A stale value is therefore
  either the value Linux would write anyway or never left behind: no
  effect on the probe after a reboot. Not changed by this fix (spec-
  wise the same class of bug; a follow-up can do the same for the
  ports).
- pxb-cxl (the host bridges) has no DVSEC; pxb_cxl_dev_reset resets its
  component registers (Q/hw/pci-bridge/pci_expander_bridge.c:300).
- The type3's other writable DVSEC, the GPF Device DVSEC (phase 2
  duration and power), is not written by Linux; not changed.

========================================================================
5. THE FIX

Q/hw/mem/cxl_type3.c only (git diff --stat: 37 insertions, 5
deletions):
- ct3_device_dvsec_init() (new :341): the body of build_dvsecs() that
  computes the device DVSEC (range sizes from the volatile/persistent
  backends, .cap 0x1e, .ctrl 0x2, .status2 0x2, bases 0) fills a
  CXLDVSECDevice; build_dvsecs() (new :408) creates the DVSEC from it as
  before.
- ct3d_reset_device_dvsec() (new :395): builds the same body again and
  copies it past the DVSEC header (the header keeps the link to the
  next extended capability) into config space at
  cxl_cstate.dvsecs[PCIE_CXL_DEVICE_DVSEC] (the range that
  cxl_component_create_dvsec() records). Nothing in qemu changes the
  device DVSEC at run time, so the rebuilt body is exactly the realize
  value: Mem_Enable, Cache_Enable etc., control2, the lock and the range
  bases go back to 0, the read-only fields stay as they are.
- ct3d_reset() calls it (new :1366), next to the reset of the
  component registers. ct3 has no FLR, so this runs only on the resets
  that also reset the HDM decoders (system reset, a secondary bus reset
  of a port above it, and the reset at hot-plug, where it is a no-op).
- scripts/checkpatch.pl: no errors, no warnings.

8. PROPOSED COMMIT MESSAGE (Q; Signed-off-by is the author's to add)

hw/cxl: Reset the CXL device DVSEC of a Type 3 device

The guest writes to the PCIe DVSEC for CXL Devices: Linux sets
Mem_Enable in its control register when it enables CXL.mem, and the
range base registers and the lock are writable too. ct3d_reset() resets
the component registers, so the HDM decoders come back uncommitted and
disabled, but nothing resets the DVSEC: the generic PCI reset only
clears the standard header, and the DVSEC is built once, at realize.

After a guest reboot the next kernel finds Mem_Enable set while HDM
decoding is disabled. It takes the device for one that firmware set up
through the DVSEC range registers, finds those ranges outside every CXL
fixed memory window and refuses the device:

  cxl_pci 0000:0f:00.0: Range register decodes outside platform defined CXL ranges.
  cxl_mem mem0: endpoint7 failed probe

so every CXL memory device of the guest stays unusable until it is
unplugged and plugged again or QEMU is restarted. A reset of a real
device clears these registers.

Build the device DVSEC in one function, used at realize and on reset,
so that a reset gives the DVSEC its initial values again.

The DVSECs of the root and switch ports have writable registers that
are not reset either, but Linux writes there only the GPF timeouts
(the same values on every probe) and Unmask SBR (restored after a bus
reset), so they are left as they are.

Fixes: e1706ea83da0 ("hw/cxl/device: Add a memory device (8.2.8.5)")
