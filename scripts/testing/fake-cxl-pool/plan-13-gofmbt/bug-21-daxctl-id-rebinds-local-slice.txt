1. SUMMARY

The dax bus of Linux has per-driver id lists. Writing a name to
/sys/bus/dax/drivers/DRIVER/new_id adds it to the list and makes the
kernel attach DRIVER to every unbound dax device that it matches
(driver_attach), by an id in its list or, kmem, by the device's type.
daxctl reconfigure-device binds with new_id and bind, and leaves the
id; it removes an id only when it unbinds (remove_id, then unbind).
memctl bound with daxctl (SetDaxDriver) and unbound with a bare unbind
(UnbindDax). So every dax device that memctl ever bound to device_dax
with daxctl stayed in device_dax's id list for the rest of the boot,
and whenever it was unbound, any new_id of device_dax, for any device
by anyone, bound it again.

memctl resizes a dax device by unbinding it and writing its size
(ResizeDaxDevice). The local allocator does that to cut the slice of a
claim out of the first dax device of the local region, which it has
just bound to device_dax with daxctl for the address line probe. When
the pool driver binds its own dax device with daxctl at that moment
(xdax: a dax-mode pool claim), device_dax takes the local device back
between the unbind and the size write, and the write fails with EBUSY
(L/drivers/dax/bus.c dev_dax_resize: "if (dev->driver) return
-EBUSY"). The local Prepare rolls back: it deletes the slice and,
since no claim uses the local memdev, destroys its region. When the
local and the pool device are under one host bridge, the concurrent
pool Prepare has put its region on the decoders above: the destroy
leaves a hole (bug-02), and the kernel creates no region through that
host bridge (the local memdev, every pool device under it) until the
pool region is gone. kubelet's retries of the local claims fail with
"failed to set target0 to memN" for as long as the pool claim lives.

Local and pool Prepares rarely overlap while a node runs: kubelet
prepares a pod's claims when the pod arrives. After a node reboot
kubelet prepares every pod of the node again as soon as the two kubelet
plugins register (bug-15), so a local and a pool Prepare start within
milliseconds of each other: FR2 hit it at the first reboot of vm0 that
had both a local and an xdax claim.

A second effect of the same ids: a new region's first dax device whose
name is still in device_dax's list (a destroyed region's daxN.0)
binds to device_dax at creation instead of its default kmem (seen on
vm0 after FR2, section 3). A numa region is then switched to kmem with
daxctl, whose kmem new_id makes kmem probe every unbound dax device of
the CXL regions (memctl's own comment, M/memctl.go:850-851).

Severity: medium-high. A spurious Prepare failure, and, when the local
memdev shares the host bridge with a pool device (vm0 and vm1 of the
cluster: the local memdev and pools a/b on hb0), a decoder hole that
blocks the host bridge for the life of the pool claim. Needs a local
slice resize (any local numa or dax claim's Prepare: the first slice
of a new region always resizes dax0.0) concurrent with a daxctl bind
to device_dax (a dax-mode pool claim's Prepare, a local dax slice or a
shared local device of another claim); most likely after a node reboot.
The model cannot predict it and should not: the driver can avoid it.

2. REPRODUCTION

Deterministic, at the kernel (B/experiment-A.log, vm0, a local memdev
hot-added through qmp-e2e.sock):
  cxl create-region -t ram -d decoder0.0 -m mem0
  daxctl reconfigure-device --mode=devdax --force dax0.0   memctl's bind
  echo dax0.0 > /sys/bus/dax/drivers/device_dax/unbind     memctl's unbind
  echo 134217728 > .../dax0.0/size                         ok
  dax_region/create, dax0.1 size 64Mi (unbound)
  daxctl reconfigure-device --mode=devdax dax0.1           "another Prepare"
    -> dax0.0 driver=device_dax: bound again by dax0.1's new_id
  echo 67108864 > .../dax0.0/size  -> "Device or resource busy"
Unit test (section 6): TestDaxIDsNotLeft runs FR2's interleaving
(another Manager binds dax0.1 with daxctl between UnbindDax(dax0.0)
and the size write) and fails without the fix with FR2's error:
"dax0.0: set size 67108864: device or resource busy".
In the cluster: a pod with a local claim (lnuma or ldax) and one with a
dax pool claim on the same host bridge of one node, a node reboot
(B/steps.txt, section 7). The collision needs the pool's daxctl bind
inside the local resize, a window of milliseconds; not every reboot
hits it.

4. ROOT CAUSE

- M/memctl.go:819-838 SetDaxDriver: daxctl reconfigure-device, which
  leaves the id of the device in the driver (X/daxctl/lib/libdaxctl.c
  :886-891 new_id, no remove_id after); SetDaxDriverSysfs removed it
  (M/memctl.go:866) but only after a successful bind.
- M/memctl.go:384-402 UnbindDax: a bare unbind, the id stays (daxctl
  itself writes remove_id before unbind).
- L/drivers/dax/bus.c:91-132: new_id adds the id and runs
  driver_attach, which binds the driver to every unbound device it
  matches (dax_bus_match :249-256: an id, else the type: kmem for the
  devices of volatile CXL regions, IORESOURCE_DAX_KMEM); bus.c:1044 a
  bound device cannot be resized (EBUSY).
- M/memctl.go:430-446 ResizeDaxDevice relies on the device staying
  unbound between UnbindDax and the size write; the local allocator
  (D/local.go:720, :722 CreateDaxDevice, D/local.go:428/531/943 binds
  with SetDaxDriver) and the pool driver (D/pool.go:1401) run
  concurrently.
- The rollback of the failed Acquire (D/local.go:373, :1154) releases
  the local region wherever it is in the decoder stack (bug-02's hole).

========================================================================
5. THE FIX

In memctl, no dax driver keeps an id of a device that memctl bound or
unbound:
a) M/memctl.go UnbindDax (new :391-410): remove_id of the device in its
   current driver before the unbind, as daxctl does (removeDaxID, new
   :412-419; a failure is logged, the kernel ignores a name that is not
   an id). Also clears ids that someone else left (daxctl by hand, an
   older driver binary in the same boot).
b) M/memctl.go SetDaxDriver (new :832-859): remove_id after daxctl
   reconfigure-device, also when daxctl failed (it may have written
   new_id before failing), for device_dax and kmem.
c) M/memctl.go SetDaxDriverSysfs (new :861-892): the id removed also
   after a failed bind (defer).
Then a device that memctl has unbound matches only its default driver
by type (kmem for volatile CXL regions), and a new region's first dax
device binds to its default driver.
Not changed: the rollback of a failed local Acquire still releases the
local region (D/local.go:373). With spurious failures gone a local
Prepare fails only on real errors (no room, a probe that finds
aliasing, a kmem bind or online failure, a cancelled context), and such
a failure concurrent with a pool Prepare on the same host bridge can
still pop the local region below the pool's (section 8).

Left:

  release at start does) would need the next Acquire and Reconcile to

  :572-578), and Release to stay as it is (the model predicts the
  holes of out-of-order releases, A9). Not done: no failure of that

  for the kept region.

  ModeNUMA) still writes kmem's new_id, which probes every unbound dax
