0. Vocabulary
-------------
- persistent device: a pool device with persistent: true, or (new) a
  local memdev of persistent memory (section 7). Modes block and fs.
- writer: a prepared claim (static or companion) of a persistent device
  with mode fs and read-write, or mode block and read-write.
- the node mount of (device, access): <driver data dir>/mounts/<serial hex
  without 0x>-<access>; driver data dir /var/lib/kubelet/plugins/
  cxl-pool.nri.io (pool) or /var/lib/kubelet/plugins/cxl.nri.io (local).
- class of a filesystem type (section 2): read-only, single-host, cluster.

1. MemoryConfig device section (CFG, stream API)
-----------------------------------------------
Device gains:
  fsType    string   mode fs only; "" = detect (section 3)
and readOnly becomes tri-state (Go *bool, json "readOnly,omitempty"):
  - mode fs: absent = read-only; readOnly: false = read-write (the opt-in);
    readOnly: true = read-only.
  - every other mode: absent = false, as today.
  A merge that sets readOnly to null removes it (back to the default of
  the mode). Callers read it through one accessor of CFG (name of the API
  stream's choice, listed in its status), never by dereferencing.
access: "" is "direct when the filesystem has DAX (erofs, ext4, xfs),
cached otherwise", decided at Prepare after the filesystem is known; an
explicit access stays as given (P7 when direct is impossible).
Texts of the section alone (CFG, "MemoryConfig: " prefix as today; in
this order among today's texts: after "device.path needs mode fs"):
  C1  MemoryConfig: device.fsType needs mode fs
  C2  MemoryConfig: device.fsType: invalid filesystem type "X" (lower-case letters, digits, "_" and "-")
      (valid: ^[a-z0-9][a-z0-9_-]{0,31}$)
Removed: "MemoryConfig: device.readOnly: mode fs is read-only: set
readOnly: true (write the device with mode block)".
Kept unchanged: every other text of usage.md "Configuration errors".

Facts of a persistent device (CFG type, replacing PoolFacts; fields):
  Persistent  the device is persistent memory
  Shared      other hosts may use the device at the same time (a shared
              pool device; a local memdev listed in sharedDevices)
  Exclusive   no other claim has the device while this one is allocated
              (the result consumed all shares; a pool device that is not
              shared has one claim at most)
  SingleHost  no other host has the device while this claim is allocated
              (status data singleHost or exclusive of a pool device; a pool
              device that is not shared; a local memdev that is not in
              sharedDevices)
  Coherent    other hosts' writes are visible without cache maintenance
              (status data coherent of a pool device; memdevSettings
              coherent of a local memdev)
  Local       the device is a local memdev (for the texts)
Rules of the device section with the facts (CFG; checked before the
device is touched, in this order after today's mode texts):
  F1  mode block, read-write, not Exclusive:
      pool:  MemoryConfig: device.mode block: a shared device is writable only exclusively (no shares request)   (unchanged text)
      local: MemoryConfig: device.mode block: a persistent local device is writable only exclusively (no shares request)
  F2  mode block, read-write, Exclusive, not SingleHost (a local memdev of
      sharedDevices):
      MemoryConfig: device.mode block: other hosts may use the device: it is not written in mode block
  F3  mode fs, read-write, not SingleHost, unless fsType is a cluster type
      (section 2) and Coherent:
      MemoryConfig: device.readOnly: false: other hosts may use the device: read-write needs it on this node only (claim status singleHost), or a cluster filesystem (device.fsType gfs2) on coherent memory
      (fsType gfs2 on a coherent device passes; the probe decides, P8)
Unchanged: block and fs need a persistent device, a persistent device
needs mode block or fs, the other texts.
Controller helper (CFG): ExclusiveHost(resolved MemoryConfig, coherent
bool) bool: mode fs, read-write, and not (fsType is a cluster type and
coherent). Pool controllers call it per result (section 5).

2. Filesystem types (CFG table, stream API; read by D and P)
------------------------------------------------------------
  type      class        DAX   read-only mount data   read-write data
  erofs     read-only    yes   dax=always|dax=never   (never)
  squashfs  read-only    no    -                      (never)
  ext4      single-host  yes   dax=always|dax=never   dax=always|dax=never
  xfs       single-host  yes   dax=...,nouuid         dax=...
  btrfs     single-host  no    -                      -
  gfs2      cluster *    no    spectator              -
  any other single-host  no    -                      -
  * gfs2 is a cluster type; a gfs2 filesystem with lock protocol
    lock_nolock in its superblock is single-host (section 3).
  dax=always for access direct, dax=never for access cached, only for the
  DAX types. The plugin never passes lockproto, locktable, noload,
  norecovery or user options.
Exported by CFG: KnownFsTypes (in this order: erofs, squashfs, ext4, xfs,
btrfs, gfs2), and per type: read-only, DAX, cluster (names of the API
stream's choice).

3. Detecting the filesystem (D, stream DRV-POOL, used by both drivers)
--------------------------------------------------------------------
The plugin reads the first 128 KiB of the block device (O_RDONLY) and
matches:
  erofs     le32 0xE0F5E1E2 at 1024
  ext4      le16 0xEF53 at 1080
  xfs       "XFSB" at 0
  btrfs     "_BHRfS_M" at 65600
  squashfs  "hsqs" at 0
  gfs2      be32 0x01161970 at 65536 and be32 1 (meta type superblock) at
            65540; lock protocol: the NUL-terminated string at 65536+96
ext4 needs recovery: le32 s_feature_incompat at 1024+0x60 has bit 0x4.
Result, with D = the declared fsType:
  one match T, D "" or T            -> T
  one match T, D another known type -> P3
  one match T, D an unknown type    -> P3
  several matches, D among them     -> D
  several matches, D "" or not among them -> P2
  no match, D ""                    -> P1
  no match, D an unknown type       -> D (mounted as declared)
  no match, D a known type          -> P3b
When the node mount of the device and access exists already, its
filesystem type (mountinfo) is the detected type.
Then, before anything is mounted:
  P4 the type is not in the node's fsTypes (section 8)
  P5 /proc/filesystems lists the type as "nodev"
  P6 read-write and the type is read-only class
  P7 explicit access direct and the type has no DAX
  P8 read-write, not SingleHost, and the instance is not cluster (a type
     that is not gfs2, gfs2 with lock_nolock) or the device is not
     Coherent
  P9 the access and read-write rules of one node (section 4)
  P10 read-only (no writer of the device on the node) and ext4 needs
     recovery; also an EROFS of a read-only mount of any type
Texts, each prefixed "device 0x<serial>: ":
  P1  <dev> has no filesystem of a type that the plugin knows (erofs, squashfs, ext4, xfs, btrfs or gfs2): set device.fsType
  P2  <dev> has signatures of several filesystems (<t1>, <t2>): set device.fsType
  P3  <dev> has a filesystem of type <found>, not <declared>
  P3b <dev> has no filesystem of type <declared> (no signature of a type that the plugin knows)
  P4  filesystem type <t> is not allowed on this node (fsTypes: <t1>, <t2>, ...)
  P5  filesystem type <t> does not mount a block device
  P6  <t> is a read-only filesystem: set readOnly: true
  P7  <t> has no DAX: use access cached
  P8  read-write on several hosts needs a cluster filesystem on coherent memory: <reason>
      reasons: "<t> is a single-host filesystem", "gfs2 with lock_nolock is a single-host filesystem", "the device is not coherent between hosts"
  P9  see section 4
  P10 <t> on <dev> needs recovery (it was not unmounted cleanly): a read-only mount cannot recover it, a read-write claim on one node does
  P11 <dev> has no <t> filesystem: <mount error>[: <messages of the filesystem context>]   (was "... has no erofs filesystem: ...")
  P12 <t> on <dev> was mounted without DAX   (was "erofs on ... was mounted without DAX"; also for ext4 and xfs)
The texts of today's erofs path that name erofs become these with <t>
erofs (test16 and docs follow).

4. One node: superblock, block device, binds (D, stream DRV-POOL;
   the same code for both drivers)
------------------------------------------------------------------
Rules per (device, node), over the prepared claims of the device on the
node (static and companion claims of the driver that owns the device):
- writer present: the superblock of the node mount is read-write and is
  the only mount of the device on the node: one access only.
  P9a (a claim with the other access while a writer exists):
      device 0x<serial>: it is mounted read-write with access <a> on this node: access <b> would mount it a second time
  P9b (a writer while both accesses are mounted):
      device 0x<serial>: it is mounted with access direct and cached on this node: a read-write claim needs one access only
  P9c (mode block read-write next to an fs claim of the node, or an fs
      claim next to it): refused by F1 already (block writers are
      exclusive).
- no writer: superblock read-only; both accesses may coexist (xfs with
  nouuid, section 2).
- /dev/pmemK is read-only (ioctl BLKROSET 1) whenever the device has no
  writer on the node, before any read-only mount is made; read-write
  (BLKROSET 0) before a writer's mount, upgrade or block device. A cached
  mount's loop device follows the same rule with BLKROSET. Read-only
  types (erofs, squashfs) keep today's read-only loop device; writable
  types use a loop device whose backing file is opened O_RDWR, with
  LO_FLAGS_DIRECT_IO|LO_FLAGS_AUTOCLEAR, made read-only by BLKROSET.
- Mounts of writable types use the new mount API: fsopen(type), source,
  the superblock flag ro unless there is a writer, the data of section 2,
  FSCONFIG_CMD_CREATE, fsmount with MOUNT_ATTR_NOSUID|MOUNT_ATTR_NODEV (no
  MOUNT_ATTR_RDONLY), move_mount to the node mount path. Read-only types
  have MOUNT_ATTR_RDONLY too (today's flags ro,nosuid,nodev). A mount
  error carries the messages that the filesystem context logged (read of
  the fsopen fd) after the errno.
- After every mount: DAX types with access direct must show dax=always in
  the super options, else unmount and P12 (today's T14 check).
- Upgrade (a writer is prepared while read-only claims of the same access
  have the superblock): BLKROSET 0 on the block device (and loop), then
  fspick(node mount) + FSCONFIG_SET_FLAG "rw" + FSCONFIG_CMD_RECONFIGURE.
  Error: device 0x<serial>: remounting <mnt> read-write: <error>
  (the Prepare fails, BLKROSET 1 again).
- Downgrade (Unprepare of the last writer while read-only claims stay):
  syncfs, fspick + "ro" + reconfigure, then BLKROSET 1. EBUSY (a file open
  for writing) or any error fails the Unprepare, kubelet retries:
  device 0x<serial>: remounting <mnt> read-only: <error>
- Last claim of the access: unmount as today (no detach; EBUSY fails the
  Unprepare); last claim of the device: holder wait and release as today
  (pool: memctl.Release with the memdev disabled; local: section 7).
- CDI mount of a claim: Options [bind, ro, nosuid, nodev] read-only,
  [bind, nosuid, nodev] read-write; HostPath the node mount; no device
  node.
- Lease binds (section 6): read-only: open_tree(node mount,
  OPEN_TREE_CLONE) + mount_setattr(MOUNT_ATTR_RDONLY|NOSUID|NODEV) +
  move_mount(target); read-write: a plain MS_BIND of the node mount.
  After the bind its mountinfo must show the type, the source of the node
  mount and the flags ro,nosuid,nodev (read-only) or rw,nosuid,nodev
  (read-write); else unmount and today's E4 text with "read-only" or
  "read-write" in it:
  device 0x<serial>: the bind of <node mount> at <target> is not a read-only nosuid nodev <t> mount
  device 0x<serial>: the bind of <node mount> at <target> is not a read-write nosuid nodev <t> mount
- Environment of a claim or lease of mode fs: MODE=fs, PATH, ACCESS (the
  effective one), READONLY=0|1, FSTYPE=<type>, SERIAL, SHARED, SIZE.
  Mode block unchanged (no FSTYPE).
- State: the prepared device records FsType and ReadOnly (effective) next
  to today's fields; the pool state file keeps its field names. The
  superblock state and the block device's read-only flag are derived
  from the prepared claims, never stored.
- Restart: today's restore, plus: a missing node mount is mounted with the
  derived superblock state; an existing one whose superblock state differs
  from the derived one is upgraded or downgraded (a failure is logged,
  the next Prepare or Unprepare of the device tries again); the block
  devices get the derived read-only flag.
- Logs (V(0) Infof, tests grep them): "<driver>: device 0x<serial>:
  mounted <source> at <mnt> (<t>, <ro|rw>, <data>)", "... remounted
  <mnt> read-write", "... remounted <mnt> read-only", "... <dev>
  read-only" / "... <dev> read-write" (BLKROSET).
One implementation for both drivers: the code of this section and of
section 3 lives in files shared by the pool and the local driver (no
copy); D/pool_persistent.go keeps what is the pool driver's own.

7. Local persistent memdevs (D local driver, stream DRV-LOCAL)
-------------------------------------------------------------
Publication: a memdev with persistent capacity (PmemSize > 0) and no RAM
capacity (RamSize == 0), enabled, not a pool device, not in
ignoreDevices, without regions that the plugin did not create, is
published as
  - name: memdev-<serial hex>
    attributes: type memdev, source local, serial, shared (true iff in
      sharedDevices), persistent: true, size (PmemSize bytes),
      nodeAffinity (when known)
    capacity: shares {value: 1M} (no requestPolicy)
    allowMultipleAllocations: true
  (no memoryBlockSize, no nodeAllocatableResources). A memdev with RAM and
  persistent capacity is published as today (its RAM) and its persistent
  capacity is not used (V(3) log "persistent capacity of a memdev with RAM
  capacity is not used"). Every other local memdev gains the attribute
  persistent: false.
Classes (H/templates/deviceclasses.yaml, values, schema, chart README):
  cxl-local and cxl-local-shared add
    && device.attributes["cxl.nri.io"].persistent == false
  new cxl-local-persistent:
    device.driver == "cxl.nri.io" && device.attributes["cxl.nri.io"].type == "memdev" && device.attributes["cxl.nri.io"].persistent == true
  DEV gains ClassLocalPersistent = "cxl-local-persistent".
Facts (section 1): Local true, Persistent true, Shared = in sharedDevices,
Exclusive = consumed all shares, SingleHost = not in sharedDevices,
Coherent = memdevSettings coherent.
Prepare (modes block and fs only; the texts of sections 1 and 3 with the
local prefixes of today, "claim NS/NAME: request R: "):
  a pmem region on the memdev under a root decoder with pmem capacity
  (memctl.CreatePmemRegionNoted), recorded in localDevices.json like the
  allocator's other regions (created at the first claim of the device on
  the node, the decoder order rules and hollow-region handling of local
  regions apply); the fsdax namespace (map mem) of its nvdimm region,
  created only by a writable block claim (today's pool rule); then
  sections 3 and 4 with node mounts under /var/lib/kubelet/plugins/
  cxl.nri.io/mounts. The CDI device claim-<uid>-<n> (kind nri.io/cxl) has
  the block device node (permissions r when read-only) or the bind mount,
  the env of section 4 and the marker.
Unprepare: section 4; the last claim of the device releases its region
(holder wait as for pool devices; the memdev stays enabled: a local
memdev is never disabled).
A shared local memdev that is persistent is never zeroed (its data is the
point); the volatile shared-device rules do not apply to it.
Restart and reboot: as for local regions (localDevices.json) plus section
4's restore.
Leases: cxl-request request --source local --serial S --mode fs|block
... (companion class cxl-local-persistent), lease binds as section 4.

11. e2e (stream E2E desk, stream RUN runs)
------------------------------------------
New S2/test20-dra-fs-read-write (pool, ext4 and others). Device fs0:
persistent, shared, 512Mi, serial from the pool's scheme. Images built in
VM1 (mkfs.ext4 -F -b 4096 -d DIR IMG, mkfs.xfs, mkfs.btrfs, mksquashfs,
mkfs.erofs as test16; tools installed by dnf if missing), written into fs0
by a block writer claim (exclusive) with dd, as test16 does. Phases:
  A preconditions; slice: fs0 persistent true, coherent true; class
    cxl-pool-persistent.
  B ext4 image written; writer gone, device free.
  C ReadWriteOnce on VM2: rw-a and rw-b (fs, readOnly: false, shares 1,
    no fsType, access default) and ro-c (fs, readOnly absent) on VM2: rw-a
    writes a file, rw-b reads it and writes another, ro-c reads both and
    its write fails "Read-only file system"; env FSTYPE=ext4,
    READONLY=0/0/1, ACCESS=direct; on VM2 one node mount of fs0, type
    ext4, superblock rw, dax=always; /sys/block/pmemN/ro is 0; the claim
    status data of rw-a and rw-b has singleHost true; the pool server's
    attachment of fs0 on VM2 is exclusive; the controller log has the
    "exclusive for a read-write" line; CDI mounts: rw-a/rw-b
    [bind, nosuid, nodev], ro-c [bind, ro, nosuid, nodev].
  D other hosts while the writers run: ro-d (VM1, read-only) and rw-e
    (VM1, read-write) stay Pending; their claims get AttachFailed reason
    Conflict (message names the exclusive attachment); fs0 has no
    attachment to VM1; nothing mounted on VM1.
  E downgrade: delete rw-a and rw-b; VM2's node mount is read-only
    (superblock ro), /sys/block/pmemN/ro is 1, the driver log has
    "remounted ... read-only"; the ext4 on VM2's /dev/pmemN is clean
    (dumpe2fs -h: no needs_recovery); ro-d starts on VM1 and reads both
    files (written on VM2); VM1's /dev/pmemM is read-only; rw-e stays
    Pending (VM1 and VM2 now have fs0): delete rw-e.
  F upgrade refused, then done: rw-f (VM2, read-write) stays Pending
    (Conflict: VM1 has fs0); delete ro-d; rw-f starts on VM2; VM2's
    superblock is rw again ("remounted ... read-write"), ro-c is still
    read-only and reads rw-f's new file.
  G one node, two accesses: a claim of fs0 on VM2 with access cached while
    rw-f runs: its pod's events have P9a; delete it.
  H refusals (each a pod whose events have the text; no mount, nothing
    left): fsType xfs on the ext4 (P3); after a dirty ext4 image (the
    image with debugfs "feature needs_recovery") is written by a block
    writer: a read-only claim (P10); an erofs image: a read-write claim
    (P6); a btrfs image: access direct (P7), then btrfs read-write with
    access cached on VM2 works (write, read back, FSTYPE=btrfs); fsType
    f2fs declared on the btrfs (P3).
  I xfs: an xfs image; ro-x1 direct and ro-x2 cached on VM2 and ro-x3 on

A17 (review B1, S1; DRV-POOL) Node-wide superblocks: before a fresh mount
   of a writable type, an upgrade (Prepare and restore) and a block
   writer's BLKROSET 0, the plugin reads the superblocks of /dev/pmemK and

   the Prepare:
   device 0x<serial>: <dev> has a superblock that no claim of this node explains (<source> mounted <ro|rw> in <where>): it is not used until that mount is gone

   the node (a read-only leftover does not stop it: read-only is safer).

   upgrade, no block writer, no BLKROSET 1 (fail closed).

A20 (user, 2026-11-03: "we must not trust writers or whatever runs in
   containers") fsTypes defaults to [erofs] (section 8 said the six known
   types). erofs is designed for untrusted images; the other types are not
   hardened against crafted images, and anyone who had a read-write block
   claim or lease of a device can plant one. Listing another type trusts
   every party that can write the node's devices raw. The shared code's own
   fallback is [erofs] as well; "fsTypes: none" in P4 for an empty list.
A21 (user, 2026-11-03; security review H-1) The lease CDI device mounts
   the lease socket directory <data dir>/leases/<claim uid> at /run/cxl
   with options rbind,ro (was rbind,rw): containers cannot write the host
   directory. The driver sets the socket's mode without following a path
   that a container could replace (containers of before the change keep
   their read-write bind until they restart) and removes the directory's
   entries by name, without the broker lock.
