Result
------
Mode fs of the CXL DRA driver mounts any block filesystem:
- The plugin detects erofs, squashfs, ext4, xfs, btrfs and gfs2 from the
  superblock. device.fsType (optional) must match, or names a type the
  plugin does not know. The node's driver configuration key fsTypes
  decides which types are mounted (default: the six known types).
- Read-write mounts are opt-in: readOnly: false. For mode fs an absent
  readOnly means read-only.
- On one node there is one superblock per device. It is read-write while
  a claim of the node writes, and containers get read-write or read-only
  binds of it. ext4 and xfs are upgraded and downgraded in place; other
  writable types make a writer wait until the node's readers are gone.
  /dev/pmemK is read-only (BLKROSET) whenever the node has no writer, so
  read-only mounts never write (xfs would), a dirty filesystem is
  refused, and nobody can remount it read-write. Every mount namespace is
  checked: a superblock of the device that no claim explains keeps
  writers and read-only flag changes back.
- Across nodes, ReadWriteOnce is enforced by the pool controller with
  exclusive per-host attachments (also across clusters). Claims of other
  nodes wait with AttachFailed reason Conflict. The node mounts read-write
  only when the claim status says singleHost (or exclusive), so a
  controller without this rule fails writes instead of corrupting.
- Cluster filesystems (gfs2 lock_dlm) may be read-write on several nodes,
  but only on a device the pool marks coherent (attribute coherent,
  status data coherent). This path is unit-tested only (user decision Q2).
- Persistent local memdevs: published by cxl.nri.io with persistent: true
  and shares 1M (class cxl-local-persistent), modes block and fs, the
  same rules on the same shared code; sharedDevices memdevs are written
  only by a cluster filesystem with memdevSettings coherent.
- Leases of mode fs mount any type, read-only by default, read-write with
  --read-write, the expected type with --fs-type; local sources are
  supported.

Answers to the task's questions (00-README, 02-design "Answers in short"):
- Two pods may share a read-write mount on one node.
- A read-write pod and a read-only pod may share the device on one node.
- Read-write on two nodes is refused for single-host filesystems and
  allowed for cluster filesystems on coherent memory.
- A writer and readers on different nodes: the readers wait.
- The driver knows a mount is dangerous from the superblock type plus the
  pool's facts (shared, exclusive, singleHost, coherent).

Security changes (2026-11-03, user)
-----------------------------------
- fsTypes defaults to [erofs] (A20): only erofs is designed for untrusted
  images; another type is the admin's statement of trust in every party
  that can write the node's devices raw. Both drivers and the shared
  code's fallback; chart values, schema, README and samples say so.
- The lease socket directory is mounted read-only at /run/cxl (A21,
  review H-1): a container cannot write the host directory. The socket is
  bound in a driver-only directory, given its mode there and renamed into
  place (nothing follows a path that an older read-write container could
  have replaced); the directory's entries are removed by name, without
  the broker lock.
- e2e: test20 and test21 configure fsTypes explicitly; test21 proves the
  default refuses ext4 (P4 event "filesystem type ext4 is not allowed on
  this node (fsTypes: erofs)"); test12 proves /run/cxl is read-only
  ("touch: /run/cxl/x: Read-only file system") while cxl-request works;
  the lease CDI assertions expect rbind,ro. Docs updated (DOC phase 4).
- Verification on image nri-dra-driver-cxl-image-b0a0eb6c6c91.tar: unit
  tests, vet, gofmt, lint clean; test21, test20, test12, test16, test15,
  test13, test18 PASS, test90 20 min PASS (507 steps).
- Open (O8): the security review (08-review-security.txt) covers H-1
