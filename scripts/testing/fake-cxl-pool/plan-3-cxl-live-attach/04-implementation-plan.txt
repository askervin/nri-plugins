Shared Go interface (package main, cmd/kubelet-cxl-plugin/lend.go, owned by
W1b; W1a codes against it and may stub it in tests)
----------------------------------------------------------------------------
// containerRef is a running container known to the NRI stub.
type containerRef struct {
    PodUID, PodNamespace, PodName, Name, ID string
    Pid        uint32 // init pid at StartContainer (0 if unknown)
    CgroupPath string // absolute cgroup v2 dir, as resolveContainerCgroupDir
    BaseMems   string // cpuset.mems.effective at start, e.g. "0-1"
}
type Lender interface {
    // ContainerByPid finds the container whose cgroup contains pid
    // (/proc/<pid>/cgroup prefix match against CgroupPath).
    ContainerByPid(pid int) (*containerRef, bool)
    // Container by pod UID and container name.
    Container(podUID, name string) (*containerRef, bool)
    // LendNode adds NUMA node to the container's cpuset.mems through NRI
    // UpdateContainers (mems = BaseMems + all lent nodes). Idempotent.
    LendNode(ctx context.Context, podUID, name string, node int) error
    // RevokeNode removes the node (pages migrate back). Idempotent; a
    // container that is gone is not an error.
    RevokeNode(ctx context.Context, podUID, name string, node int) error
    // LentNodes returns the nodes currently lent to the container.
    LentNodes(podUID, name string) []int
    // OnContainerGone registers a callback for StopContainer/RemoveContainer
    // of a container that has lends or a lease socket (W1a releases leases).
    OnContainerGone(func(ref containerRef))
    // OnContainerStarted registers a callback for StartContainer (W1a
    // re-applies exclusive lends of Ready leases to a restarted container).
    OnContainerStarted(func(ref containerRef))
}
The *nriPlugin (nri.go) implements Lender. driver.go already keeps
driver.nriPlugin; W1a reaches it as `driver.nriPlugin` (nil when NRI failed
to start: then lease requests fail with "lending unavailable: NRI not
connected").

W1b: lend primitives in nri.go (+ lend.go, lend_test.go)
----------------------------------------------------------
1. Container table: fill on CreateContainer (pod uid/ns/name, container
   name, id), StartContainer (pid, cgroup dir via resolveContainerCgroupDir,
   BaseMems from <cgroup>/cpuset.mems.effective), StopContainer/
   RemoveContainer (remove, fire OnContainerGone). Implement Synchronize
   (stub.SynchronizeInterface): rebuild the table from the runtime's list of
   pods and containers at (re)connect; BaseMems of a container that already
   has lends: read cpuset.mems.effective minus the lent nodes W1a re-applies
   (document the approximation).
2. LendNode/RevokeNode: compute mems = BaseMems union lent nodes (k8s.io/
   utils/cpuset for parsing/formatting), call
   p.stub.UpdateContainers([]*api.ContainerUpdate{{ContainerId: id, Linux:
   &api.LinuxContainerUpdate{Resources: &api.LinuxResources{Cpu:
   &api.LinuxCPU{Mems: api.String(mems)}}}}}) and check the per-container
   result (UpdateContainers returns failed updates). Never set a cpuset.mems
   without BaseMems (a movable node alone breaks the container). Keep the
   lent set per container id in memory; LentNodes reads it.
3. Interaction with cgmpolmgr steering: a container that has a cgmpolmgr
   manager (p.managers[id]) is refused for LendNode with a clear error
   ("container is memory-steered by a local CXL claim; lending is not
   supported together with steering yet"); document in POOL.md.
4. Unit tests with a fake stub (the stub interface used: UpdateContainers,
   Start, Stop): table lifecycle, mems arithmetic, idempotence, revoke of a
   gone container, refusal when steered. Existing nri.go behaviour must stay
   unchanged (go test ./cmd/kubelet-cxl-plugin/...).

W1a: token device, lease broker, companion objects, CLI
-------------------------------------------------------
Files: dynamic.go (token device + CDI edits), broker.go (socket server,
leases, companions, fd passing), lease_store.go (persistence), pool.go
(LendConfig hooks), driver.go/main.go (wiring, flags), cmd/cxl-request/
(static CLI, new), deployments/cxl/pool/device-class-dynamic.yaml and
examples/borrower-pod.yaml, doc/cxl/POOL.md "Lending to running containers",
RBAC additions in deployments/cxl/base/resource-driver.yaml (pods and
resourceclaims: create, get, list, watch, delete; events create).
1. Token device: node_state.go GetResources publishes in the cxl.generic
   slice a device `dynamic` (attributes type=dynamic, name=dynamic; no
   capacity; AllowMultipleAllocations true; no NodeAllocatableResources).
   DeviceClass cxl-dynamic: device.driver == "cxl.generic" &&
   device.attributes["cxl.generic"].type == "dynamic". buildDevInfos gets a
   synthetic DeviceInfo for it (Dev type *device.DynamicToken).
2. Prepare of a claim containing the token (prepareAllocatedDevices path):
   create <plugin data dir>/leases/<claim uid>/ (0755) and start a listener
   on <dir>/cxl.sock (0666); return, besides the existing claim marker, a CDI
   device `generic/cxl=lease-<claim uid>` with mounts
   {hostPath: <dir>, containerPath: /run/cxl, options: [rbind, rw]} and
   {hostPath: <flag --cxl-request-bin, default /usr/local/bin/cxl-request>,
   containerPath: /usr/local/bin/cxl-request, options: [bind, ro]} and env
   CXL_LEASE_SOCKET=/run/cxl/cxl.sock. Record claim uid -> pod (reservedFor)
   in the store. Unprepare: release all leases of the claim's pod (delete
   companions, wait for them to disappear, bounded by the kubelet RPC
   timeout: return an error "still releasing" so kubelet retries if not done
   in 30 s), close the listener, remove the directory. On plugin start:
   re-create listeners for stored claims (the directory is already mounted
   into the containers; a fresh socket inside it is reachable).
3. Protocol on cxl.sock: SOCK_STREAM unix, one JSON object per line.
   Request {"op":"lease","kind":"memory","size":"512Mi","wait":"120s",
   "requestId":"..."} | {"op":"lease","kind":"shared","serial":"0xc1ae0001",
   "wait":"120s"} | {"op":"release","lease":"<id>"} | {"op":"release",
   "all":true} | {"op":"list"} | {"op":"fd","lease":"<id>"} (re-send the fd
   of a Ready shared lease). Response: one JSON line {"lease":"<8 hex>",
   "state":"Creating|Pending|Lending|Ready|Releasing|Failed","kind":...,
   "node":N,"size":bytes,"serial":"0x..","dax":"/dev/daxX.Y","error":"..."};
   for a Ready shared lease the response line is sent with the open dax fd
   as SCM_RIGHTS ancillary data on the same write (net.UnixConn.WriteMsgUnix;
   open the dax O_RDWR; close the plugin's copy after sending).
   Caller auth: SO_PEERCRED (syscall.GetsockoptUcred) pid -> lender.
   ContainerByPid; the container's pod UID must be the pod of the claim that
   owns the socket; otherwise 403-style {"error":"not a container of the
   claim's pod"}. The lease is bound to (pod UID, container name).
4. Companion objects in the requester's namespace: ResourceClaim
   `cxl-lease-<id>` (spec.devices.requests[0]: exactly {deviceClassName:
   cxl-pool-memory, capacity.requests.memory: <size>} or {deviceClassName:
   cxl-shared-memory, selectors: [cel serial == <serial>]}; spec.devices.
   config[0].opaque {driver: cxl-pool.generic, parameters: {apiVersion:
   cxl-pool.generic/v1alpha1, kind: LendConfig, lease: <id>, pod: {namespace,
   name, uid}, container: <name>}}; ownerReference -> requester pod
   (controller: true)) and Pod `cxl-lease-<id>` (ownerReference -> requester
   pod; nodeAffinity required matchFields metadata.name In [node];
   tolerations [{operator: Exists}]; restartPolicy Always; one container
   `pause` image registry.k8s.io/pause:3.10 with resources requests=limits
   cpu 1m memory 8Mi and NO resources.claims; spec.resourceClaims [{name:
   lease, resourceClaimName: cxl-lease-<id>}]; labels cxl-pool.generic/lease=
   <id>, cxl-pool.generic/requester-uid=<pod uid>). kubelet prepares the
   claim although no container references it (dra/manager.go). Create the
   claim first, then the pod.
5. pool.go hooks: parse LendConfig from claim.Status.Allocation.Devices.
   Config (opaque, driver == pool driver name) in prepareClaim; after
   prepareDevice: exclusive -> lender.LendNode(ctx, pod.uid, container,
   node) (retry the region creation once after 3 s on "add_dev() failed"
   style errors; a lend error fails the Prepare: kubelet retries, nothing
   is left half done because Unprepare revokes idempotently); shared ->
   nothing to lend here; then broker.OnPrepared(lease, LendConfig, device
   info incl. dax path and node). In unprepareClaim, before release:
   exclusive -> lender.RevokeNode; shared -> broker.OnReleasing(lease) (the
   fd holders get SIGBUS after region destroy, documented). Store the lend in
   preparedPoolClaims.json (new fields) so a restart re-applies it
   (OnContainerStarted callback: for each Ready exclusive lease of that
   container, LendNode again).
6. Lease state machine and store: leases.json in the plugin data dir,
   written before any API object is created (Creating), then Pending
   (objects exist), Lending (companion claim prepared, lend in progress),
   Ready, Releasing, Failed (message). "wait" blocks the request until Ready
   or Failed or timeout (timeout -> release and Failed "timeout"). Release
   = Releasing, RevokeNode (exclusive), delete companion pod (foreground
   propagation; the claim follows by ownerReference and by the
   resourceclaim controller), wait until pod and claim are gone, drop the
   lease. Reconcile at start and every 60 s: leases whose requester
   container is gone (lender.Container fails) or whose companion pod is gone
   -> release/drop; companions with our labels on this node without a lease
   -> delete. OnContainerGone -> release all leases of (pod, container).
7. Flags (main.go): --cxl-request-bin, --lease-wait-default 120s,
   --companion-image registry.k8s.io/pause:3.10, --pool-lend (default true).
8. cmd/cxl-request (static, CGO_ENABLED=0): `cxl-request memory 512Mi
   [--wait 120s]`, `cxl-request shared 0xc1ae0001 [--exec CMD ARGS...]`
   (receives the fd, sets CXL_LEASE_FD=<n> and CXL_LEASE=<id>,
   CXL_LEASE_DAX, CXL_LEASE_SIZE, then execs CMD with the fd inherited at
   fd 3; without --exec it prints the JSON and exits, the fd is dropped),
   `cxl-request fd <lease> --exec CMD` (re-attach), `cxl-release <lease>|
   --all` (also as `cxl-request release`), `cxl-request list`. Socket from
   $CXL_LEASE_SOCKET. Exit codes 0/1/2(usage)/3(timeout or failed).
9. Unit tests: protocol (fake Lender, fake clientset, fake pool helper
   hook): lease create -> objects created with the exact spec; auth
   rejection; OnPrepared -> Ready; release deletes objects and revokes;
   restart loads the store and re-creates sockets; reconcile drops
   orphaned leases; LendConfig parsing. go vet, go test -race.
10. Docs: POOL.md section with the flow, the protocol, the CLI, the
   limitations from 03-summary.txt (memory limits, steering conflict,
   SIGBUS on forced release, RBAC).

W1b Findings
------------
1. Container table. Every container is tracked (not only those with
   claims), keyed by container id: CreateContainer adds pod uid/ns/name,
   name, id; StartContainer adds Pid (ctr.GetPid()), CgroupPath
   (resolveContainerCgroupDir) and BaseMems, then fires OnContainerStarted;
   StopContainer and RemoveContainer remove the entry and fire
   OnContainerGone once (whichever comes first). The callbacks fire for
   EVERY container, not only those with lends or a lease socket: W1a
   filters. Container(podUID, name) returns the newest entry (creation
   order) if a restarting container briefly has two ids.
   ContainerByPid matches /proc/<pid>/cgroup against CgroupPath by path
   element (dir or dir/...; ".../c1" does not match ".../c10"); for an
   entry without a resolved cgroup it falls back to "cgroup path contains
   the container id" (cri-containerd-<id>.scope, crio-<id>.scope).
2. Deadlock rule (measured in source, not in a VM): containerd's NRI
   wrapper takes one lock for every event AND for unsolicited updates
   (internal/nri/nri.go updateFromPlugin l.Lock()), and NRI StartContainer
   runs before task.Start (cri/server/container_start.go:240/247).
   Therefore UpdateContainers must never be called synchronously from an
   NRI event handler. Consequences in the code: OnContainerGone and
   OnContainerStarted callbacks run in their own goroutines (W1a may call
   LendNode from them; the update then waits until the StartContainer
   event has returned, which is what we want); p.mu (taken by the event
   handlers) is never held across UpdateContainers; a separate lendMu
   serializes LendNode/RevokeNode. W1a must not call LendNode/RevokeNode
   from inside Synchronize/Create/Start/Stop handlers of its own.
3. Synchronize (stub.SynchronizeInterface) on start/restart: rebuilds the
   table from the runtime's pods and containers (CREATED, RUNNING, PAUSED;
   STOPPED skipped). Running ones get pid, cgroup and BaseMems like at
   StartContainer. It fires no OnContainerStarted (W1a re-applies from its
   lease store at start; WaitSynchronized(ctx) lets it wait for the table,
   because stub.Start returns after Configure, before Synchronize). On a
   reconnect, lent sets of containers that remain are kept and containers
   that vanished fire OnContainerGone. A container synced with claims that
   have DRAM/CXL devices (same rule as CreateContainer's plan) is marked
   steered, although cgmpolmgr steering itself is not resumed after a
   plugin restart (existing behaviour).
4. BaseMems derivation: cpuset.mems.effective of the container cgroup at
   StartContainer (fallback: the spec's linux.resources.cpu.mems if the
   file is unreadable), MINUS the nodes currently lent to any container by
   this plugin (an unconstrained container started while another
   container's lent CXL node is online would otherwise count that node as
   its own). Approximation after a restart: the lent sets are lost, so
   BaseMems = effective still contains the nodes lent before the restart;
   every node passed to LendNode/RevokeNode is a pool node and is removed
   from BaseMems at that call. A previously lent node whose lease W1a does
   NOT re-apply stays in BaseMems until RevokeNode(node) is called for it;
   RevokeNode also issues the shrink when the node is not in the lent set
   but appears in the cgroup's cpuset.mems. Not covered: an unconstrained
   container started while a pool node was online but before any lend of
   it (node not lent yet), whose effective set then includes the pool
   node. The first LendNode/RevokeNode of that node to THAT container
   removes it; for other containers it remains (they could use it anyway,
   being unconstrained: existing weakness).
5. LendNode/RevokeNode: mems = (BaseMems \ {node}) union lent (k8s.io/
   utils/cpuset), sent as UpdateContainers([{ContainerId, Linux.Resources.
   Cpu.Mems}]). Note: LinuxCPU.Mems is a plain string in NRI v0.12.2, not
   an OptionalString as the spec's api.String(mems) suggested. A failed
   update (returned in the failed list) or an error is returned and the
   lent set is not changed. Refusals: base empty after removing the node
   ("base memory nodes unknown, refusing to set cpuset.mems without
   them"), container not started yet, not found (LendNode only), NRI not
   connected (p.stub nil: "lending unavailable: NRI not connected"), ctx
   already done. Idempotent: no update when nothing changes. Revoke of a
   gone/unknown container is nil (containerd also returns success for
   unknown ids). Revoke never removes the node from cpuset.mems "too
   early" because the kernel migrates pages at once on shrink (02-...
   mechanics 3.1); checking numa_stat afterwards is W1a's job.
   On revoke to an empty lent set the container keeps an EXPLICIT
   cpuset.mems = BaseMems (it may have been empty = all nodes before the
   first lend). This is intended: a later pool node with the same number
   is not inherited.
6. Steering refusal: LendNode returns an error wrapping errSteered
   ("container is memory-steered by a local CXL claim; lending is not
   supported together with steering yet") when p.managers[id] or
   p.pending[id] exists or the entry is marked steered. RevokeNode is
   allowed (no-op unless something to undo).
7. Open issues: (a) UpdateContainers in the stub uses
   context.Background(), so ctx cannot cancel an update in flight; a hung
   runtime blocks LendNode (and other lends via lendMu). (b) The stub does
   not reconnect after onClose (existing behaviour); after a runtime
   restart LendNode gets the stub's error until the plugin restarts.
   (c) nri-resource-policy or the kubelet memory manager on the same node
   would also own cpuset.mems (03-summary limitation); not detected.
   (d) The update sends only Cpu.Mems; containerd's toCRIResources then
   passes zero cpu shares/quota/period and memory limit, which containerd's
   WithResources skips (internal/cri/opts/spec_linux_opts.go:386-401, "!= 0"
   checks), so only cpuset.mems changes; lendctl in 02-...mechanics did the
   same on containerd 2.4.1. CRI-O is unverified.
   (e) Lent sets are in memory only; persistence is W1a's lease store plus re-application through LendNode.

W2 Findings

1. Deviation from the story, by fact: "another container of the same pod
   does not [have node N]" does not hold in VM2 as specified. Every
   container there has an EMPTY cpuset.mems (kube-proxy, coredns, the
   scratch borrower; kubepods.slice too): no CPU manager, no NRI policy.
   An empty cpuset.mems inherits the root's effective mems, which grows
   with every onlined node, so container idle has N in
   cpuset.mems.effective and Mems_allowed_list without any lend (R8 of
   02-option-companion-pod-dra-lend.txt, "exclusive only by convention").
   test12 asserts what is true and meaningful instead: cpuset.mems (the
   container's own file) of main == DRAM nodes + N after the lend and ==
   DRAM nodes after the release (the lend made it explicit), cpuset.mems
   of idle unchanged; if idle's cpuset.mems is empty (VM2), it asserts N
   IS in idle's effective nodes and says so; only if idle has its nodes
   set does it assert N absent and that numa-touch.py in idle gets EINVAL.
   Consequence for the design (report, not fixed): pages of other
   containers can land on a lent node (only as a fallback, the node has no
   CPUs), and the release then depends on offline migrating them.
2. Node lists are compared as sets: the kernel and k8s.io/utils/cpuset
   both join ranges ("0-1" + 2 prints "0-2").
3. In the container only /usr/local/bin/cxl-request is mounted, so test12
   uses `cxl-request release L|--all`, not `cxl-release`.
4. D reads the shared bytes back with `cxl-request fd <lease> --exec ...`
   (re-send of the Ready lease's fd), not with a second `cxl-request
   shared`: a second shared lease for the same serial in the same pod
   would be a second claim on the same device and node. D also checks the
   --exec environment: CXL_LEASE_FD=3, CXL_LEASE, CXL_LEASE_SIZE ==
   256 MiB, CXL_LEASE_DAX == readlink /proc/self/fd/3.

   checks that the token claim is deleted with the pod and that
   $DRA_LEASE_DIR/<token claim uid> is removed (unprepare). The pod has no
   memory limit (lent memory is charged to the container).

   lent node (numa-touch --hold) and one shared lease (fd dropped), and
   requires everything gone within 90 s of the delete.

Protocol as implemented (cxl.sock, SOCK_STREAM, one JSON object per line
each way, several requests per connection allowed)
- Requests: {"op":"lease","kind":"memory","size":"512Mi","wait":"120s",
  "requestId":"..."}, {"op":"lease","kind":"shared","serial":"0xc1ae0001",
  "wait":"120s"}, {"op":"release","lease":"<id>","wait":"..."},
  {"op":"release","all":true}, {"op":"list"}, {"op":"fd","lease":"<id>"}.
  serial: any base accepted by strconv.ParseUint(s, 0, 64), normalized to
  0x<lower hex> for the CEL selector. size: a resource.Quantity > 0.
- Response: {"lease":"<8 hex>","state":"...","kind":"memory|shared",
  "node":N,"size":<bytes, int>,"serial":"0x..","dax":"/dev/daxX.Y",
  "error":"..."}; omitted fields are absent (node only for a lent memory
  lease; size is the requested size until Ready, then the device size).
  list and release-all: {"leases":[...]} ([] when empty).
- States: Creating, Pending, Lending, Ready, Releasing, Failed; and
  "Released" (response only: the lease is gone).
- Ready shared lease: the response line to "lease" and "fd" goes with the
  open dax fd (O_RDWR) as SCM_RIGHTS in one WriteMsgUnix; the plugin
  closes its copy after sending.
- Auth: SO_PEERCRED pid -> Lender.ContainerByPid -> the container's pod
  UID must be in the token claim's reservedFor (re-read from the API once
  on a miss, for claims shared by several pods). Otherwise every request
  on that connection gets {"error":"not a container of the claim's pod
  (...)"}; without NRI: {"error":"lending unavailable: NRI not connected"}.
- Release/list/fd scope: lease/fd belong to (pod uid, container); list,
  release and release-all accept any container of the same pod; fd only
  the owning container.

Choices where the spec left room (and small deviations)
1. Release deletes BOTH companion objects (pod, then claim; foreground
   propagation) and waits until both are NotFound. The claim's controller
   owner is the requester pod (as specified), so the resourceclaim
   controller would only delete it when the REQUESTER is done; deleting
   it explicitly while the companion terminates is safe (finalizer until
   deallocation; kubelet unprepares from its own claim cache).
2. Extra companion fields beyond the spec: label cxl-pool.generic/node=
   <node> (reconcile lists orphans by it; a Pending companion has no
   nodeName), annotation cxl-pool.generic/requester=<ns>/<pod>/<ctr>,
   automountServiceAccountToken false, enableServiceLinks false,
   terminationGracePeriodSeconds 1. Request name and pod claim name:
   "lease". The claim's config has no "requests" list (applies to all).
3. OnContainerGone does NOT release unconditionally (it fires on every
   container stop, including restarts): leases are released when the
   pod is gone/being deleted/Succeeded/Failed, has a different UID, or
   has restartPolicy Never, and no new instance of the container is
   already running; otherwise they are kept and OnContainerStarted re-applies exclusive
   lends (lifecycle row "requester container crashes/restarts" of
   03-summary). The reconcile uses the same rule for "requester
   container gone".
4. Re-application after a plugin restart is done by the broker's
   reconcile (start, after (*nriPlugin).WaitSynchronized with a 30 s cap,
   then every 60 s: LendNode for every Ready memory lease whose
   container exists; idempotent), not by pool.go. pool.go persists the
   lend so its Unprepare can revoke after a restart.
5. Lend failures (errSteered, not started, not found, NRI not connected,
   base mems unknown, any LendNode error): Prepare fails and is rolled
   back (region released, best-effort revoke), and the broker marks the
   lease Failed with the error text and releases it; the waiting request
   returns Failed with that message (coordinator item 3). A Failed lease
   keeps state Failed (not Releasing) until it is gone.
6. LendConfig is untrusted tenant input: accepted only with Source
   FromClaim, apiVersion <pool driver>/v1alpha1, pod.namespace == claim
   namespace, and only if the broker has that lease for the same pod and
   container (OnLending), checked before any device is touched.
7. Timeout: the response (state Failed, error "timeout: not Ready after
   D") is sent at once; the release continues in the background.
8. "wait":"0s" returns the current state and keeps the lease (Pending
   leases stay until released or cleaned up by the pod's end).
9. --exec is fork+exec+wait with signal forwarding and exit-code pass
   through (exec.Cmd.ExtraFiles -> fd 3), not execve in place: dup2 onto
   fd 3 in a running Go process can clobber the runtime's epoll fd.
10. The CLI is also mounted as /usr/local/bin/cxl-release.
11. The token is published only with --pool-lend AND the pool helper
   enabled (lending needs the pool driver).
12. Auth happens once per connection (at accept).

W2 Findings (phase 2)
---------------------
1. The lease design works end to end on stock Kubernetes in VM2: a
   running container asked for 512Mi, got pooled0 as NUMA node 2 in its
   own cpuset.mems (0-2, written through NRI; the other container's
   cpuset.mems stayed empty), put 256 MiB there (numa_stat anon N2 = 256
   MiB), released it while the process kept running (pages moved to N0 in
   < 1 s, numa-touch.py still alive and reporting N0), and the device went
   back to the pool in ~7 s. Shared memory: the written string was in the
   host's shared0.raw, read back through a re-sent fd (`cxl-request fd`),
   with CXL_LEASE_FD=3, CXL_LEASE, CXL_LEASE_SIZE=268435456, CXL_LEASE_DAX
   == readlink /proc/self/fd/3; no /dev/dax* in the container. Four cycles
   left nothing behind; deleting the pod with a memory lease in use and a
   shared lease cleaned up everything (GC + "requester container gone").
2. Device cgroup (measured, containerd + systemd cgroup driver): the first
   runtime update of a container (crictl update or NRI UpdateContainers,
   here the lend) attaches one more cgroup_device eBPF program with
   DIFFERENT code next to runc's (probably systemd's for the scope's
   DeviceAllow); later updates add none (checked with 3 updates). The
   device rules of the spec stay [{"access":"rwm","allow":false}], and an
   mknod'ed dax node cannot be opened after the lend: the fd passing does
   not widen the device cgroup. Ids of attached programs are not a usable
   "unchanged" signal.
3. Companion start is slow because of its CPU limit (report, not changed:
   the 1m/8Mi Guaranteed shape is W1a step 4 / 03-summary). In test12 the
   companion pause pod took ~12 s from NodePrepare to Running (Prepare
   +12.8 s, Pulled +20.6 s, Started +24.8 s) while test10's pods take ~1 s.
   Measured in VM2 with plain pause pods: limits cpu 1m -> Running after
   14.4 s, 10m -> 14.3 s, 100m -> 2.4 s, 1 -> 2.4 s, no CPU limit -> 2.4 s.
   The CFS quota of the pod cgroup throttles the sandbox and runc init.
   The lease is Ready at NodePrepare, so requests do not wait for it, but
   a companion that is still starting cannot be stopped before it has
   started: in F the shared lease's companion was 7 s old and not started
   when the borrower was deleted, and its unprepare waited until kubelet
   had created and started its pause container (+12 s), most of F's 20 s.
   Suggestion for W1a/coordinator: companion requests=limits cpu 100m (or
   no CPU limit, Burstable) - 100m charges 0.1 CPU per lease to the node.
4. A lease is Ready when the companion's claim is prepared, before the
   companion's container runs (by design: kubelet prepares before it
   creates containers). Nothing depends on the pause container running.
5. Kubelet logs "failed to read memory cgroup config for the pod" (pod
   cgroup already removed) for every companion at teardown: noise of
   kubelet, harmless; it also appears for other short pods.
6. The companion of F that was stopped right after its start ended
   "Error" instead of "Completed" (pause killed during start with
   terminationGracePeriodSeconds 1). Harmless, cosmetic.
7. The R8 limitation (phase 1 Finding 1) is confirmed in the VM: idle's
   cpuset.mems.effective was 0-2 during every lend, without a lend.
8. Not tested (left out): requester container restart (re-applied lend),
   plugin restart with active leases (reconcile after WaitSynchronized),
   lease timeout / unsatisfiable request (pooled0 busy), auth rejection
   from another pod, CRI-O, SELinux enforcing (VM2 has it disabled), a
   steered container (refusal), several borrowers at once.
