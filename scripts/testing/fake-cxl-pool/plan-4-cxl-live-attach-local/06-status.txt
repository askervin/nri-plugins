DAX SLICING PROCEDURE (memctl vs 01 1.2 and linux drivers/dax/bus.c)
- First slice: CreateRegion(devdax) binds daxX.0 to device_dax (moving it
  off kmem and offlining), then ResizeDaxDevice unbinds, writes the size
  and reads it back, then bindSlice -> SetDaxDriver(device_dax). 01
  measured unbind kmem -> size -> bind device_dax. memctl adds one
  device_dax bind/unbind cycle of daxX.0, which does no harm.
- Later slices: echo 1 > create, cat create (youngest), size, bind. This
  matches 01. The kernel agrees: create_store returns -ENOSPC when
  available_size is 0 (bus.c:368-410), and addSlice checks the free space
  first. A new device has size 0, and dax_bus_probe refuses size 0 with
  -ENXIO (bus.c:199-216), so it stays unbound until it is sized and bound
  explicitly, as memctl assumes.
- Delete: unbind -> size 0 -> echo daxX.Y > delete, with daxX.0 kept at
  size 0. This matches 01, and delete_store refuses a bound device, a
  non-zero size and id 0 (bus.c:534-578). The region goes with cxl
  disable-region + destroy-region and the memdev stays enabled, as
  measured.
- daxctl path (`daxctl reconfigure-device --mode=devdax --force daxX.Y` on
  a freshly created, sized, never bound slice) is plausible, not verified.
  As far as I recall libdaxctl (ndctl source is not in ~/github.com, so I
  could not read it), reconfigure to devdax disables the device (a no-op
  when it is unbound) and enables device_dax through new_id/bind. That is
  the same call `daxctl create-device` makes for a new device, and the
  kernel accepts the probe once size > 0. The unit fake only models "fails
  at size 0". Check on VM2 (daxctl installed) for a devdax region R:
    D=$(echo 1 > .../dax_region/create; cat .../dax_region/create)
    echo 33554432 > /sys/bus/dax/devices/$D/size
    daxctl reconfigure-device --mode=devdax --force $D; echo rc=$?
    readlink /sys/bus/dax/devices/$D/driver   # .../device_dax
    cat /sys/bus/dax/devices/$D/dev; ls -l /dev/$D   # same major:minor
    daxctl list -D -d $D                     # mode devdax, size 32M
  Repeat for daxX.0 after unbinding it from device_dax and shrinking it.
  Then delete $D (unbind, size 0, delete) and create it again under the
  same name: it must come up unbound (no new_id left behind). Also check
  that dmesg has no "probe ... rejects match" for bound slices, and that
  no daxdev-reconfigure@ unit acted (/etc/daxctl.conf.d empty).

Deviations from 09, with reasons
 1. numa slices are bound to kmem with memctl.SetDaxDriverSysfs (the sysfs
    bind of that one device), not SetDaxDriver: with daxctl installed (VM2)
    SetDaxDriver runs `daxctl reconfigure-device --mode=system-ram
    --no-online`, a path no test has measured. As far as I know libdaxctl
    binds through the driver's new_id, which makes kmem take every unbound
    dax device of the CXL regions (R1's R4), and with --no-online it refuses
    when the kernel auto-onlines added memory. The sysfs bind is what 08
    measured. device_dax (dax slices, region creation) still goes through
    SetDaxDriver/daxctl as measured in test14.
 2. memctl regionBlocks counts only the blocks that lie wholly in the
    region, and waitRegionBlocks returns at once when there are none. kmem
    adds only whole blocks, so before this, CreateRegion on a region that
    does not start at a block boundary (the only case in which the mapping
    fallback is needed) waited forever for a partial block. Same result for
    aligned regions (all e2e regions), so the pool path behaves as before.
 3. A device of one block publishes requestPolicy {default: BS, validValues:
    [BS]}: the API server rejects a validRange whose min+step exceeds the
    capacity. Devices smaller than one block, and all devices while the
    block size is unknown, are not published (a slice could not be served).
 4. ConsumedBytes = TotalBytes = slice size also for dax claims (09 named
    only numa): one rule for all local slices; for dax TotalBytes already was
    the slice size. cgmpolmgr's CXL quota of a numa claim is its slice.
 5. New memctl API beyond 09 2a-c: Range (with End included, as sysfs and the
    mapping attribute have it), RegionRange, SetDaxDriverSysfs;
    RegionFreeGaps returns an error as well.
 6. The scan input is a *localSnapshot (modes and block size) instead of the
    modes map: buildDevInfos/scanDevices take it; nil literals in other
    tests still compile; Modes() is kept for tests.
 7. Reconcile also deletes dax devices of the region that belong to no slice
    (a crash between creating a slice and saving the state), offlining kmem
    ones first.
 8. Old state files (mode per device): slices take the device mode. A numa
    device of such a file has its whole region online (ram region, daxX.0 on
    kmem): further numa claims share it (Online again, as before), a dax
    claim gets "no room" (daxX.0 is counted as used), until the region is
    released with its last claim. Only reachable when the plugin is
    upgraded with numa claims prepared.
 9. A claim without consumed capacity gets the device size rounded down to
    whole blocks (the scheduler normally fills consumedCapacity = default).
10. The example manifests' comments were updated: local-dax-readonly-pod.yaml
    said "dax memory is not cleared", wrong since R3's zeroing.

W3 open issue (c): a block size larger than the region alignment
-----------------------------------------------------------------
Facts from the 7.3 source. x86 caps the block size by the alignment of
the CFMWS base and size (drivers/acpi/numa/srat.c acpi_parse_cfmws ->
memory_block_advise_max_size; arch/x86/mm/init_64.c
probe_memory_block_size), so window bases are block-aligned. Regions in
a window get their HPA ascending at 256 MiB alignment
(drivers/cxl/core/region.c alloc_hpa -> alloc_free_mem_region(...,
SZ_256M); kernel/resource.c ascending by default). Consequences:
- With BS <= 256 MiB (the VMs) every region is aligned.
- With BS > 256 MiB a local region is misaligned exactly when the
  regions below it in the same window (pool or shared devices under the
  host bridge) do not end on a block boundary.
- The head is then at most BS - 256 MiB, and the region holds at least
  floor((S - (BS - 256 MiB)) / BS) whole blocks: one block less than
  S/BS for a block-multiple S, while the scheduler counts S/BS.
- First-fit dax slices make it worse. They take the head plus part of
  the next block, which numa slices cannot use. TestLocalNUMAPlacement
  shows it: dax0.0 gets the 64 MiB head and 64 MiB of memory75. A
  numa, dax, numa, numa sequence of one-block claims on its 512 MiB
  region (published 512Mi = 4 blocks, 3 whole blocks) fails the fourth
  claim at Prepare.
Proposal:
1. Place every slice on whole blocks, dax slices too. In addSlice
   (local.go:498) drop the `s.Mode == device.ModeNUMA` condition before
   alignSlice. Aligned regions do not change (first-fit is aligned
   already). On misaligned regions the head and tail are never used, so
   a dax slice cannot split a block that numa needs. Let the fallback
   cover several aligned gaps when no single gap fits: one mapping
   write per range, since mapping_store appends a range through
   alloc_dev_dax_range, then check all ranges. Free whole blocks then
   stay usable after releases.
2. Publish what the device is sure to hold (node_state.go:588,
   602-618, 432). Capacity value and default become
   usable(size, BS) = floor(size/BS)*BS when BS <= 256 MiB, else
   floor((size - (BS - 256 MiB))/BS)*BS. The one-block validValues case
   and "not published below one block" apply to usable. The only new
   constant is the kernel's CXL HPA alignment (256 MiB), not a block
   size. Optionally, the exact whole-block count of RegionRange while
   the plugin holds the region (it is >= usable). The value then drops
   back when the region is recreated, so the conservative value alone
   is simpler.
3. Log a warning when a created region is not block-aligned. Rewrite
   the LOCAL.md limitation as "with memory blocks larger than 256 MiB a
   device publishes one block less than its RAM capacity". Add a unit
   test: the TestLocalNUMAPlacement region publishes 384Mi and serves
   numa and dax claims in any order.
Cost: nothing on the VMs or on aligned servers, at most one block per
device on servers with blocks over 256 MiB. 08's option B (2Mi dax-only
devices) is independent of this.
