B1 D cmd/kubelet-cxl-plugin/lending.go:272-274 (parseConfig) - owner S1
   What: if an opaque config of the driver has a kind other than the one
   being parsed, the code skips it without an error
   (`if head.Kind != kind { continue }`). No Prepare path checks
   afterwards that every config of the driver had a known kind. Two tests
   assert this skip: lending_test.go:307 ("other kinds and drivers") and
   node_state_test.go:221 (TestParseMemoryPolicyFromClaim_WrongKindSkipped).
   Why: after the renames, an old kind is the most likely user error. A
   reader claim on cxl-pool-shared with {kind: PoolDeviceConfig, readOnly:
   true} prepares without error. Its container gets a read-write
   /dev/daxX.Y: the mode is dax by default for shared devices and readOnly
   stays false. {kind: LocalDeviceConfig, mode: dax} silently gives a numa
   slice. A wrong apiVersion fails the Prepare but a wrong kind does not.
   So strict decoding (02 4.1, I6) has a hole exactly where the rename
   table removed names.
   Fix: fail the Prepare for an opaque config of the driver whose kind the
   driver does not know. cxl.generic knows DeviceConfig and
   MemoryPolicyConfig; cxl-pool.generic knows DeviceConfig. Example texts:
   `unknown kind %q (DeviceConfig or MemoryPolicyConfig)`, and
   `(DeviceConfig)` for the pool driver. Do it in one place: a per-driver
   kind set checked in parseConfig, or validateConfigKinds(claim, driver,
   kinds...) called once at the start of nodeState.prepare and
   poolDriver.prepareClaim. Change the two tests to expect the error. Add a
   test with kind PoolDeviceConfig and readOnly: true on a shared device.
   The new text needs a line in 02 4.1 and in USAGE.md (S4).

B2 D cmd/kubelet-cxl-plugin/broker.go:1324 (deleteOrphans) - owner S1; the
   behaviour predates plan-5, but plan-5 moved the label into the
   cxl.generic domain
   What: the selector is only cxl.generic/node=<node>. A pod or
   ResourceClaim in any namespace with that label is deleted on every
   reconcile (60 s) unless its cxl.generic/lease value is a known lease. An
   object with no lease label counts as unknown, because
   Labels[LeaseLabel] == "" is never known.
   Why: users associate cxl.generic/ with this driver. A workload labelled
   cxl.generic/node for its own selection is deleted silently. Only the
   objects of whoever set the label are affected; nothing crosses
   namespaces.
   Fix: select on both labels, LabelSelector
   "cxl.generic/node=<node>,cxl.generic/lease", where the second term is an
   existence check. Also require the name cxl-lease-<value> before
   deleting. Add a test with a pod that has only the node label.

I-1 D cmd/kubelet-cxl-plugin/node_state.go:1059-1075 (preparedDeviceInfo,
   region and dram cases) - owner S1, needs a 02 4.1 text
   What: DeviceConfig is parsed only for memdev results. Take a claim on
   cxl-region or cxl-dram with a cxl.generic DeviceConfig {mode: dax} or
   {readOnly: true}. That includes a config without a requests list, which
   "applies to all requests of its driver" (02 4.1). Such a claim is
   prepared as numa without an error.
   Why: 02 2.1 makes "the Prepare error with a clear message" the check for
   a mode a device cannot do, and shared + numa does fail. For region and
   DRAM the same kind of mismatch passes silently. So the one DeviceConfig
   kind behaves differently per device type without telling the user.
   Fix: parse the DeviceConfig of the request for region and dram results
   as well. Fail when the effective mode is dax or readOnly is set, for
   example "DeviceConfig: mode dax: a region is used as numa only" (and the
   same for dram). Add the texts to 02 4.1 and USAGE.md (S4), with one test
   per device type. A config without a requests list in a claim that mixes
   memdev dax and region requests would then fail; the user lists
   requests. If the user prefers silence, USAGE.md must say that
   DeviceConfig applies to memdevs only.

I-3 The claim-level CDI device loses DRA's per-request container scoping -
   a consequence of 02 5.1, which S1 implemented as written
   D node_state.go buildClaimsCDISpec and prepareAllocatedDevices: every
   result lists claim-<uid>. pool.go:364 and buildCDISpec: every result
   lists generic/cxl-pool=claim-<uid>.
   What: take a container that references one request of a multi-request
   claim (resources.claims[].request: r1). It gets claim-<uid>, which
   carries the CXL_<KEY>_* of every device of the claim and the device node
   of every dax slice. That includes r2's devices, and a read-write node
   when only r1 is read-only. At e1c7274 local dax slices had one CDI
   device per allocation result (local-<uid>-<n>), and pool devices had one
   per serial, so this narrowing existed then.
   Why: kubelet scopes a container to a request through the CDIDeviceIDs of
   each result. One device per claim makes that scoping ineffective.
   Fix (the user decides; it changes 02 5.1): keep claim-<uid> for the
   marker only. Add claim-<uid>-<n> per allocation result, with api.Env of
   that device and its device node. Each result lists claim-<uid> plus its
   own device; the pool driver does the same with
   generic/cxl-pool=claim-<uid>-<n>. Otherwise USAGE.md must say that a
   container always gets the memory of the whole claim.

I-4 P cmd/fake-cxl-pool-client/main.go:839 - owner S2 (S2 documents this
   as F3, but the reason does not hold)
   What: `guest region create DEVICE --mode devdax` is no longer a usage
   error (exit 2). It now fails after the device lookup, with memctl's text
   and exit 1.
   Why: the client's exit code 2 means "usage". A script that passes an old
   mode now gets the same exit code as a device error. Checking against
   memctl.ModeNUMA/ModeDax would not copy the check, and the error text can
   still come from memctl.

   error` returning "invalid mode %q (numa or dax)", and use it in
   CreateRegion. Call it in the client before the lookup and turn its error
   into a usage error. Test: --mode devdax exits 2 with that text.
