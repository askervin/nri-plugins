Bugs
----
B1 build.sh:51 (with :41-49) and llm.source.sh:44-46: the build fails on a
   fresh cache when LLAMA_CPP_SRC is given.
   What: mktemp -d "$LLM_CACHE/build.XXXXXX" needs $CACHE_DIR/llm to exist.
   Only the fetch branch of build.sh (mkdir -p "$repo", :45) and the
   download branch of llm-model-fetch (:45) create it. With LLAMA_CPP_SRC
   and llm_model=PATH both set (the two documented offline options,
   test16:38-41), or build.sh run alone with LLAMA_CPP_SRC, nothing creates
   it: "mktemp: failed to create directory via template ...: No such file
   or directory" (checked: mktemp -d with a missing parent exits 1), then
   "llm-build: cannot build cxl-llm, see above".
   Why it matters: the documented ways to avoid the network break the first
   run on a host.
   Fix: mkdir -p "$LLM_CACHE" in build.sh before :51 (for instance right
   after :27).

B2 test16:141 and llm.source.sh:313-335 (llm-where-assert), against the
   claims of test16:17-19 ("every access to the weights goes to the CXL
   memory and nothing is copied") and :21-23 ("all page frames of the
   model mapping ... are in a CXL window").
   What: the assertion sums the present pages of every mapping of
   $CXL_<KEY>_DAX in the engine and asks for at least 90% of the model
   size. The engine has two mappings of the device: cxl-llm's own PROT_READ
   mapping of the whole device (cxl-llm.cpp:240-241, 512 MiB, kept until
   exit) and llama.cpp's model mapping (398458880 bytes). The log shows
   "2 mappings, 404750336 bytes present" (97280 + 1536 pages).
   A run in which llama.cpp copies the weights instead of mapping them
   passes every assertion of test16. With use_mmap off, llama.cpp reads
   every tensor through the cookie FILE, a memcpy from cxl-llm's mapping:
   about 97000 pages of that mapping become present, all in the CXL window,
   the page cache does not grow, the answer is the same; only the anonymous
   memory differs (research A 3.6: 520888 kB for dax-copy, against 82872 kB
   in this e2e). Weight repacking (use_extra_bufts, cxl-llm.cpp:466) is the
   same case: the model mapping is fully present and 205 MiB of weights
   are copied into anonymous memory; nothing in test16 sees it.
   rss_anon_kb is logged (test16:143) but not asserted; model_bytes is not
   asserted either.
   Why it matters: "nothing is copied" and "repacking off" (D2, 02 section
   1) are what the direct mode demonstrates. Today they hold because the
   code is right, not because the test checks them.
   Fix: (a) in llm-where-assert, or in readers-check, select the mapping
   whose size equals model_bytes of the summary line; assert model_bytes
   == LLM_PADDED, present == pages for that mapping, and every page of it
   in a "where" chain that ends with "> $(basename "$path")" (the log
   shows "CXL Window 0 > region0 > dax0.0"; the dax name comes from the
   run-time path, so no probe-order name enters). (b) Assert
   rss_anon_kb * 1024 < LLM_MODEL_SIZE / 2 (82872 kB measured; a copy is
   at least the model, repacking adds 205 MiB), with its own message.

Risks
-----
R1 llm.source.sh:208-223 and test16:127-139: the read-only device node is
   proven by configuration only. test16 checks CXL_<KEY>_READONLY=1 and
   "permissions: r" in the CDI device, but no reader tries to open the
   device for writing; test13 does (dax-rw.py check-ro: "open for writing
   refused: EPERM", "writable mapping refused: EACCES"). If the device
   cgroup rule were missing, test16 would still pass.
   Fix: add to llm-reader-script, before the engine,
     if (exec 3<>"$CXL_<KEY>_DAX") 2>/dev/null; then echo "open for writing: allowed"; else echo "open for writing: refused"; fi
   (busybox ash has <>) and assert the "refused" line in readers-check; or
   mount the dax-rw ConfigMap (dra-dax-tool-install) and run check-ro as
   test13 does.

R2 llm.source.sh:47, build.sh:47 and :60-77: the download and the build
   have no time limit. curl has --connect-timeout 30 only: a transfer that
   stalls behind the proxy hangs test16 indefinitely; git fetch, the image
   pull of podman run and dnf likewise.
   Fix: curl --speed-limit 1048576 --speed-time 60 (or --max-time 1800);
   timeout 600 around git fetch and timeout 1800 around podman run, into
   the existing error messages.

R3 llm.source.sh:51-57: the download is moved into the cache before its
   sha256 is checked. A proxy error page served with status 200, or any
   wrong file, becomes $CACHE_DIR/llm/Qwen3-0.6B-Q4_K_M.gguf, and every
   later run fails with "Remove it to download it again" until someone
   does.
   Fix: check "$LLM_MODEL_SHA256  $part" before the mv; on mismatch remove
   $part and fail with the URL and both sums.

R4 build.sh:23, :34, :64, :85: the build is reproducible only for one state
   of fedora:43. The image tag and the dnf packages move; the cache key is
   cxl-llm.cpp + build.sh + the llama.cpp commit; source.txt records the
   tag but not the image digest or the compiler and glibc versions. Two
   hosts (or one host before and after a Fedora update) with the same key
   can hold different binaries, and nothing tells.
   Fix: pin BUILD_IMAGE by digest (registry.fedoraproject.org/fedora:43@sha256:...),
   or at least write podman image inspect --format '{{.Digest}}' and
   rpm -q gcc-c++ glibc-static libstdc++-static cmake into source.txt.

R5 build.sh:51-52, :57, :77-80: on a failed build the EXIT trap removes
   $work and with it the build.log that :57 announces; only the 40 lines
   printed at :78 remain.
   Fix: on failure copy the log to $LLM_CACHE/build-failed.log and name
   that path in the die message (or keep $work on failure).

R6 test16:211, :320: a failed run leaves $POOL_DIR/llm0.raw (512 MiB of the
   host's tmpfs /tmp, with the model in it) until the next run of test16
   removes it at :211; pool-cleanup, the EXIT trap, keeps the backing
   files of static devices.
   Fix: after dra-install-node (the last dra-installed-add sets the trap),
   trap 'dra-cleanup; pool-cleanup; rm -f "$LLM_BACKING"' EXIT; or say in
   the header that the file stays after a failure.
