0. Short answers
----------------
- Upstream: the dax half (drivers/dax/fsdev.c, fs_dax_get, dax_set_ops) is
  in mainline since v7.1 (libnvdimm-for-7.1), with fixes in v7.3-rc1. The
  FUSE half is no longer John Groves' famfs-specific GET_FMAP series (last
  V11, 2026-07-20). The FUSE maintainer rewrote it himself as a generic
  "DAX device based extent maps" facility (FUSE_PASSTHROUGH_V2,
  FUSE_NOTIFY_BACKING_MAP, cyclic/striped maps). v5 was posted 2026-10-16
  and on the same day it was committed to fuse.git for-next. It is in
  linux-next from next-20261016; it was not in next-20261015. It targets
  the v7.4 merge window, which opens about now (mainline is at
  v7.3-rc7-244). It is late, so v7.5 is possible. Nobody has objected to
  this version. John Groves wrote "go ahead and merge it". Amir Goldstein,
  Dave Jiang and Gregory Price reviewed parts of it.
- Maintenance: famfs userspace is very active. It had 135 commits in 2026
  (117 by John Groves, the rest from Micron and one from Miklos Szeredi),
  and the last commit is 2026-10-10. It has never had a tag or a release
  and no distribution packages it. famfs needs a forked libfuse: upstream
  libfuse has no extent-map support.
- On v7.3-rc4: merging fuse/for-next into v7.3-rc4 is clean (52 commits,
  36 files, +2773/-674). The v5 mbox alone does not apply: patch 04
  conflicts without the earlier for-next commits. No kernel config change
  is needed: qemu-cxl-kernel.config already has FUSE_FS=y,
  FUSE_PASSTHROUGH=y, FS_DAX=y, FS_DAX_PMD=y, DEV_DAX_FSDEV=y.
  Userspace is built in the VM: famfs with the libfuse fork, plus ndctl's
  famfs branch or Fedora 43's daxctl 85, which has --mode=famfs.
- Semantics: these fit our use well. Only the master (writer host) creates
  files, with famfs cp/creat, preallocated in 2 MiB units. Plain cp and
  creat() fail with ENOTSUP. Clients mount and replay the log, and their
  files are 0444. read() goes through dax_iomap_rw, so fread works. mmap
  takes DAX faults (huge_fault, VM_HUGEPAGE, PMD) straight to the CXL
  frames. There is no page cache and no option for one. allow_other is on
  by default, and one node mount can be bind-mounted read-only into any
  number of containers. In-kernel extent maps keep open files working if
  the daemon dies (from source, not measured).
- Effort: about 1 day of VM work to a first llama.cpp answer, mostly the
  famfs userspace build (6 git dependencies from personal GitHub repos)
  and the daemon lifecycle. The kernel is an upstream maintainer branch
  with no porting.
- Verdict: GO for prototyping, by the fail-fast rule. famfs is maintained,
  and its kernel half is being merged by the FUSE maintainer himself. On
  v7.3-rc4 it is a clean merge of an upstream branch, not a port. The
  conditions are in section 6: the userspace pins, and an erofs fallback
  if the bind-mount or daemon experiments fail.

4. Semantics that matter for us (docs and source)
-------------------------------------------------
4.1 mkfs (master): `mkfs.famfs [--set-daxmode] [--loglen 8m] /dev/daxN.M`.
  The superblock is at offset 0 and the log follows it (default log 8 MiB).
  The default allocation unit is 2 MiB, configurable with --alloc-unit/--4k
  (589a95e, 2026-08-08). With fsdev_dax bound, the char device has no mmap
  ("No mmap support - all access is through fs-dax/iomap", fsdev.c l.28),
  so mkfs and fsck work through a temporary "dummy mount" (famfs_lib.c
  l.6025-6075, l.2432-2450).
  The master is the host whose /opt/famfs/system_uuid equals the uuid in
  the superblock (famfs_misc.c l.202-228, famfs_lib.c l.505-531). The file
  is generated on first use, so the two VMs differ as long as /opt/famfs
  is not copied between them.
4.2 Creating and filling files: only `famfs cp SRC DST` and
  `famfs creat -s SIZE` work. They allocate (2 MiB units, optional
  interleave), append a log entry, create the shadow entry, then copy the
  data in through the mounted file. famfs_fused's .create returns ENOTSUP
  (famfs_fused.c l.963-975), so plain cp, creat() and O_CREAT fail. write()
  past i_size returns ENOSPC (ext_map.c fuse_ext_map_write_iter), and
  truncate and hole punch are refused on S_DAX inodes (commit f6593d899494).
  The GGUF (396705472 bytes) gets 190 units = 380 MiB. Its i_size is the
  exact byte length, so llama.cpp's fseek(SEEK_END) gives the true size
  (the devdax problem in 02-findings 1 goes away). One contiguous
  allocation is one extent, which is the O(1) lookup case.
4.3 Mounting other hosts: `famfs mount /dev/daxN.M /mnt/famfs` (fuse mode is
  chosen automatically, or with -f). It validates the superblock and log,
  makes a shadow tree in /tmp/famfs_shadow_XXXXXX (tmpfs YAML per file),
  starts famfs_fused (which does the kernel mount), and replays the log
  (markdown/famfs-fuse-design-notes.md "famfs mount" steps 1-6). Files
  created later by the master become visible only after `famfs logplay
  /mnt/famfs`. Client files have mode 0444, the master's 0644
  (famfs_lib.c l.1635). Coherence rule: famfs keeps its own metadata
  coherent, with cache flush/invalidate around superblock and log access,
  but not file data. The writer must finish (famfs cp returns) before
  readers mount or replay the log; on hardware that is not cache-coherent,
  `famfs flush` is also needed. In qemu the shared backing is host RAM and
  coherent.
4.4 read() and fread: fuse_file_read_iter -> fuse_passthrough_read_iter ->
  fuse_ext_map_read_iter -> dax_iomap_rw (ext_map.c l.276-295;
  passthrough.c l.51). This is a memcpy from the dax memory, with no
  daemon round trip, so llama.cpp's fread of the GGUF header works.
4.5 mmap: fuse_ext_map_mmap sets fuse_ext_map_vm_ops and VM_HUGEPAGE
  (ext_map.c l.315-320). .huge_fault -> dax_iomap_fault(order), so PMD
  faults are possible (CONFIG_FS_DAX_PMD=y, 2 MiB-aligned extents; famfs
  smoke test c184b1c checks PMD population). The pages are fsdev_dax's
  MEMORY_DEVICE_FS_DAX pages inside the CXL window (fsdev.c probe:
  devm_memremap_pages of the dev_dax ranges), so pagemap and
  /proc/iomem frame checks work as they do with devdax. MAP_POPULATE
  pre-faults without copying. The inode is S_DAX: no page cache at all, and
  famfs and FUSE offer no option to turn one on. A cached mode would need
  something else (erofs/ext4 on pmem, research FS).
4.6 After the mount, the daemon answers LOOKUP, GETATTR, READDIR and OPEN
  from the shadow tree. On the first OPEN of an inode it pushes the extent
  map with FUSE_NOTIFY_BACKING_MAP, keyed by a 64-bit backing id
  (famfs_fused_extmap.c l.140-235). The dax device itself is registered
  once with fuse_passthrough_v2_open(fd). After that, data access never
  goes to the daemon. If famfs_fused dies, the connection aborts: new
  lookups and opens fail (ENOTCONN). Already-open files and existing
  mappings should keep working, because the inode holds its fuse_backing
  (inode.c l.178) and the backings are freed only when the connection is
  destroyed at unmount (fuse_backing_files_free, inode.c l.1039). The
  read and fault paths check only fuse_is_bad(inode) and dax_error. This is
  from source and not measured, so it is an experiment in 6.3. The daemon
  must outlive the readers, which makes it node-level state (systemd unit
  or host process). It cannot live in a pod that may restart.
4.7 One mount, many containers: famfs mount passes allow_other and
  default_permissions by default (famfs_cli.c l.278-279 useraccess=1,
  default_perm=1; famfs_mount.c l.654-675), and client files are 0444, so
  any container uid can read. A bind mount of the node mount (CDI mount or
  hostPath with "ro") shares the same superblock and FUSE connection, which
  is ordinary VFS. The kernel enforces MNT_READONLY on each bind mount, and
  containers need neither /dev/fuse nor privileges. I found no FUSE
  restriction on bind mounts across mount namespaces. The known FUSE
  container problems are about running the daemon inside a userns, which
  we do not do. The node mount must exist before the container starts, or
  be propagated with rslave/HostToContainer.
  One mount per dax device per host: the FUSE backing takes the dax holder
  with fs_dax_get(daxdev, fb, &fuse_dax_holder_ops) (backing.c l.169), and
  the holder is exclusive. A second famfs mount of the same daxdev on a
  host fails, and while fsdev_dax is bound no process on that host can use
  the raw /dev/daxN.M (no mmap). On a host, famfs and the current direct
  dax mode exclude each other per device. Other hosts are independent:
  each binds its own view.
4.8 Which devdax: fsdev_dax binds to any dev_dax via daxctl
  (reconfigure-device works on regions from cxl create-region in ram mode,
  i.e. daxN.0) and handles multi-range devices. dev_dax->nr_range loop,
  multi-range offsets fixed in e0cb40c3c676 (v7.3-rc1), so a slice daxN.M
  of a dynamic region should work too. Research B measured the binding of
  dax2.0. A slice is a prototype check (6.3 step 9). Size: 512 MiB holds
  the superblock (2 MiB) + log (8 MiB) + 380 MiB model.

5. Effort and risks
-------------------
Effort (VM time, no host builds):
- Kernel: none to port. Merge fuse/for-next into a v7.3-rc4 checkout, or
  apply the saved diff. Same config plus LOCALVERSION. One binrpm-pkg
  build, cached like today's kernels (custom-kernel.yaml can take an
  arbitrary kernel_getsource command).
- Userspace: dnf install of about 15 -devel packages, then `make release`
  in a famfs checkout (it clones 6 repos and builds ndctl, libfuse
  (meson) and famfs (cmake)). Tens of minutes. Tar the release/ outputs
  and cache them on the host.
- Integration (later streams): node-level famfs mount and daemon life
  cycle in the driver, fsdev_dax binding per host, famfs cp in the writer
  step, CDI bind mounts to readers. With direct mmap through a regular
  file, test16 loses cxl-llm and the dax-mapping hacks, and readers run
  stock llama.cpp.
Risks:
- R1 Not merged yet: the FUSE uapi (7.47) could still change before or
  during the v7.4 merge, or the series could slip to v7.5. Pin the
  kernel to fuse for-next 4dd8d3967401 and libfuse a6e314173360 together,
  since famfs_fused refuses mismatched pairs (630f9b0). Move to vanilla
  v7.4-rc1 when it lands.
- R2 Userspace has no upstream home besides Micron's repo: no releases,
  a forked libfuse (until famfs support lands in libfuse), build-time
  clones from personal GitHub repos (jagalactic). Pin every commit.
  Installing the fork's libfuse3.so must not replace Fedora's fuse3-libs:
  run famfs_fused from its build directory or set an rpath.
- R3 Brand-new kernel code (v5 posted 2026-10-16, kernel test robot and
  sashiko still reporting on v3/v4). Expect bugs. A crash in a VM costs a
  VM reboot.
- R4 The daemon is a single point of failure for new opens, and there is
  one mount per daxdev per host. This forces a node-level design, and it
  conflicts with raw devdax use of the same device on that host.
- R5 No cached mode: if a page-cache variant is still wanted, famfs cannot
  give it.
- R6 Real-hardware coherence (famfs flush) does not show up in qemu.

6. Verdict and prototyping recipe
---------------------------------
Verdict: GO, for a time-boxed prototype. Fail-fast checks:
- Maintained: yes (135 commits in 2026, Micron plus the FUSE maintainer).
- Going seriously upstream: yes. The dax half has been in mainline since
  v7.1. The FUSE half is written by the FUSE maintainer and has been in
  fuse.git for-next and linux-next since 2026-10-16, with reviews and no
  open objection.
- Too much hacking on up-to-date vanilla: no. A clean merge of an
  upstream maintainer branch, no config change. The userspace fork of
  libfuse is the only non-upstream piece.
- FUSE problems with ro bind mounts into several containers: none
  expected from source (4.7). Prove it in step 7 below, and return NO-GO
  if it fails.
Stop and fall back to erofs (research FS/P1) if any of steps 4-8 fails in a
way that needs kernel changes beyond fuse/for-next.

6.1 Kernel (in VM1, then install the RPMs on both VMs):
  git clone --depth 1 -b v7.3-rc4 \
    https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git linux
  cd linux && patch -p1 < fuse-for-next-4dd8d3967401-on-v7.3-rc4.diff
  (copy the diff from the FA scratch; check its sha256 first. The
  alternative is a full clone of fuse.git, checkout 4dd8d3967401, which is
  v7.3-rc1 based.)
  cp qemu-cxl-kernel.config .config; set CONFIG_LOCALVERSION="-famfs";
  make olddefconfig; check that grep shows FUSE_PASSTHROUGH=y FS_DAX=y
  FS_DAX_PMD=y DEV_DAX_FSDEV=y FUSE_VDAX=y; make -j$(nproc) binrpm-pkg
  (the same steps as custom-kernel-fedora.yaml). Cache
  kernel-pkgs.tar on the host. Boot both VMs. Check: grep -w
  fuse_backing_is_dax /proc/kallsyms.
6.2 Userspace (in VM1; cache the result on the host, then install on both):
  dnf install -y git gcc gcc-c++ make cmake meson ninja-build libuuid-devel \
    libyaml-devel zlib-devel libcurl-devel daxctl daxctl-devel kmod-devel \
    json-c-devel libtraceevent-devel libtracefs-devel keyutils-libs-devel \

  git clone -b famfs.extmap https://github.com/jagalactic/libfuse famfs/libfuse
  (pin a6e314173360); make release. Record the commits of ndctl, mongoose,

  --fuse-abi prints extmap. Tar release/ (binaries + libfuse/lib/
  libfuse3.so*) to the host cache. Install it under /opt/famfs-bin on both
  VMs.
6.3 Experiments (two VMs, three readers, stock llama.cpp):
  1. Shared device as today (cxl-pool-shared, 512Mi, daxN.0 on both VMs).
     On both: daxctl reconfigure-device --mode=famfs daxN.0; daxctl
     list shows mode famfs.
  2. VM1 (master): mkfs.famfs /dev/daxN.0; famfs mount /dev/daxN.0
     /mnt/famfs; famfs cp Qwen3-0.6B-Q4_K_M.gguf /mnt/famfs/; sha256sum
     /mnt/famfs/Qwen3-0.6B-Q4_K_M.gguf equals ac2d9771...; check that
     cp /etc/hosts /mnt/famfs/x fails (ENOTSUP), to document the writer
     rule.
  3. VM2 (client): famfs mount /dev/daxN.0 /mnt/famfs; ls -l shows the
     GGUF with mode 0444 and the exact size; sha256sum matches;
     touch/echo > fails.
  4. read path: python3 -c 'open(p,"rb").read(64)' and dd bs=1M of the
     whole file on VM2: no growth of FilePages in /proc/meminfo, no
     growth of the reader cgroup's memory.stat file.
  5. mmap path: llama-cli/llama-simple (stock build, repacking off as in
     02-findings) -m /mnt/famfs/...gguf on VM2 answers "Hello! How can I
     assist you today?". Frame proof: /usr/local/bin/cxl-where.py (or
     /proc/PID/pagemap of the model VMA as root) shows every frame inside
     the "CXL Window" of /proc/iomem. Node FilePages grows < 5% of the
     model. PMD faults: the fs_dax tracepoint dax_pmd_fault_done
     (tracefs events/fs_dax) fires for the model VMA with result NOPAGE,
     not FALLBACK. A
     canary byte changed by the master (famfs cp of a small file
     overwritten via mmap on VM1) is seen by VM2 at once.
  6. Containers: on VM2 create two pods and on VM1 one pod, all hostPath
     /mnt/famfs readOnly (later CDI mounts), non-root uid, no privileges.
     Run stock llama.cpp in all three at the same time: same answer, frames
     in the CXL window, node FilePages stays flat. Check mountinfo in the
     container: fuse.famfs, ro.
  7. Bind-mount robustness: a container started before the node mount sees
     nothing without propagation, so document the ordering. Umount while
     a reader runs gives EBUSY. Remount after an unmount and logplay.
  8. Daemon death: kill -9 famfs_fused on VM2 while a reader runs. The
     running llama.cpp keeps generating, a new open gives ENOTCONN, and
     fusermount -u -z plus remount recovers. Record dmesg.
  9. Slices: repeat 1-3 with a daxN.M slice of a dynamic dax region and
     with two famfs filesystems on two slices at once.
  10. Unwind: famfs umount (fusermount -u), daxctl reconfigure-device
     --mode=devdax, then the old direct test (cxl-llm) still reads the
     same bytes. No leftovers.
  Write the results to 12-proto-famfs.txt in the plan directory.
