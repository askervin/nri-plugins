0. Short answers

(phase B ran 2026-10-17 10:33-11:25 local; details in section 3)
- Verdict: conditional GO. famfs works end to end in both VMs: a 4 GiB
  shared device, the master on VM1, a client on VM2, and three non-root
  pods running stock llama.cpp at the same time. It does NOT work on
  unmodified fuse/for-next 4dd8d3967401, and that is still the for-next
  tip on 2026-10-17. Any posix_fadvise() on a famfs file oopses the
  kernel: a NULL backing file in fuse_passthrough_fadvise. Stock
  llama.cpp always calls posix_fadvise(SEQUENTIAL) before it maps the
  model (llama-mmap.cpp l.530), and so does sha256sum. A 1-line fix
  (kernel/fix-fadvise-extmap.patch) makes it work. That is a bug fix for
  an upstream branch, not a port, so the "too much hacking" rule is not
  hit. Still, it shows that the unmerged code is not ready yet. FUSE has
  no problem with read-only bind mounts of one node mount into many
  containers (NO-GO rule 2 not hit).
- Kernel: 7.3.0-rc4-famfs2 = P1's fsexp config + KALLSYMS + FTRACE event
  tracing + the FA diff + the fadvise fix. binrpm-pkg built in 267 s
  (the first build) and 72 s (incremental). The kernel has
  fuse_backing_is_dax in kallsyms, the fsdev_dax driver,
  events/fs_dax, and still EROFS.

3.4 Crash 1 and 2 (VM1, kernel -famfs). sha256sum of the model through
  the mount oopsed the kernel: panic_on_oops=1, reboot after 10 s. The
  first time the oops was lost with the journal; the second time it was
  caught on the serial console (host/serial-log.py,
  logs/serial-vm1-oops1.txt):
    BUG: kernel NULL pointer dereference, address: 0000000000000008
    CPU: 6 UID: 1000 PID: 1563 Comm: sha256sum
    RIP: 0010:vfs_fadvise+0x4/0x20
    Call Trace: fuse_passthrough_fadvise+0x32/0x40, __x64_sys_fadvise64
  The cause: fuse/for-next has both fadvise passthrough
  (fuse_file_fadvise -> fuse_passthrough_fadvise) and extent maps. For
  extent-map files ff->passthrough and ff->cred are NULL. read_iter,
  write_iter, splice and mmap check this; fadvise does not. Any user
  who can open a famfs file can crash the host. The fix (P2/kernel/
  fix-fadvise-extmap.patch, 1 line in fs/fuse/file.c): use the
  passthrough path only if ff->passthrough is set, else
  generic_fadvise, which for DAX inodes accepts the advice and does
  nothing. Rebuilt as -famfs2 (72 s), installed with --oldpackage on
  both VMs, rebooted.
  After every reboot the guests did not see the memdev again. A qemu
  re-plug (device_del/device_add, safe with no region in the guest)
  fixed it, as P1 saw.
  With the fix, sha256sum through the mount works on both VMs (0.5 s,
  correct hash).
3.5 Measurements (logs/: vm2-readpath.txt, pods-where.txt,
  vm2-daemon-kill.txt, vm2-umount.txt), summarised in 0. Short answers.
  Bind-mount detail: in the containers the mount is
  "/models ro,relatime - fuse /dev/dax1.0 rw,user_id=0,...,allow_other".
  The per-mount ro comes from the CRI bind; the superblock stays rw.
  The propagated submount (HostToContainer) has no per-mount ro:
  "/models/famfs rw,nosuid,nodev,relatime master:283". It was protected
  only by file mode 0644 root:root against uid 1000 (Permission denied).
3.6 What the driver must do (famfs in 11-research-IN 4.2), beyond FA:
  - the kernel fix above;
  - pool devices >= 4 GiB, or a 1-line famfs patch;
  - famfs mount -f;
  - after mounting a reader's node mount, "mount -o remount,bind,ro".
    Otherwise a client root, or a root container through a propagated
    mount, can write the shared model in place;
  - one famfs_fused per device per node that outlives the readers. Its
    death breaks only new opens; recovery needs all readers stopped
    first;
  - order: the node mount exists before the containers start, or use
    HostToContainer on a parent directory;
  - never a second famfs mount of the same device on a node while
    container bind mounts of the old one exist (it hangs for 45 s, then
    fails).
