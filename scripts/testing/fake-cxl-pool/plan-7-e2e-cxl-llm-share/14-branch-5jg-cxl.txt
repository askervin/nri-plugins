3. How the driver is built, deployed and tested now
---------------------------------------------------
- Build: the image, like any other plugin,
    make PLUGINS=nri-dra-driver-cxl SKIP_LICENSES=1 OTHER_IMAGE_TARGETS= BINARIES= images
  (build/images/nri-dra-driver-cxl-image-<id>.tar). Tests do not build
  the driver: dra-build builds only fake-cxl-pool. No go.mod replace, no
  pseudo-version of nri-plugins, no second repository to commit to (the
  "for the user: commit the driver's go.mod" item of
  05-status-orchestrator is void).
- Image: gcr.io/distroless/static with /bin/nri-dra-driver-cxl,
  /bin/cxl-request and cxl and daxctl of ndctl v85 with their libraries
  (cmd/plugins/dra-driver-cxl/Dockerfile). No ndctl, no shell, no
  mount/losetup tools.
- Deployment: a DaemonSet of the chart, privileged, hostPID, hostPath
  mounts of /var/lib/kubelet/plugins, plugins_registry, /etc/cdi,
  /var/run/cdi, /var/run/nri, /sys, /dev, /lib/modules; NODE_NAME from the
  pod. The e2e installs it with helm-launch through dra-install (on every
  node of the cluster; e2e values E/dra-driver-cxl.helm-values.yaml); the
  driver's log is kubectl logs of its pod on a node (dra-plugin-log).
  fake-cxl-pool-controller still runs on VM2 as a transient systemd unit.
- Cluster: n4-cxl-shared-2/test00-up makes the two VMs one cluster (VM2
  control plane, VM1 worker); every other test only checks it with
  pool-cluster-require. Run order: n4-cxl-shared-1/test00-up,
  n4-cxl-shared-2/test00-up, then any test. D11 of 03-decisions is now
  the rule of the whole suite; vm-k8s-reinit and k8s_restore appear only
  in test00-up.

4. What this changes for the erofs/famfs work (13-fs-findings, 11-IN)
---------------------------------------------------------------------
Superseded statements:
- 11-IN 0 and 1.3 ("the plugin image is FROM scratch, no cxl, daxctl or
  ndctl, so pool devices need the host-process plugin"): the plugin is a
  container with cxl and daxctl; there is no host-process plugin.
- 11-IN 7 risk 8 (memctl and the go.mod replace): gone.
- 11-IN 4.1 "ndctl joins the VM tools": for pmem it must join the image
  (ndctl create-namespace for the writer's fsdax namespace), or memctl
  does that step through sysfs.
New consequences of a containerized driver, to design for:
- Mounts made by the driver must reach the host's mount namespace,
  because containerd/runc resolve CDI mounts there. The chart's
  /var/lib/kubelet/plugins volume has no mountPropagation today: the node
  mounts (erofs per device and access, famfs per device) and the lease
  mount points (11-IN 3.1, propagated into running containers with
  rslave) need mountPropagation: Bidirectional on the volume that holds
  them (allowed for privileged containers; kubelet makes /var/lib/kubelet
  rshared). Mounting itself is a syscall (golang.org/x/sys/unix Mount,
  the loop ioctls for the "both modes on one node" case of 12-P1 3.5): no
  tools needed in the image for erofs.
- The driver pod is restarted on upgrades and crashes. Kernel mounts
  (erofs) survive that and are found again from the plugin state; the
  restart must not unmount anything that containers use (12-P1 6: never
  lazy-unmount, never release a region under a live superblock).
- famfs: its FUSE daemon would run in the driver pod (needs /dev/fuse,
  present through the /dev mount, and famfs userspace with the forked
  libfuse in the image). A driver restart kills the daemon: existing
  mappings keep working, new opens get ENOTCONN (12-P2), and the device
  cannot be mounted again while containers keep the old superblock (one
  famfs mount per device per host). A daemon that outlives the driver pod
  needs its own pod or a host unit. This weighs against famfs beyond what
  13-fs-findings section 3 says.
Unchanged: the API proposal of 11-IN 2 (modes block and fs, fsType,
access, path, PATH env), the lease mount through propagation, the stock
llama.cpp reader, the shape of the new test16 (11-IN 6), the kernel facts
and prototypes (11-FA, 11-FS, 12-P1, 12-P2, 13).
