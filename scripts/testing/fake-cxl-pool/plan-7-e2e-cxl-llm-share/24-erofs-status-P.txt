1. What T relies on (exact names)
---------------------------------
Server config (DeviceConfig) key:    persistent: true      (default false)
POST /api/v1/devices (DeviceCreate): "persistent": true    (default false)
Client:                              create ... --persistent
api.Device JSON:                     "persistent": <bool>  (always present)
                                     "lsaPath": "<file>"   (persistent only;
                                                            omitted otherwise)
LSA file name rule (pool.LSAPath):   the data path with its extension
  replaced by ".lsa": <pool dir>/llm0.raw -> <pool dir>/llm0.lsa; a data
  file without extension gets ".lsa" appended (/x/llm0 -> /x/llm0.lsa).
  Size 262144 bytes (256 KiB, sparse, all zeros when new). Created exactly
  when the data file is (server start for config devices, create over the
  API, state load, every attach if missing); removed exactly when the data
  file is (DELETE of a device created over the API, only if the data file
  is in the pool directory). Config devices keep both files, as before.
qemu ids of an attach of device D on a host (counter N, as today):
  data backend      fcp_D.hpN       memory-backend-file, mem-path=<data>,
                                    size=<device size>, share=on
  LSA backend       fcp_D.hpN-lsa   memory-backend-file, mem-path=<lsa>,
                                    size=262144, share=on
  cxl-type3 device  fcp_D.hpN       persistent-memdev=fcp_D.hpN,
                                    lsa=fcp_D.hpN-lsa, sn=<serial>
                                    (no volatile-memdev)
  The attachment's qemuDeviceId and qemuObjectId are fcp_D.hpN as for
  volatile devices; the attachment JSON also has "qemuLsaObjectId":
  "fcp_D.hpN-lsa" for persistent devices (omitted for volatile ones; see
  Review fixes).
HMP commands, in order (QMP: the same arguments as object-add/device_add/
device_del/object-del JSON):
  object_add memory-backend-file,id=fcp_llm0.hp1,size=536870912,share=on,mem-path=<pool>/llm0.raw
  object_add memory-backend-file,id=fcp_llm0.hp1-lsa,size=262144,share=on,mem-path=<pool>/llm0.lsa
  device_add cxl-type3,bus=<slot>,persistent-memdev=fcp_llm0.hp1,lsa=fcp_llm0.hp1-lsa,id=fcp_llm0.hp1,sn=0xc1ae0001
  detach: device_del fcp_llm0.hp1, then (qemu deleted it, nothing mapped)
          object_del fcp_llm0.hp1, object_del fcp_llm0.hp1-lsa
  failed device_add: object_del fcp_llm0.hp1, object_del fcp_llm0.hp1-lsa
  failed object_add of the LSA: object_del fcp_llm0.hp1
Every qemu that attaches the device maps the same two files (the same
mem-paths in every VM), so the labels in the LSA are shared.
ResourceSlice attribute (controller):  persistent (bool) on EVERY published
  device, false for volatile devices (CEL: device.attributes["cxl-pool.nri.io"].persistent).
Claim status data (claim.status.devices[].data):  "persistent": true for a
  persistent device, the key omitted for volatile devices; next to
  "serial", "shared", "size", "exclusive" (also "host", "hostUUID",
  "attachment", "qemuDeviceId" as before).
Client table columns: NAME SERIAL SIZE SHARED PERSISTENT SCOPE STATE
  ATTACHED-TO OWNER (columns 1-4 unchanged; SCOPE and later moved one to
  the right). "devices NAME" adds the lines "memory:   persistent|volatile"
  and, for persistent devices, "lsa:      <file>".

4. Deviations from 22 and additions, with reasons
-------------------------------------------------
- api.Attachment has "qemuLsaObjectId" (omitempty), added by review fix
  R5; for attachments made by the server it equals qemuObjectId + "-lsa".
- A persistent device whose data file a VM pre-declares on its command line
  (befile_ binding) cannot be attached (InvalidArgument "... has no label
  storage area"): such a backend has no LSA, and an LSA added next to it
  would not be the command line's. Not used by test16.
- Validation added (not in 22): a persistent config device whose data file
  has the extension .lsa (its LSA would be the data file), or whose LSA is
  a file of another config device, is a config error; a persistent device
  created over the API whose files clash with another device's is a 409.
- Client "devices NAME" shows "memory: persistent|volatile" instead of a
  "persistent:" line: a longer key would change the column alignment of the
  whole detail output, which an existing test (and possibly scripts)
  match.
- Client create --persistent added (22 lists only the table and JSON).
- The "lsa property must be set" and "can't find value" texts of the fake
  follow qemu's (hw/mem/cxl_type3.c, qdev link properties).
- TestPublish's expected attribute set changed (persistent added), as the
  contract changed.
