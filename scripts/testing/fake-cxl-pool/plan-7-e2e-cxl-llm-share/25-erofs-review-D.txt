Bugs (must fix)
---------------

B1 D/pool_persistent.go:345-386 (releaseDevices), D/pool.go:366 (fail ->
   rollback), D/pool.go:587-590 (prepareDevice returns nil dev on error)
   Rollback of a failed persistent Prepare releases the region of the
   device that failed without the holder wait. releaseDevices fills
   blockDevs only from devs (pc.Devices = the devices already prepared);
   the device whose preparePersistent failed is only in `touched`, so its
   serial goes straight to p.release (cxl disable-region, destroy-region,
   disable-memdev). This breaks the rule of 22 section 5 ("only when
   nothing holds the block device any more", 21 F10). Status D 4 even says
   "Rollback of a failed Prepare does the same", which it does not.
   Failure scenario (T14, the case T14 exists for): someone mounted
   /dev/pmem1 by hand on the node with dax=never (or any other non-plugin
   user holds it). A direct fs claim is the only claim of the device on
   the node: the plugin's mount gets the foreign superblock, T14 fires,
   the plugin unmounts its own mount, and rollback destroys the region
   under the foreign mount (the erofs of the other user loses its block
   device; with a live DAX mapping this is the oops of F10). Same when
   the T14 unmount itself fails (pool_persistent.go:243-249 logs and
   keeps the mount) or loop.Release(true) fails on T13 cached
   (pool_persistent.go:260-262): the plugin's own mount or loop is left
   and the region is destroyed under it.
   Fix: give rollback the block device of the failing device too, e.g.
   prepareDevice returns the partly filled dev with the error (or
   preparePersistent records serial -> BlockDevice in a map that
   prepareClaim passes to rollback), and releaseDevices runs waitNoHolder
   for every serial with a known block device; on "still in use" the
   region stays (logged), as in Unprepare. Add a test: T14 with a foreign
   holder (fakeMounter.holders) must not run disable-region.


Should fix
----------

R1 D/pool_persistent.go:216-228 (ensureNodeMount, existing mount)
   An existing mount at the node mount path is reused after checking only
   FsType == erofs: not its source (/dev/pmemK for direct, a loop over
   /dev/pmemK for cached) and, for direct, not dax=always. Scenario: the
   T14 path fails to unmount (only logged, line 244-245) and leaves a
   non-DAX erofs at mounts/c1ae0001-direct; the next direct claim on the
   node reuses it silently, and the reader gets page-cache access while
   the claim says direct (test16 D/C proofs would catch it, a user would
   not). Same in restoreMounts (it calls ensureNodeMount). Fix: on reuse,
   for direct require mi.Source == blockDev and hasSuperOpt(daxAlways)
   (else T14), for cached require the loop's backing_file to be blockDev;
   else fail with "<mnt> is a mount of <source>".

R2 D/pool_persistent.go:391-421 (restoreMounts) with D5
   At start, a prepared fs device whose node mount is missing is mounted
   from the recorded d.BlockDevice without checking that /dev/pmemK is
   still the namespace of that device. After a node reboot (the state file
   under /var/lib/kubelet/plugins survives, the regions do not), pmemK may
   be another device: a local NVDIMM/memmap pmem, or another persistent
   device whose region was created first. Scenario: two persistent devices
   A (pmem0) and B (pmem1) prepared; reboot; B's region comes back first as
   pmem0 (or a platform pmem0 exists): restoreMounts mounts B's (or a
   foreign) erofs at mounts/<A>-direct and the restarted pods of A read B's
   data. Fix: before re-mounting, check that d.BlockDevice still belongs to
   d.Namespace of d.NdRegion of the memdev with d.Serial (e.g.
   /sys/class/block/pmemK resolves under bus/nd/devices/<ndRegion> and its
   dev is BlockMajor:BlockMinor, and FindMemdev(serial) has d.Region), else
   log and skip. (D5 accepted that the region is not re-created; this is
   only about not mounting the wrong device.)

R3 D/pool_persistent.go:318-338 (waitNoHolder) under D/pool.go:646-647
   (UnprepareResourceClaims holds p.mu)
   The holder wait (up to 10 s per serial, in turn per serial of the
   claim, and per claim of the batch) runs with p.mu held, so every
   Prepare and Unprepare of the pool driver on the node waits behind it.
   The old code also held p.mu over release and over the memdev wait, so
   this is the existing pattern, but the new wait is the one that is
   expected to time out (a lingering container bind): a pod with N
   persistent devices on a node with a stuck holder blocks the node's pool
   claims for N x 10 s per kubelet retry, and N x 10 s may exceed
   kubelet's DRA call timeout (45 s, if I remember kubelet's
   draplugin default right), so the retries never finish. Fix (cheap):
   one shared deadline for all serials of a releaseDevices call; or
   (better) wait without p.mu: mark the serial "releasing" (like inflight),
   unlock, wait, relock and re-check preparedDevice before p.release.

R4 Tests, D/pool_persistent_test.go
   Error paths and the life cycle are covered well for single-device
   claims (T1-T14 texts and order, shared mount table, EBUSY, holder,
   restart). Missing:
   - rollback of a claim whose first result mounted (and/or shares a
     mount with another claim) and whose second result fails: the first
     mount must go, the shared one must stay;
   - the B1 case (failing device with a holder: no disable-region);
   - the T14 unmount failure and the T13 loop-detach failure;
   - ensureNodeMount over an existing non-erofs mount and (with R1) a
     wrong-source mount;
   - restoreMounts when the re-mount fails (block device gone): logged,
     state unchanged, mount dir removed;
   - waitNoHolder with ctx cancelled and with a Holder error;
   - p.sync failure after a persistent Prepare (rollback unmounts).
   sysMounter.Holder's backing_file matching (mount.go:241-251) is pure
   sysfs reading and testable with a temp sysRoot and a missing device
   (ENOENT -> ""); only the O_EXCL/LOOP_* syscalls need root.

R5 P/pkg/server/server.go:1144-1150 (finalizeDetach)
   The LSA backend is object-deleted only if s.devices[a.Device] still
   exists and is persistent, and its id is derived as objID+"-lsa", not
   taken from what was plugged. An adopted attachment whose tree LSA id is
   different (another server version, a hand hotplug with an fcp_ data
   id) leaves its LSA backend mapped in qemu; a device removed from the
   map before finalize (config reload) leaves it too. Not hit by test16.
   Fix: record the LSA object id in the attachment (unexported field, or
   from t3.LSA at adoption) and delete what was recorded.
