R (should fix)

R1 T16:145, T16:508, T16:513, T16:514-515, T16:516: the "nothing left"
   checks of E (and the region check of llm0-free) ignore whether their
   probe command worked. Each one tests only that the output is empty, or
   pipes into grep:
     145  pool-vm-command "$vm" "ls ... | grep '^region[0-9]'" && error ...
     508  left=$(dra-vm-command-q ... "kubectl get pods,resourceclaims ... 2>/dev/null")
     513  [ -z "$(dra-pmem-loops "$vm")" ]
     514  [ -z "$(dra-cdi-devices-with "$vm" "CXL_${LLM_HEX}_")" ]
     516  pool-vm-monitor "$vm" "info qtree -b" | grep -q 'dev: cxl-type3' && error
   How it misleads: an ssh failure, a kubectl error (apiserver briefly
   unavailable, a stray kubeconfig) or an unreadable monitor gives empty
   output, and the test prints "no pods, claims, mounts, loop devices, CDI
   devices, memory devices or regions of llm0 left" without having looked.
   (145 is covered by cxl-assert 'regions == []' just before it, so it is
   the mildest.) Fix: capture output and status separately and fail on a
   non-zero status, e.g.
     out=$(dra-pmem-loops "$vm") || error "cannot list the loop devices of ..."
     [ -z "$out" ] || error "... still has loop devices over pmem: $out"
   and the same for 508 (no 2>/dev/null, check the status), 514 (the awk
   loop: return 1 if neither /etc/cdi nor /var/run/cdi was readable), 516
   (qtree=$(pool-vm-monitor ...) || error; then grep the variable). The
   helpers dra-pmem-loops and dra-cdi-devices-with should return the
   status of the remote command, which dra-vm-command-q already gives.

R2 DRA:959-973 (dra-fs-mounts): a findmnt line that does not split into
   exactly 7 fields is dropped silently (if len(fields) == len(keys)).
   C and D are safe (mounts-assert compares the exact target list, so a
   dropped mount fails), but E (T16:511-512) only checks that the list is
   "[]": a mount under the mounts directory whose line does not parse (an
   empty FS-OPTIONS column, which "read -r t s f o" collapses, or a future
   column change) makes E pass with the mount still there. Fix: in the
   Python part, exit non-zero on any line with another field count
   (sys.exit("dra-fs-mounts: cannot parse: %r" % line)), so the caller's
   "|| error" fires; also print "-" for an empty FS-OPTIONS in the remote
   snippet (o=${o:--}).

R3 T16:374 (the EXIT trap dra-cleanup; pool-cleanup) on a failure where
   the driver could not unprepare: dra-uninstall waits 60 s for the claims
   and then goes on, and pool-cleanup (S/pool.source.sh:382-417) runs
   "fake-cxl-pool-client guest release" (cxl disable-region,
   destroy-region, disable-memdev) and then detaches the device in qemu,
   without looking at erofs mounts or loop devices over /dev/pmemK. That
   is exactly the state the driver's holder wait refuses to release (21
   F10: a region released under a live erofs/DAX user can oops the guest),
   and the plan rule "never device_del a CXL device that a guest still
   uses". With volatile devices nothing on the node could hold the device
   once the pods were gone; with mode fs a node mount or a container bind
   can. How it fails: a run that fails in C or D with an Unprepare stuck at
   "unmounting ...: device or resource busy" or "/dev/pmemK is still in
   use" ends in a guest oops or a hung VM, and the next run pays a VM
   restart or worse. Fix (test16 only, no helper change needed): put a
   function in the trap between dra-cleanup and pool-cleanup that runs
   dra-fs-mounts and dra-pmem-loops on both VMs and, if either shows
   something, says so and restarts that VM (pool-vm-restart, as
   pool-vm-reset does) instead of letting pool-cleanup release the device
   under it; or, more conservatively, skip pool-cleanup's release for llm0
   and leave the VMs for debugging with a clear message (the
   run-e2e-tests skill already says failed tests leave state behind). A
   rerun is then safe anyway: pool-vm-reset at T16:335-336 restarts a VM
   that still has CXL devices before anything else.

R4 T16:398-407 (A, "cxl-pool-shared does not match llm0"): the proof is
   "the pod is Unschedulable within 60 s and its claim has no allocation".
   Unschedulable has many causes; the log shows the scheduler's message
   (T16:405 prints it: "0/2 nodes are available: 1 cannot allocate all
   claims, 1 node(s) didn't match Pod's node affinity/selector") but the
   test does not assert it. How it misleads: if VM2 is momentarily
   NotReady or tainted (the cluster was just rebuilt by test00-up; the
   message would then be "1 node(s) had untolerated taint ..."), the pod is
   Unschedulable although the class would match, and A passes. Fix: assert
   the PodScheduled message of the same JSON in the dra-wait expression,
   e.g. "... and 'cannot allocate all claims' in c.get('message', '')".
