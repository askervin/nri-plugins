Bugs (must fix)
---------------
B1  D/local.go:438 (sharedDevice -> createRegion), no zeroing of a newly
    created shared region.
    Problem: the content of a shared device is "never zeroed" (03 D3), but
    the region a first shared claim creates is new: its bytes are whatever
    the previous users of the physical memory left. The sliced allocator
    zeroes a dax slice when it gives it out (local.go:626) and never when
    it takes it back, and numa slices are system RAM whose frames keep
    their content after offlining (the kernel clears pages on allocation,
    not on free or offline). So the first shared claim reads what earlier
    tenants left: the guarantee of zeroSlice ("a claim never sees what an
    earlier one left there") breaks at the sliced -> shared switch, and
    after a reboot (the state of another boot is dropped; RAM-backed CXL
    memory and qemu memory-backend-ram keep their content across a warm
    or guest reboot).
    Failure: mem1 is sliced; claim A gets a numa slice, the kernel puts
    page cache and anonymous memory of arbitrary node processes there;
    A goes, the region is released. The admin adds mem1 to
    sharedDevices and restarts the plugin (03 section 7 "device joins
    sharedDevices"). A reader claim (shares: "1", readOnly) creates the
    region and mmaps /dev/dax0.0: it reads those pages. Same with dax
    slices (the last tenant's bytes) and after a reboot of the node.
    Fix: in sharedDevice, after createRegion succeeds for a NEW region
    (not for a kept one), bind dax0.0 to device_dax, read its numbers and
    a.zero(major, minor, size, align) the whole device before returning;
    on failure dropUnused as for the other creation errors. This keeps D4
    (content kept while the region exists) and Q4 (no zeroing when idle):
    the bytes are zeroed once, before anybody can map them. Log it like
    zeroSlice ("zeroed dax0.0 in <t>"); it runs under a.mu (1 GiB is well
    under a second; document that big devices make the first claim slow).
    TestLocalSharedClaims then expects one zeroing at creation and none
    for later claims or reuse. Contract wording: 03 D3/section 5 step 2
    "never zeroed" -> "zeroed once when its region is created, never
    while it exists" (an orchestrator/user decision, a Request to DOCS).

R2  D/node_state.go:1268-1275 (prepareLocalMemdev, sliced path) accepts an
    allocation result of the shared shape.
    Problem: both shapes are named memdev-<serial>. The guard refuses a
    result without shares on a shared device, but nothing refuses a result
    WITH shares on a sliced device: it gets size = the whole usable size
    (no memory consumed), and the scheduler, which counted shares and no
    memory, keeps allocating the memory capacity to other claims.
    Failure: a claim is allocated memdev-c100e2e1 (shared, consumed shares
    1M), the admin removes the serial from sharedDevices and restarts the
    plugin before kubelet prepares it (03 section 7 calls this a stale
    allocation). The device is idle, published sliced; the stale claim
    takes the whole device as a numa slice; the next cxl-local claims fail
    at Prepare with errNoRoom until it is gone.
    Fix: in prepareLocalMemdev, when !dev.Shared and r.ConsumedCapacity
    has device.CapacityShares, fail with e.g. "device 0x<serial>: allocated
    as a shared device, which it is not any more" (the symmetric case is
    already refused by consumedShares). Unit test next to the guard.

- Zeroing: the shared path never calls zero, resize or online (tested);
  slices keep zeroSlice in addSlice (see B1 for the creation case).

- Precedence ignoreDevices > pool serials > sharedDevices > sliced, logged

  the one of ignoreDevices (memdevMatches).
- One dax device per node for all claims; per-claim CDI device with

- State compatibility: localDevice.Shared omitempty (an old file loads as
