B1  T17:332-337 and T18:407-412: the "reads zeros before the first write"
    proof of zeroing at region creation (R-D B1) can pass with the
    zeroing broken. The local device's memory is the qemu backend that
    the topology pre-declares (fake-cxl-pool server ops.go:783-784: a
    local device with a binding reuses b.ObjectID, no object-add), so its
    bytes are whatever was written since qemu started: zeros on a fresh
    qemu, an earlier test's leftovers otherwise. In a first run after a
    VM start, or after any test that left zeros at 0 and 1M, the read of
    zeros is true whether or not the driver zeroed. In the logged
    regression it only happened to be meaningful (test17 H leaves TEXT0
    at 0 for test18; test17 run 2 sees run 1's text). What remains is
    the grep of "zeroed new shared dax0.0 size N in", which proves the
    routine ran, not that the bytes are zero (a wrong range or window in
    zeroDax passes).
    Misleads: the comments say "the writer finds zeros where it writes";
    the reader takes it as proof of B1.
    Fix: seed non-zero bytes before the first claim, in both tests, before
    dra-install (the device can be attached first: dra-local-device works
    without the driver):
      dra-local-device "$VM2"
      pool-client "$VM2" guest region create "$DRA_LOCAL_SERIAL" --mode dax
      # write "stale $TAG" with pool-dax-rw.py write /dev/daxN.M at 0 and 1M
      # (and e.g. at size-4K), read it back
      # destroy the region but keep the memdev enabled (cxl destroy-region -f
      # regionN; or guest release + cxl enable-memdev memN)
      pool-cxl-dump ...; cxl-assert "regions == []"
    then dra-install with DRA_DRIVER_CONFIG and keep the zero reads of B
    and L3 as they are (they now fail if zeroing is skipped or partial).
    Seed and read an offset near the end too: a zeroing that stops after
    the first window is the likeliest bug. Keep the log grep.
