3. New case "pool-fs": any filesystem, one writer, three readers
-----------------------------------------------------------------
Setup: demo setup pool-fs [ext4|xfs|btrfs] (default ext4; the type is
DEMO_FSTYPE of run/state.env). Device fs0: 512Mi, shared, persistent,
serial 0xc1ae0001, its files removed first (no filesystem). The driver is
installed with fsTypes: [erofs, <type>] (the trust note of the docs is
printed by setup and in README). The pods use the demo image, which
gains e2fsprogs, xfsprogs and btrfs-progs. Writer on vm1; reader-a and
reader-b on vm2; reader-c on vm1. Steps R1-R11 (T1 title "R3/11"):
R1  "a writer starts on vm1; it has no CXL memory yet"
    kubectl apply -f pool-fs/writer.yaml
R2  "the writer asks for the device as a block device"
    kubectl exec writer -- cxl-request request --serial S --mode block
R3  "the writer makes an empty <type> filesystem on it"
    kubectl exec writer -- /demo/mkfs --type <type>
    (mkfs.<type> of an image file of the block device's size in the
    container, written through the lease fd)
R4  "the writer mounts it read-write instead"
    kubectl exec writer -- sh -c 'cxl-request release --all && cxl-request request --serial S --mode fs --read-write --name data'
R5  "the writer writes hello.txt"
    kubectl exec writer -- /demo/fswrite "Hello from the writer, $(date +%T)"
R6  "three readers start: two on vm2, one on vm1"
    kubectl apply -f pool-fs/readers.yaml
R7  "readers ask to read: vm1's reader at once, vm2's must wait"
    for r in reader-a reader-b reader-c; do kubectl exec $r -- cxl-request request --serial S --shared --mode fs --name data --wait 0s; done
    (reader-c Ready: same node as the writer, one superblock; reader-a
    and reader-b waiting: their claims get AttachFailed reason Conflict,
    the device is attached exclusively to vm1 for a writer)
R8  "the writer adds a line; vm1's reader sees it at once"
    kubectl exec writer -- /demo/fswrite --append "...";
    kubectl exec reader-c -- cat /run/cxl/fs/data/hello.txt
R9  "the writer is done: vm1 turns the filesystem read-only, vm2's readers mount it"
    kubectl exec writer -- cxl-request release --all
    (vm1 remounts read-only, /dev/pmemK read-only; the attachment is no
    longer exclusive; vm2 attaches, reader-a and reader-b Ready)
R10 "each reader reads hello.txt; a write fails"
    for r ...; cat; then kubectl exec reader-a -- sh -c 'echo x >> /run/cxl/fs/data/hello.txt' (expects "Read-only file system")
R11 "everything goes away"
    kubectl delete -f pool-fs/
The views show what is new: t2 "fs rw excl" / "fs ro share" and
"waiting (Conflict)"; t3 the writer and the waiting readers with the
reason; t4 per node the node mount's type and its superblock rw/ro, the
pmem block device's read-only flag, the lease binds; t5 the controller's
"exclusive for a read-write ... claim", AttachFailed Conflict, the
driver's "mounted ... (<type>, rw|ro ...)", "remounted ... read-only";
t6 fs0, its attachments (exclusive or not) and the filesystem's type and
state from the backing file (superblock magic; for ext4 clean or needs
recovery), without parsing files of the writable types.
Zooms as for pool-shared-fs, plus "demo zoom mounts vm1|vm2" showing
superblock ro/rw and the block device's flag.

4. New case "wizard"
--------------------
Setup: demo setup wizard. Devices: vm2's local 1G and vm1's local 256M
(sliced, not shared); a local persistent memdev lp0 512Mi on vm2 through a
second fake-cxl-pool-server without a controller (as test21, serial
0xc100f5e1); pool A (cabled to vm1 and vm2) with pooled0 (512Mi,
exclusive, volatile), shared0 (256Mi, shared, volatile) and fs0 (512Mi,
shared, persistent). Setup formats fs0 and lp0 with ext4 holding
hello.txt (a block writer pod of the demo image) so that fs claims find
something. fsTypes: [erofs, ext4, xfs, btrfs]. The views show the wizard's
objects generically (section 5).
Commands (bin/demo wizard, implemented in bin/wizard.py):
  demo wizard                      interactive: questions, preview, create
  demo wizard new [OPTIONS]        the same without questions; --dry-run
                                   prints the YAML only
  demo wizard list                 the objects it made: name, kind, pod
                                   phase, device(s), node, mode, access
  demo wizard yaml NAME            the YAML of NAME
  demo wizard delete NAME...|--all delete objects it made (pod and claim)
Options (questions in this order; only valid choices are offered; each
answer has a default; the interactive mode shows why a choice is not
available):
  --kind claim|lease               a pod with a ResourceClaim of the
                                   device (claim), or a pod with the
                                   cxl-lease claim and the cxl-request
                                   command to run in it (lease, which the
                                   wizard runs with kubectl exec)
  --source local|pool|any          any = firstAvailable: local, then pool
  --memory volatile|persistent
  --sharing exclusive|shared       shared = capacity shares "1"
  --mode numa|dax|block|fs
  --size whole|SIZE                SIZE: a slice of a local volatile
                                   memdev (block multiples), or the
                                   least size of an exclusive pool device
  --serial any|SERIAL              a device by its serial (the wizard lists
                                   the published devices that fit)
  --read-only / --read-write
  --fs-type detect|TYPE --access direct|cached --path PATH   (fs)
  --steering none|auto|...         (numa)
  --node vm1|vm2|any
  --command idle|env|mkfs TYPE|write TEXT|read
  --name NAME                      default w<N>
Rules (the driver's, pkg/cxl/config and docs/memory/cxl): volatile local
sliced: numa (default) or dax, readOnly dax only, slice or whole;
volatile pool exclusive: numa or dax, whole device, a least size; volatile
pool shared: dax only, exclusive or shared; persistent (local or pool):
block or fs only; block read-write only exclusively; fs read-only by
default, read-write opt-in; a shared persistent device read-write on one
node at a time (the wizard says that a pod of another node waits);
access direct for DAX types only. A choice that the setup's devices
cannot satisfy is still allowed with a warning (the pod will wait), so
that waiting can be shown.
YAML: one file per object in run/wizard/<name>.yaml (a ResourceClaim and
a Pod, labels app=cxl-demo-wizard, cxl-demo/wizard=<name>), with a
comment header that says in words what it asks for; MemoryConfig
entries with apiVersion cxl.nri.io/v1alpha1. Created with kubectl apply
in vm2 (the demo namespace), deleted with kubectl delete.

8. Amendments
-------------
A1 (FSCASE) R4 is cxl-request request --serial S --shared --mode fs
   --read-write --name data: without --shared the writer's companion takes
   all shares and no reader of vm1 could join in R7. The writer still has
   its node alone (the controller's exclusive attachment, singleHost).
A2 (FSCASE) "waiting (Conflict)" comes from the claim's Events (the
   AttachFailed condition goes when the scheduler deallocates the claim):
   the probe gains a kind "events". The controller's "status of ..." lines
   are not trace events. A reader whose attach fails is never shown as
   having a share.
A3 (FSCASE) Captions longer than 50 columns wrap into at most two lines
   in T1 (R7, R9).
A4 (FSCASE) The demo image gains e2fsprogs, xfsprogs and btrfs-progs:
   its tag changes for every case (imported into the VMs once).
