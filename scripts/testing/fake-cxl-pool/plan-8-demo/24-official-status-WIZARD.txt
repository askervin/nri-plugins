6d. Script 5: wizard (every kind of device, any claim)
-------------------------------------------------------
Not a script but a wizard: a few questions choose a pod and its claim (or
lease) among the combinations that the driver accepts, show the YAML,
create it in the demo namespace and delete it again. To demonstrate a
case, and to show what its YAML looks like. demo setup wizard makes every
kind of device:
  vm2's local 1Gi and vm1's local 256Mi CXL memory devices: sliced, a
      claim gets a slice of its own (or the whole device);
  lp0 (0xc100f5e1): a persistent local memdev of vm2, 512Mi, through a
      second fake-cxl-pool-server (local-pmem) that has no pool
      controller, so the node's driver publishes it as local;
  pool A (cabled to vm1 and vm2): pooled0 (512Mi, exclusive, volatile,
      0xc1ee0001), shared0 (256Mi, shared, volatile, 0xc1ae0001), fs0
      (512Mi, shared, persistent, 0xc1ae0002).
Setup formats fs0 and lp0 with an ext4 holding hello.txt (a block writer
pod of the demo image, manifests/wizard/formatter.yaml), so that fs
claims find something, and configures the driver with fsTypes: [erofs,
ext4, xfs, btrfs]. Trust: ext4, xfs and btrfs are not hardened against
crafted images: a node that mounts them trusts every party that can write
the device raw (a read-write block claim or lease of it, on any node of
any cluster that shares the pool, and a read-write fs claim); erofs alone,
the default, trusts nobody (docs/memory/cxl/usage.md, Filesystems).
Setup prints this note.
T1 runs "demo wizard": fifteen questions, each with its choices numbered,
the default marked "*" (Enter takes it), and the choices that the driver
refuses with the reason ("- numa, dax: a persistent device needs mode
block or fs"); q stops. Then what it asks for in words, the warnings
(the pod will wait: why), the same as a command line, and "Enter create,
y the YAML, q quit". The same without questions:
  demo wizard new [OPTIONS] [--dry-run]   (--dry-run prints the YAML)
  demo wizard list                        name, kind, state, node,
                                          device, mode, access
  demo wizard yaml NAME                   run/wizard/NAME.yaml
  demo wizard delete NAME...|--all        pods, claims, leases gone
The options, in the order of the questions ("demo wizard new --help"):
  --kind claim|lease     the pod has a ResourceClaim of the device, or a
                         lease claim and the wizard runs cxl-request in it
  --source local|pool|any        any: firstAvailable, local then pool
  --memory volatile|persistent
  --sharing exclusive|shared     shared: capacity shares "1"
  --mode numa|dax|block|fs
  --size whole|SIZE              a slice of a local memdev, or the least
                                 size of an exclusive pool device
  --serial any|SERIAL            the published devices that fit are listed
  --read-only|--read-write       dax, block, fs (fs: read-only unless asked)
  --fs-type detect|TYPE  --access default|direct|cached  --path default|PATH
  --steering none|auto|first-dram|...   (numa, claims)
  --node vm1|vm2|any
  --command idle|env|read|write TEXT|mkfs TYPE   (/demo/cxl-wizard.py)
  --name NAME                    default w<N>
The rules are the driver's (docs/memory/cxl, pkg/cxl/config/device.go):
- volatile local (sliced): numa (default) or dax, readOnly with dax only,
  a slice of SIZE (rounded up to memory blocks) or the whole device;
- volatile pool, exclusive device (pooled0): numa or dax, the whole
  device, SIZE its least size;
- volatile pool, shared device (shared0): dax only, exclusively (by its
  serial) or one share;
- persistent (lp0, fs0): block or fs only, the whole device, exclusively
  or one share; block read-write only exclusively; fs read-only by
  default, read-write by opt-in (not erofs); a shared persistent device is
  read-write on one node at a time: a pod of another node waits
  (AttachFailed Conflict); access direct for erofs, ext4, xfs only;
- a lease: the same rules, through cxl-request (no path: its filesystem is
  at /run/cxl/fs/NAME; no steering; a request needs a size, a serial or a
  share; a local device only in a pod of its node).
A choice that the devices cannot satisfy now is taken with a warning,
and the pod (or lease) waits: that is how waiting is shown.
Point at: T1 the question screens and the YAML (the comment header says
in words what it asks for); T2 the wizard's pods: "claim" or the lease id
and what it got ("numa 256Mi c100e2e1", "dax rw excl shared0", "fs rw
share fs0", "block rw excl lp0", "waiting (Conflict)"); T3 every device
with its holders and the waiting claims; T4 both nodes, a row per memdev
(region, kmem node, dax device, pmem block device with its filesystem and
ro/rw) and who uses it; T5 the trace; T6 both pool servers: devices,
attachments (exclusive), the filesystem state of fs0 and lp0 in their
backing files ("ext4 clean", "ext4 needs recovery" while a node writes).
A walk (bin/wizard-rules.sh runs all of it and checks each result):
  demo wizard new --name w1 --source local --mode numa --size 256Mi --node vm2
      -> w1: Running; T2 "numa 256Mi c100e2e1", T4 "region0 256M kmem node2"
  demo wizard new --name w12 --source pool --mode dax --serial 0xc1ae0001 --node vm1 --command write "Hello"
  demo wizard new --name w13 --kind lease --source pool --sharing shared --read-only --serial 0xc1ae0001 --node vm2 --command read
      -> w13: waiting: cannot allocate (w12 has shared0 exclusively)
  demo wizard delete w12   -> w13 Ready, its log reads "Hello"
  demo wizard new --name w18 --source pool --memory persistent --sharing shared --mode fs --read-write --serial 0xc1ae0002 --node vm1
      -> waits while another node has fs0 (AttachFailed Conflict), then
         vm1 alone has it read-write (T6 "vm1 exclusive; ext4 needs recovery")
  demo wizard yaml w18     -> the claim and the pod
  demo wizard delete --all
"demo reset wizard" is "demo wizard delete --all".

20. Cause and fix
-----------------
- mkfs.xfs on a block device node sets the device's block size
  (BLKBSZSET), which needs CAP_SYS_ADMIN; an unprivileged container has
  the node (CDI, rw) but not the capability. mkfs.ext4 and mkfs.btrfs do
  not, which is why only xfs failed. The desk tests used a regular file
  as the "node", which has no such ioctl.
- Fix (cxl-wizard.py do_mkfs), as FSCASE's /demo/mkfs: every type is made
  in an image file of the device's size in /tmp (erofs: its own small
  image), then written whole through the device: the node of a claim
  (opened read-write, no ioctl) and fd 3 of a lease alike; the image is
  removed after, the line says the bytes and the time ('made xfs
  (534773760 bytes in 0.8 s), no files ...'). The first MiB is zeroed
  first, as before. README 6d says how mkfs works.
- Desk check (wizard.py check --block, opt-in: it attaches a loop device
  through a privileged docker container, the only privileged step, and
  detaches it in any case): a loop device over a file of 534773760 bytes
  is /dev/pmem9 of an unprivileged container of the demo image (docker
  run --device, no --privileged). There mkfs.xfs on the node fails with
  "cannot set blocksize 512 on block device /dev/pmem9: Permission
  denied" (the live error, reproduced), and the tool's mkfs of xfs,
  ext4, btrfs and erofs succeeds and read finds each type. The tool of
  before this fix fails it (xfs). Run at the desk: passes; losetup -a is
  empty afterwards. Without --block the check says it was not run.
